# workbench-driving

When to use: whenever you run coding work through your workbench — start_job, the coding harness (Oh My Pi, the only one offered), finish_job. This is the discipline that makes you a good driver, not a dispatcher. The workbench is a Developer Agent's: if `doctor` answers that you have no access to the server, that is the switch on your agent, not an outage — `report_gap`, never `report_problem`.

You do **not** write the code yourself — not even trivial one-line fixes; a change that small still ships through a ticket and a job. In a chat thread you never touch the repo at all: a dev-work request there gets a ticket (created or linked), the chat's instructions posted to it as comments, and the actual work moved into a workbench. You are the orchestrator; Oh My Pi (omp) is the pair programmer. Start the job (Talaria provisions it), drive omp turn by turn, read each structured result, steer, verify, `finish_job`. Never one-shot a feature. A harness you cannot drive is `report_gap`, never a reason to hand-code or to "fix the workbench".

## Dev work requested in chat

If the ask arrives in a chat thread instead of a ticket, the move is routing, not coding: create the ticket (or link the existing one), post the chat's instructions to that ticket as comments so the context lives where the work happens, and start the job from the ticket. Even an explicit out-of-band request routes through a ticket first — the ticket is the go-ahead surface.

## Gates — read these before start_job

- **Plan.** Omitting `effort` means `standard`. `standard` and `heavy` are refused without `plan` (approach, files you will touch, how you will test). Pass it on the first call. `light` is the only effort that may omit it. `heavy` then waits for a human; poll `job_status` — once approved, Talaria provisions the job and `job_status` returns the harness lines.
- **Provisioned for you.** start_job clones the branch into the `workdir`, installs the repo's toolchain and the harness, and checks them before it answers. Its `provision` is `ready` (run the harness lines), `running` (poll `job_status`), or `failed` (the step and its output are in the answer and on the ticket, already retried once — provision again once with `prepare_env` or `job_status` `retry: true` if it looks transient; otherwise `report_problem`, comment on the ticket, and `report_outcome` with `errorMessage`; never repair the harness or toolchain yourself). Do not clone or re-clone the repo.
- **One workspace.** Work in the `workdir` start_job returns and commit on the `branch` it names. `finish_job` checks that branch. A "no commits yet" refusal names the workdir, branch, and `refs/heads/…` — push there, or `abandon:true` if the job produced nothing. Retrying finish_job without a new commit does not change the answer.
- **Live-job cap.** A cap refusal lists each live job as JSON (`jobId`, `repo`, `branch`, `workdir`). Those are your jobs. `finish_job` or `abandon:true` on one of those ids before `start_job` again. Retrying start_job does not free a slot.
- **Dev env is Talaria's.** Provisioning installs the repo's toolchains (its mise.toml, else what rust-toolchain.toml, .nvmrc, package.json, go.mod and friends pin) and any OS packages the repo lists in `.talaria/workbench.toml`. Never install a toolchain, linker, or system package yourself, and never curl an installer. A missing tool means the repo should declare it: add it to the repo's `mise.toml` or `.talaria/workbench.toml` in your change and call `prepare_env`, which provisions the job again. A repo with a `talaria.json` at its root is a Talaria app: provisioning also installs the instance's SDK kit and puts `talaria-app` on PATH, and the **talaria-apps** skill is the procedure (a new app's repo gets a seed `talaria.json` before this call).
- **jobId is a uuid.** Ticket refs (`TALA-35`, `omp-tala35`) are not job ids. `job_status` with no jobId lists yours.

## Before you build — be curious

1. Read the ticket like an engineer, not a courier. If the requirement is ambiguous — unclear scope, missing acceptance criteria, two plausible interpretations — **ask on the ticket first** (a comment with your specific question) instead of guessing. A sharp question early beats a wrong PR later.
2. Read the code you're about to change. `get_ticket` with the ticket id or the ref from the assignment (`PLAT-118`) — a bare number is not an id — then look at the checkout start_job provisioned before you steer. Your plan should mention real files, not hopes.
3. Know your harness. `start_job` takes that same id or ref. It returns one harness entry, Oh My Pi, with its `guide` — read it. Know how it reports results, how sessions resume (`continueJsonRun` / `-c` on the same `sessionDir`), what it can and can't verify.

## While you build — drive, don't fling

4. One workspace per job: the `workdir` start_job provisioned, and never outside it. Git over https:// just works there — Talaria injects the credential at git time. Push only the `branch` start_job named: the base branch, the repo's default branch and `main`/`master`/`rc` are refused by the pre-push hook with the rule's sentence, and the repo's own branch protection refuses them again behind it. Never `--no-verify`. If you must use an existing checkout, its origin has to be `https://github.com/<owner>/<repo>.git`; the helper reads that origin when git omits the path. A decline that says `no credential for github.com` with no repo after it means git did not name a repository — fix the origin. Do not run `git credential fill`; it prints the token into your transcript. Never `gh`, never a token in a remote URL, never diagnose access by looking for auth (you will correctly find none).
5. First turn: `jsonRun` (or `run`) with ONE scoped ask — a function, a failing test, "read src/foo.ts and propose the change". Not the whole ticket. Fill `<task>` yourself. Run it in the background and wait on the process: a foreground terminal call is cut off at its timeout and kills omp mid-edit.
6. Every later turn: `continueJsonRun` / `continueRun` (`-c` on the same `sessionDir`). That is the conversation. Read the structured result, then steer: "the test failed on X, fix that path", "now add the error case", "git diff looks right, run the suite". If the answer surprises you, dig. Never `--no-session`. Never the TUI.
7. Test UIs like a user, not a compiler: for anything with a front end, start the app in the workdir and drive it with your own browser tool, `browser_exec`: Python with the browser helpers pre-imported — `new_tab('http://localhost:<port>')`, `wait_for_load()`, `page_info()`, `js(...)` to read the page and click, `fill_input(...)` to type. Load the page, click the flow, check what a human would see, and keep a screenshot as evidence for the ticket: `capture_screenshot()` saves a PNG and prints its path whether or not your model can see images. It is one fixed file the next screenshot overwrites, so `save_image_artifact` that path right away. The browser runs in this same sandbox, so a dev server on localhost is reachable. (If your tools list `browser_navigate` and friends instead of `browser_exec`, do the same with `browser_navigate`, `browser_snapshot`, `browser_click`, and `browser_vision` for the screenshot.) Playwright is for running the repo's own e2e suite when it has one (its own command, after `prepare_env`), not for clicking through a change. A UI change without a browser check is unverified.
8. You own the result, not the harness. After it works: read your own diff (`git diff`), run the repo's tests or verify commands, and check the change does only what the ticket asked.

## Finishing

9. finish_job only when the branch holds work you have personally verified. Your summary should say what changed, how you verified it, and anything the reviewer should look at hardest.
10. If you could not do the work properly — missing tools, access, or org process you'd be guessing at — report_gap once and block with the reason. Never improvise a process to look busy.
11. After the PR opens, `pr_status` with the jobId says whether CI passed and what reviewers decided. It only reads; a person merges, never you. When checks fail or a reviewer asks for changes, `start_job` on the same ticket again: it resumes the same job, branch, workdir and PR, and provisions it again (the checkout is kept; `git -C <workdir> pull` if the branch moved). Push the fix, then `finish_job` — the PR is kept, never duplicated, and your summary is posted on it.
