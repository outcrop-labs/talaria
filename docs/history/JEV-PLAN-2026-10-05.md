# Decision models — audit and integration plan

Dated 2026-10-05. An audit of every place Talaria makes a judgment, measured against what
decision models are good at — TypeSafe's
[System One models](https://typesafe.ai/blog/introducing-system-one-models-and-jev) and anything
built like them — plus the plan to wire them in as an **optional** capability an operator points
at whichever model they want.

Jev is the model the audit measures against, because it is the one that exists and publishes
numbers. It is not the model the architecture assumes.

---

### The two divergences

**The ticket gate had not run since 2026-09-19.** `82eb786e` extracted the module into its own
crate behind a `OnceLock` and never set it, so `ticket_message_relevant` answered `true` for
every non-structural message — not a degraded gate, no gate. The live instance's `harness_runs`
dates it to the hour: nine rows ending 2026-09-19 00:28 UTC, the extraction landing at 04:28
that morning, nothing since. **Phase 1 had no baseline to shadow against**, which is why the
fix came first and the comparison has to wait for traffic.

Two gates now guard that class: an `oncelock-seam-never-set` invariant (which rides
`bun run check`) and a boot assertion in the jobs completeness test. Twelve other injected
edges are never set either, recorded in `UNSET_SEAM_CENSUS` as a backlog that can only shrink.
They are **unaudited**: an unset edge kills the call path that reads it rather than always a
whole feature — the Titler has 49 live harness runs despite one of its edges being dark.

**CI was not running any of the api crates' tests.** `ci.yml`'s api job runs `cargo test` from
`api/`, and because `api/Cargo.toml` is a workspace root that *also* carries a root package with
no `default-members`, bare `cargo test` selected only `talaria-api` — three test binaries, none
of the ~200 under `crates/`. Their test code was not merely unrun but never compiled: a type
error inside a member crate's `#[cfg(test)]` module passed both CI steps. Lint coverage was
fine; `clippy --all-targets` does reach the member crates' libraries.

This matters to the whole programme, not just to one PR: **every number this plan proposes to
trust is produced by code whose tests were decoration.** The flip to
`cargo test --workspace --no-fail-fast` is PR #517 (`--no-fail-fast` because cargo stops at the
first failing *binary*, so one broken crate hid four others alphabetically after it).

Nine tests were failing, and **every one was a cross-check** — the kind whose job is to notice
that something was added and not registered. Three root causes, all repaired: `hermes:work`
reached three of its four registries (and was therefore measured, scored, archived and shown
nowhere); four Google Slides/Sheets tools were registered and invisible to fitness, two of them
with no sandbox backend; and the Hermes Google harness had grown 13 → 17 fixtures with its
counts never updated and five newer fixtures missing arms in the test's helpers.

### What the unstarted phase-2 items actually cost

- **Guard semantic rules** remain the highest-value item, and the landing site is still there:
  `Finding.confidence` and `GuardConfig.min_confidence` exist and are filled with constants a
  developer typed. The cost not visible from the audit: `rule_ids()` feeds the fitness
  adversarial tier, which asserts that *every* rule id is targeted by an adversarial fixture.
  Adding a rule therefore means adding a fixture that attacks it — a good obligation, and the
  reason this is a larger piece than it looks. The guard also runs synchronously in the
  completion path, so a semantic pass belongs detached and observe-only first.
- **Workflow matching** is still the place a semantic judgment most obviously beats what is
  there. Note the layering when it happens: `talaria-workflows` is a leaf with no `AppState`,
  so the question construction belongs in the crate and the call belongs at the two call sites
  that hold state — the same split `TicketRelevanceInput` already uses.
- **Gap dedup** is unchanged from the audit.

## What Jev is, in the terms that matter here

Jev is a decision model, not a text model. You hand it **state** (a string, a JSON object, or
an array of text) and a map of named **questions**, each one of three primitives, and it
answers all of them in one round trip:

| Primitive | Answers | Comes back as |
|---|---|---|
| **Noul** | does this condition hold? | `noul`: a probability 0–1 |
| **Choice** | which one of these options? | `choice`, `probabilities`, `confidence` (≤255 options) |
| **Score** | where on this described scale? | `score`, `legend`, `probabilities`, `confidence` (2–10 levels) |

One `POST https://api.typesafe.ai/v1/systemone` with a bearer key. Independent questions over
the same state go in the same request and run in parallel.

The numbers that decide whether this is worth doing (`jev-1.13.0`, as documented):

- **$0.042 / MTok input, output tokens free.** No output cost at all, because there is no
  generated text to pay for.
- **70–500ms end-to-end.** TypeSafe claims 40×–200× faster than frontier models on this class
  of task; treat that as their marketing and ours to measure.
- **64k context per request**, 32k of it for state plus the longest question.
- **100K tokens/sec, 40 requests/sec**, and the docs warn those limits are moving.
- **Structurally impossible to return an off-schema answer**, so there is no parse-failure
  branch — which is most of what our JSON harnesses' repair turns exist for.
- **Calibrated probabilities on every answer.** This is the part that actually matters to us,
  and §4 is where it pays.

**It cannot write.** Anything whose output a person reads as prose — a title, a summary, a
brief, a reply, a plan document — is out of scope by construction, and that rules out most of
our harness registry. What is in scope is everything we currently ask a text model to decide
and then parse back out of its answer.

## 1. The audit

Thirteen surfaces, each judged on what decides today and what would change.

| # | Surface | Where it lives | What decides today | Jev shape | Verdict |
|---|---|---|---|---|---|
| 1 | Ticket-thread gate | `talaria-harness-defs/.../ticket_relevance.rs` | a full LLM turn returning `{relevant: bool}`, temp 0, Utility seat, fails open | Noul | **First target** |
| 2 | Guardrails | `talaria-gateway/src/guard.rs` | 5 regex rules over the reply + tool record | Noul per rule | **Highest value** |
| 3 | Retrieval rerank | `talaria-retrieval-rerank` | 8-provider cross-encoder registry | Score per candidate | **Near drop-in** |
| 4 | Workflow matching | `talaria-workflows::match_workflow` | case-folded substring keyword match | Noul per workflow | **High value** |
| 5 | Capability-gap dedup | `talaria-gaps::signature_of` | `board_id \| slug(kind)` string key | Choice over open rows | **Good fit** |

| 8 | Judge verdict | `.../judge.rs` | LLM JSON `{verdict, summary, issues[]}` | Choice (verdict only) | **Partial** |
| 9 | Research scoper | `.../research.rs` (scope) | LLM JSON verdict on the ask | Choice / Noul | **Partial** |

For scale: the harness registry holds **40 harnesses**; **13** declare `Output::Json` and the
other **23** declare `Output::Text`. The JSON thirteen are the entire addressable surface
inside the harness system, and only some of those are decisions rather than structured writing.

### The five worth doing properly

**1 · The ticket-thread gate** is the cleanest fit in the codebase, and it reads like it was
written for this. It already returns one boolean. It already runs at `temperature 0.0` because
"a gate that answers differently on a re-read is not a gate". It already fails open by
construction — `OnFailure::Null` plus the caller's `unwrap_or(true)`. Its own header states its
economics outright: it sits in the cheap Utility seat because "the gate's whole economics are
'cheaper than the reply it prevents', and a judge that costs what the answer costs prevents
nothing."

A Noul *is* that gate, at roughly $0.00006 per call for ~1.5k tokens of state, with no output
tokens, no repair turn, and no `normalize_relevant` coercion of `"yes"`/`"true"`/`"relevant"`
into a boolean — because the answer was never a string. It also gets something it does not have
today: a *number*. Right now the gate's uncertainty is squashed into the prompt line "when
genuinely uncertain, answer true". With a Noul the lean-true tie-break becomes a threshold we
can actually tune against observed traffic instead of a sentence we hope the model honours.

**2 · The guardrails** are the highest-value item on the list, and the reason is in their own
header: they are "a cheap, model-agnostic STRUCTURAL check on model output: no LLM call, no
added model tokens — regex over the answer plus the turn's tool record." Five rules —
`zero_tool_claim`, `ungrounded_ref`, `fabricated_outage`, `secret_leak`, `pii_leak` — and every
one of them is a shape match standing in for a meaning.

That tradeoff was correct when the only alternative was a second LLM turn per completion. At
$0.042/MTok with free output it is no longer the only alternative. And the landing site is
already built: `Finding` carries `confidence: f64`, and `GuardConfig` carries
`min_confidence: 0.5`. A Jev-backed rule class fills both fields with a calibrated probability
instead of a regex's hand-assigned constant — which is what `min_confidence` was always
pretending to be.

The rules regex structurally cannot reach are the ones worth having: a reply that *implies* an
action completed without using any of the claim phrasings; a confident answer that contradicts
the tool result above it; a tone or commitment an agent has no authority to make. None of those
are shapes.

**3 · Retrieval rerank** is the shortest path to a shipped adapter. `RERANK_PROVIDERS` is
already a static registry of 8 providers — `tei`, `openrouter`, `voyage`, `together`, `nvidia`,
`pinecone`, `cohere`, `jina` — each with one pure reader for the envelope it speaks, a sealed
key in `app_settings`, a live-or-fallback model catalog, and `provider: "off"` as the default.
Reranking is already declared best-effort: "a provider failure falls back to vector order,
never breaks search." A Jev reader is a ninth arm in that match, scoring each candidate against
the query as a Score question. TypeSafe publishes reranking as one of its own cookbooks.

**4 · Workflow matching** is where a semantic judgment most obviously beats what is there.
`match_workflow` is substring containment over a case-folded `title\ndescription` haystack. A
workflow keyed on `"delivery failure"` does not pull in on a ticket that says "the webhook
retries are flaking", and nobody finds out — the hook just silently does not fire, the agent
works the ticket without the skills and toolkits it was supposed to get, and the output is
merely worse rather than wrong. One Noul per enabled workflow, all in a single request over the
same ticket state, is exactly the parallel-questions pattern. The current keyword match stays as
the fast path and the fallback.

**5 · Capability-gap dedup.** The honesty loop promises "one row per work-shape ever, repeats
bump `seen_count`", and `seen_count` is the ranking signal that decides what an admin sees
first in the Studio's Suggested queue. Identity is `signature_of(board_id, kind)` — a slug of
the agent's own free-text name for the kind of work. So "cannot access staging DB" and "no
staging database credentials" are two rows, each with `seen_count: 1`, and a real recurring gap
reported five ways never ranks. This is entity alignment, which TypeSafe also publishes a
cookbook for: a Choice over the board's open gap rows, plus a no-match option, decides whether
a new report is a sighting of something already filed. The slug stays as the fast path — an
exact signature hit never asks a model anything.

### The three partials

**7 · Inbox command routing** is the textbook function-calling shape — pick an action id, fill
its arguments — and it already has the safety rail that pattern needs: a `verify` closure
checking the answer against `allowed_focus_action_ids`, called from all three places that must
agree. A Choice over the allowed ids cannot return an id outside the list at all, which turns
that verify from a check into a type. But the same harness also emits `payload.message` prose
for a `reply` action, so this becomes two steps: Jev chooses the action and the arguments it can
pick from a list, and a text model writes the message only on the branch that needs one. Worth
doing, after phase 1 proves the port.

**8 · The judge** returns `{verdict, summary, issues[]}`. The verdict is a Choice over a small
enum; the summary and issues are prose a person reads in the review queue. Splitting them is
real work and the judge is the one harness that `RoleFloor::refuses` below its floor, with the
sharpest failure mode in the registry — "a verdict that is trusted and wrong, and its verdicts
move tickets". A Jev verdict with a calibrated confidence plus an LLM-written summary is
probably better than what we have, and it is explicitly not a phase-1 experiment.

**9 · The research scoper** judges the ask before anything is planned. Its verdict half is a
Choice; it is low-risk and low-traffic, so it is a good second proving ground but not a
priority.

### 10 · The one new product capability

In a group channel an agent speaks only when @mentioned. In a ticket's task room, the assigned
agent also answers whatever the relevance gate says is for it. That asymmetry is deliberate and
the module says so — no chatter. But it means an agent that could answer a question in #eng
stays silent unless somebody remembers it exists.

A Noul — "is this message something this agent, specifically, should answer?" — at sub-100ms
and effectively free is the first time that gate has been affordable to run on every message in
every channel. It is also the single highest-risk item here, because the failure mode is agents
talking over people in a shared room. Ship it **off by default, per channel**, and only after
phase 1 has produced real precision numbers for the same question on ticket threads.

## 2. What we are deliberately not doing

**Grading model fitness with a model.** Tier 2 of the fitness suite states the invariant
directly: `taskScore` is "the fixture's own deterministic `check`. No model judging a model."
Jev is a model. A Jev-graded fixture would mean the ruler moves when a vendor ships new weights,
and the suite's whole claim is that "if the benched number and the observed number ever diverge,
it is because the model changed, not because the ruler did." Not negotiable, and worth writing
down so nobody rediscovers it as a good idea.

**Anything in the 23 `Output::Text` harnesses.** Jev does not generate text. Titler, Summarizer,
Muse, Briefer, Distiller, Concluder, the blurb writer, plan-doc, work-session and the whole
Hermes family stay exactly as they are.

**Replacing deterministic code with a judgment.** Status categories, permission checks, ACLs,
approval entitlement, the workchain DAG's derived states, `collating_cmp`, dependency
resolution, the price oracle — these are rules and lookups with right answers. TypeSafe's own
guidance is to keep known rules, calculations and exact lookups in code, and the repo already
agrees with it.

**Letting a judgment move a ticket to `done`.** `AGENTS.md`: never force a `done` transition.
A confidence score is not a human sign-off and must not become one.

## 3. The architecture: one port, any decision model

**The requirement is not "Jev, with an open-source escape hatch". It is that an operator can
run whatever decision model they want, and Jev is one entry in that list.** Talaria already
treats every other class of model this way — LLM endpoints are a registry an admin fills, and
so are rerankers — and a decision model is no different. The shipped adapters are a convenience,
never a ceiling.

A new crate, `talaria-decide`, modelled field-for-field on the rerank registry because that
pattern is already load-bearing in this repo and an operator already knows how to drive it.

```
talaria-decide/
  lib.rs             the port — Question (Noul | Choice | Score), State, Answer, confidence
  registry.rs        DECIDE_PROVIDERS: the static meta table + sealed-key config
  adapters/jev.rs    POST api.typesafe.ai/v1/systemone          hosted, calibrated
  adapters/tei.rs    POST {url}/predict                          local classifier sidecar
  adapters/gw.rs     any Talaria-routed model, constrained JSON  universal, needs logprobs
  adapters/http.rs   any endpoint speaking one of the above      bring your own
```

Config is one `app_settings` row, `decide_config`, shaped like `rag_rerank_config`:
`{provider, url, model, keySealed, …}`, the key envelope-encrypted through `SecretBox`,
plaintext never reaching the client, and **`provider: "off"` as the default**. That default is
how "optional feature" is honoured in fact rather than in prose: on every existing install, and
on every fresh one, the port is off and every call site runs exactly the code it runs today.

### The adapters, and what each one honestly gives you

Four, because they cover the four *shapes* an operator's decision model can arrive in — a
hosted decision API, a local classifier, a chat model they already registered, and anything
else. The fourth is the one that makes the list open rather than a menu.

**`jev`** — the hosted model. Full three-primitive support, multi-question parallel fan-out in
one request, calibrated probabilities, 70–500ms. Needs an API key and sends state to TypeSafe,
which is a real consideration for a self-hosted product and is why it can never be the only
option.

**`tei`** — a local classifier, credible because we already run the infrastructure.
`text-embeddings-inference` is in `docker/sidecars.compose.yml`, the embeddings
client already talks to it, and the rerank registry already calls its `/rerank`. A zero-shot
NLI or cross-encoder model served from the same sidecar answers Noul- and Choice-shaped
questions as sequence classification, and a classifier's softmax over labels is a genuine
probability — not a token sampled from a text model and read as if it were one.

Be honest about the ceiling: no multi-question fan-out (it is one forward pass per question),
weaker on long or heavily structured state, and Score needs encoding as ordered labels. It will
not match Jev. It will beat a substring match, it costs nothing per call, and no state leaves
the operator's machine.

**`gateway`** — any model an operator has already registered, asked for a constrained answer.
Universal, and the one whose confidence may simply not exist: `logprobs` is not plumbed
anywhere in the relay (`grep -rn logprob api/crates` returned nothing), and without a
distribution every threshold in §4 is a coin flip wearing a number.

**This turned out not to need the relay at all** — recorded here because the plan said it
would. The adapter resolves the endpoint row and its sealed key through
`talaria_gateway::registry`/`provider` and calls the upstream `/chat/completions` directly over
the shared `HttpFetch` edge, exactly as the rerank providers already do. So it sets `logprobs`
on its own request and reads them off its own reply, and no change to the metered relay path
was required. What it does instead is report `calibrated: false` on any endpoint that answers
without them, so a call site can refuse to gate on a number that is not real.

The remaining honest gap: a model that cannot hold the one-token contract is only discovered
per call. Declaring `logprobs` as a measured capability would surface it on the fitness sheet
instead — see the open questions.

**`http`** — a URL, an optional sealed key, and a declaration of which wire shape the endpoint
speaks (TypeSafe's `/v1/systemone`, a TEI-style `/predict`, or OpenAI-compatible chat). This is
the adapter that makes the registry open: a System One competitor, a fine-tuned classifier
behind vLLM, an in-house service, or a model that does not exist yet needs no code from us.

**No blessed default, and no recommended model.** The rerank panel already set this precedent
and it is the right one: fetch the live catalog where the provider has one, fall back to a
documented list where it does not, and let the operator choose. Talaria's job is to make the
choice real and to tell the truth about what each option can do — not to have an opinion about
which model an operator should run.

### The invariant every call site carries

Modelled on the harness contract's `OnFailure`, which exists for exactly this reason — before
it, "the model returned something I could not use" was answered differently and silently at
every call site.

**As built this is an `Option`, not an enum, and the change is worth recording.** The plan
first described a `DecideFallback { Keep, Fixed(Answer) }` that each call site would declare.
But the port cannot *run* a call site's fallback: only the caller knows whether its
deterministic answer is a keyword match, a slug comparison, or a costed fail-open. So `decide`
answers `Option<_>` and `None` means "run your own path" — which is the shape `rerank` already
uses, for the same reason. A second helper applies the threshold:

```rust
/// Some only when a judgment arrived, the number behind it is real, and it clears the bar.
pub fn gated(j: Option<Judgment>, min_certainty: f64) -> Option<Judgment>
```

`None` therefore covers all of: provider `off`, incomplete config, a primitive the provider
cannot serve, a malformed question, a refusal or timeout, an unreadable reply, confidence below
the site's threshold, and `calibrated: false` where the site gates on confidence. The property
that follows is the one that makes this safe to ship: **with the port off or broken, the
product behaves exactly as it does today.** No call site may be written such that turning the
port off makes it worse than it was before the port existed.

## 4. Confidence is the actual feature

It is tempting to read this whole plan as a cost and latency play. It is not. The thing Talaria
gets that it cannot get today is a *number* on every judgment.

Right now every one of these decisions is binary at the point of use. The ticket gate's
uncertainty is a prompt line. A guard finding's `confidence` is a constant a developer typed. A
workflow either matched a substring or did not. There is nowhere to put "probably, but ask".

With calibrated probabilities each site gets a threshold chosen from what a wrong answer
actually costs there — TypeSafe's confidence-routing pattern, and it maps cleanly onto
structures this repo already has:

| Site | Low confidence should | Existing machinery |
|---|---|---|
| Ticket gate | fall open (reply anyway) | `OnFailure::Null` + `unwrap_or(true)` |
| Guard rule | observe, don't disclose | `GuardMode::Observe`, `min_confidence` |
| Judge verdict | escalate to a human | `OnFailure::Escalate` + the approvals census |
| Workflow match | fall back to keywords | the existing `match_workflow` |
| Gap dedup | file a new row | today's behaviour |
| Rerank | fall back to vector order | already declared best-effort |

Every row's right-hand column already exists. That is the strongest argument that this
integration is a fit rather than a graft: the places a calibrated probability would route to are
already built, already named, and currently reachable only by failure.

## 5. The plan

### Phase 0 — the port, zero call sites — **BUILT** (#518)

Build `talaria-decide` with all four adapters and no consumers. Admin surface under
Admin → Agents, leading the tab: provider picker, URL, wire, model, key, timeout, a capability
sheet per provider, and a Test button. Ships with `provider: "off"`, so merging it changes
nothing anywhere.

*Verified by:* `bun run gate`; unit tests per adapter against recorded responses from each real
service; one live smoke call per configured provider through the Test button.

### Phase 1 — the ticket gate, in shadow

**Blocked on a prerequisite that phase 1 itself uncovered, now fixed.** The gate's
`TICKET_RELEVANT` edge was never set after `82eb786e` extracted the module into its own
crate, so `ticket_message_relevant` answered `true` for every non-structural message from
2026-09-19 until 2026-10-05 — no gate at all. The live instance's `harness_runs` dates it:
nine `ticket-relevance` rows ending 2026-09-19 00:28 UTC, the extraction landing at 04:28
that morning, nothing since.

That matters to the plan and not only to the product: **there was no baseline to shadow
against.** A comparison needs the existing harness to be deciding, and it was not. So phase
1 now has an ordering it did not have before:

1. **Wire the gate and let it run.** Done, with two gates against the class
   (`oncelock-seam-never-set` plus a boot assertion). The product needs some days of real
   traffic through the restored gate before any comparison means anything — on the live
   instance, nine runs over its whole prior life is not a sample.
2. **Then shadow.** Only once the baseline is producing decisions again.

The original phase-1 text follows, unchanged, because it is still what step 2 does.



Wire site #1 and run it **in shadow mode first**: on real ticket-thread traffic, call both the
existing LLM harness and the configured decision provider, record both answers plus the
probability and the latency, and let the existing harness keep deciding. Change nothing a user
sees.

Then read the numbers off real traffic and pick the threshold from them: agreement rate, the
distribution of Jev's probability on the cases the two disagree about, p50/p99 latency, and cost
per thousand gate calls against the Utility seat's actual ledger spend. Flip the gate over only
once that table exists, and keep shadow recording for a week after.

This is the phase that decides whether the rest of the plan is worth executing, and it has to be
measured on captured production traffic rather than fixtures — the gate's failure modes are
chatter and silence, and neither shows up in a suite written by the person who wrote the gate.
The harness eval fixtures get replayed too, but as a regression check, not as the evidence.

*Verified by:* a shadow-traffic comparison table from the live instance; the 6 existing
`ticket_relevance` eval fixtures replayed green through the fitness suite (including the
prompt-injection one — "an instruction embedded in the message cannot silence the agent", which
a Choice-shaped answer makes structurally unreachable); the chatty/quiet behaviour exercised by
hand in the running app on a real board.

### Phase 2 — the four that are worth it — **rerank built** (#518), the rest not started

In rough value order, each independently revertible and each keeping its deterministic path as
the fallback:

1. **Guard semantic rules** (#2) — new rule ids alongside the five regex ones, not replacing
   them. Default to `Observe` so the first weeks produce findings nobody is shown, and promote
   to `Annotate` per rule once the false-positive rate is known.
2. **Workflow matching** (#4) — keyword match stays the fast path; Jev runs on the misses.
3. **Rerank** (#3) — the ninth arm of `RERANK_PROVIDERS`. **Built**, and the shape is worth
   recording: it asks for no credential of its own, delegating to the port's config, and scores
   candidates with one Score question *per candidate over shared state* in a single request.
   The levels describe situations rather than a scale, and a Score lands between levels, so the
   result is an ordering rather than buckets; dividing by the level span puts it on the same
   0..=1 axis a cross-encoder already uses. A provider that cannot fan out is refused rather
   than spent N times, and reranking is best-effort, so that refusal is vector order.
4. **Gap dedup** (#5) and **brief focus rank** (#6) — both additive over an exact-match fast
   path.

### Phase 3 — expose it

Only once phases 1–2 have produced our own numbers. Then the proven port becomes a product
primitive: a Jev-backed condition in a task workflow's match rules, a `decide()` in
`@talaria/sdk` for apps, and an MCP tool so a Hermes agent can ask for a typed judgment instead
of prompting a text model and parsing the answer. Each of those is a public surface with its own
docs, conventions and support burden, which is precisely why it comes after the evidence.

### Not scheduled

The partials (#7 inbox routing, #8 judge verdict, #9 research scoper) and #10 channel speech
land opportunistically after phase 2, each on its own merits. #11 approval urgency is a
nice-to-have. #12 stays rejected.

## 6. Risks

**Latency in the request path.** 70–500ms is fast for a decision and slow for a gate on every
channel message. The brief's focus card has a stated ten-second deadline; the guard runs on
every completion. Every call site needs a timeout whose expiry is just `DecideFallback`, and the
shadow phase is where we find out which sites can afford a round trip at all.

**A hosted dependency in a self-hosted product.** Mitigated by the `off` default and the `tei`
adapter, not by a promise. This is also the live lesson from
`prefer-live-upstream-images-over-private-mirrors`: depend on the maintained upstream directly,
and keep a real replacement rather than a mirror of someone else's artifacts.

**Moving rate limits.** The docs say limits "are adjusting dynamically" and may change without
notice. 40 req/s is not a lot if the guard runs on every completion on a busy instance, so the
port needs the breaker-and-fallback posture the notify outbox already has, not retry-forever.

**Calibration is domain-specific.** TypeSafe's own guidance: the models are trained for
calibrated decisions, and you still have to validate them in your domain. Every threshold in
this plan is a number to be measured on our traffic, and none of the ones quoted in TypeSafe's
cookbooks should be copied in.

**State leaves the building.** A ticket's description, a channel message, an agent's reply — the
Jev adapter sends real customer content to a third party. That needs saying in
`docs/ENCRYPTION.md`'s neighbourhood and on the admin panel itself, next to the key field, not
buried in a changelog.

## 7. Open questions

- Does Jev's 32k state budget hold the guard's grounding context — a full reply plus the turn's
  tool record — or does the guard need to pre-select spans in code first?
- Should `decide_config` be one instance-wide provider, or per-site (so rerank could run on
  Jev while the guard runs on a local classifier)? The rerank precedent is one row; per-site is
  more rope, but it is also what "use any model you want" means if an operator wants two.
- Do the shipped adapters need a declared capability sheet — which primitives each one serves,
  whether it fans out multiple questions, whether its confidence is real — so a call site can
  refuse a provider that cannot answer its question shape? The LLM side already has
  `ALL_CAPABILITIES` and `RoleFloor` for exactly this problem.
- Is there an org-level opt-out, so one workspace on a shared instance can refuse to have its
  tickets sent to a hosted decision model?
- Decision calls do not land in the token ledger. The `gateway` adapter calls its endpoint
  directly rather than through the metered relay — deliberately, because a decision is not a
  conversation and the relay would put guard passes and persona accounting on a yes/no — but
  that means spend on this port is currently invisible. At $0.042/MTok with free output it is
  nearly free per call; at guard-on-every-completion volume it stops being nearly free. Worth
  closing before phase 2, not before phase 1.
- The `gateway` adapter speaks OpenAI-compatible `/chat/completions` only: `logprobs` and the
  one-token contract belong to that dialect, so a native Anthropic or Gemini endpoint is
  reachable only through a compatibility layer. Is that worth widening, or is `custom` the
  honest answer for anything else?
