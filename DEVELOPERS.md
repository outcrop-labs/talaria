# Talaria — for developers

This is the working guide: how the platform is laid out, how to run it, how to build against
it, and the index of every doc in the repo. It's the companion to [`README.md`](./README.md)
— the README sells the product; this page is the map for the people who build and run it.

How the platform actually works — the two planes, the request lifecycle, the auth stack, the
fleet — is [`docs/ARCHITECTURE.md`](./docs/ARCHITECTURE.md). Conventions and pull-request
norms: [`CONTRIBUTING.md`](./CONTRIBUTING.md).

---

## Quick start

One script takes a blank machine to a running instance (it generates `ui/.env`, the fleet config
plane, the `talaria` docker network, pulls infra images, installs deps, and prints your admin
login):

```bash
bun talaria setup           # first-run setup — prints your generated admin credentials
talaria dev                 # dev infra + the app → http://localhost:5273
```

Setup also puts a bare `talaria` command on your PATH — a two-line sh shim in bun's bin dir
(`~/.local/bin` if bun's isn't there; `TALARIA_BIN_DIR` overrides) that runs this checkout's
CLI from anywhere. It points at the checkout that most recently ran setup, so re-running
setup elsewhere repoints it. The rest of this repo spells `bun talaria …` because that form
works on any fresh checkout with no setup step.

Then:

1. Sign in, add an LLM provider on `/models` (keys are encrypted in the DB).
2. Set your organization in Admin.
3. Design your first agent on `/agents` — Muse drafts the whole thing from a description. Talaria
   renders the fleet and brings it up under the `talaria-fleet` compose project; each agent's models
   route through Talaria's gateway.

### Updating an install

An install updates itself: `Admin → Security → Updates` shows the running commit, checks the
remote, and `Update now` pulls, installs, builds into `dist-next`, swaps it for `dist` (the old
build stays one generation as a manual rollback), and restarts the server through
`scripts/update-restart.mjs`. Manual by default; the `Update automatically` toggle opts into a
scheduled check every few hours. Dev installs never update (vite reloads on its own), a dirty
checkout is refused rather than pulled over, and `TALARIA_UPDATER=off` is the kill switch for
installs supervised some other way (systemd and friends, which own their own restarts). Logs land
in `logs/talaria.log` and `logs/updater.log` at the repo root.

### Back up the root key

`TALARIA_SECRET_KEY` lives in `ui/.env`. **Copy it somewhere a snapshot isn't.** Every stored
secret is sealed with it, and a database restored without it cannot read its own secrets
([`docs/ENCRYPTION.md`](./docs/ENCRYPTION.md) explains how protection works and the one rule
that keeps secrets recoverable).

`Admin → Secrets` lists everything the instance holds sealed, per row, with whether it can still be
decrypted and a way to clear anything that cannot.

App-level auth and data/infra details are in [`ui/README.md`](./ui/README.md).

## Repository layout

| Path | Piece | Build / test |
|---|---|---|
| [`ui/`](./ui) | **Talaria app** — the product: every surface, the LLM gateway, the fleet renderer/orchestrator, the app-platform host + `@talaria/sdk` | `cd ui && bun i && bun run dev`; `bun run typecheck` |
| [`apps/`](./apps) | **Talaria apps** — self-contained apps that compile into the deployment (installed via the marketplace or git). Ships the `contacts` reference app + dev guide | see [`apps/README.md`](./apps/README.md) |
| `fleet/` | **rendered fleet** (gitignored — generated, so no link: it does not exist in a fresh checkout) — one chassis renders every agent into `docker-compose.yml` + `fleet.json` (model → each agent's persona-gateway url + key) | generated by the app |
| [`mcp/`](./mcp) | **talaria-mcp** — the agent-facing MCP server: 51 tools, every call proxied to the app with the agent's own key; guardrails hold server-side (no assignee writes, no terminal status moves) | `cd mcp && bun i && bun run build` |
| [`plugin/talaria/`](./plugin/talaria) | **Hermes plugin** (dormant — nothing mounts it): registers, heartbeats for work, reports up to `quality_review` | `python3 -m py_compile plugin/talaria/*.py` |
| [`docker/dev-compose.yml`](./docker) | **dev infra** — Postgres, Redis, Qdrant, TEI embeddings, MinIO, SearXNG. The app runs on the host; the fleet runs under its own compose project | `docker compose -f docker/dev-compose.yml config` |
| [`cli/`](./cli) | **the `talaria` CLI** — setup, dev, boxes, worktrees, resets, deploys, backups: every way to drive the repo. Command table: [`docs/CLI-REFERENCE.md`](./docs/CLI-REFERENCE.md) | `bun talaria --help` |
| [`RELEASING.md`](./RELEASING.md) | **release channels** — nightly/RC/stable, the branch model, how a release is cut, the GHCR tags | read it |
| [`package.json`](./package.json) | **the runner hub** — Bun is the installer and runner for the whole repo. From the root: `bun run dev` (full stack), `build`, `start` (production server), `test`, `typecheck`, `check` (invariants + docs + generated references), `verify` (all of it) | `bun run verify` |

The fleet itself is **rendered**, not hand-written: Talaria materializes `fleet/` (gitignored) from
one Talaria-owned chassis when you design an agent in the app. Don't edit it by hand.

## Dev loop

1. Make the change, verify it: `bun run typecheck` in `ui/` (and `bun run build` where relevant).
2. Exercise the affected path in the running app (`bun talaria dev` → <http://localhost:5273>).
3. Update `CHANGELOG.md` and include what you verified with the change
   ([`CONTRIBUTING.md`](./CONTRIBUTING.md)).

Reset or start over: `bun talaria reset <mode>` clears a wedged stack (secrets, database, or
fleet); backups and restores are `bun talaria backup` / `bun talaria restore` and
[`docs/BACKUPS.md`](./docs/BACKUPS.md).

Manual dev fixture: `node scripts/seed-daily-brief.mjs` seeds a workspace with a realistic
morning (blocked/review/inbox tickets, unread DMs, notifications) and then drives the Home daily
brief through the real `openBrief`/`sweepBrief` as the day moves — an empty install only ever
shows "nothing is waiting on you". It only ever touches rows it wrote; `--clean` removes those.

### Plugin: dormant, mounted by hand

The plugin lives once in this repo (`plugin/talaria/`), but it is **dormant**: nothing in the
fleet render mounts or enables it, and it still targets the legacy mission-control integration.
There is no distribution wiring — if you ever want it on an agent, mount the directory into
`/opt/data/plugins/talaria` and opt in via `plugins.enabled: [talaria]` by hand.

### Working in parallel

Spin up an **isolated** dev stack per branch instead of running two servers against one database —
see [`docs/WORKTREES.md`](./docs/WORKTREES.md) (`bun talaria worktree <name>`). For parallel
*agent* sessions, the containerized alternative is a devbox — a full stack per
task with the agent CLIs inside: [`docs/DEVBOX.md`](./docs/DEVBOX.md)
(`bun talaria box new <name>`).
