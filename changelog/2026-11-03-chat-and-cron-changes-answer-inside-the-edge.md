- **Fixed: a chat with an agent that is slow to its first word, and a cron change on a slow agent, now answer inside Cloudflare's 100 s instead of getting its 524.** Every real instance sits behind a Cloudflare tunnel, which answers 524 when the origin has sent no headers for 100 s. `/api/chat` held its headers until the agent opened the turn, and an agent that has taken the turn but is slow to its first frame (a long context, a compaction) gets five minutes for that. So the person got a 524 for a reply that went on and landed. Now the route waits at most 30 s for the agent's own answer. Past that it answers 200 `text/event-stream` at once and sends a `: waiting for the agent` comment every 15 s until the agent speaks, and then the reply streams as before. That also names a new thread sooner, so a Stop on its first turn has an id to use. A turn that opens within 30 s is answered exactly as before. If the agent answers with an error status after the 200 has gone out, the error goes into the stream as a failure frame, and the reply lands as an error that says why. A cron create, schedule edit or run is several calls on the agent. Each call had its own 40 s bound, but the whole had none, and a guarded schedule edit can be six calls. Now the request waits 75 s for the whole change, and past that it answers 503 that the change may still land, while the change runs on to its end and its outcome is logged. A thread's schedule writes its row in that same task, so a create that lands late still reports into the thread. Creating one job on many agents now runs the creates side by side, and the cron work done when a thread is deleted, archived or restored waits at most 75 s. One trade-off stays, set deliberately in #647: when a person is reading a chat and the agent comes back 80 to 120 s after a restart, they get the "didn't come back within 80 seconds" reply where the two-minute hold used to wait for it. That reply is kept in the thread and tells them to send the message again. An app's agent turn (`/api/llm` on an app's key) keeps its two-minute hold. Only the app host holds an app key, and it reaches the api over the instance's internal URL, never through the edge.
