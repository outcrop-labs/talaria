- **Talaria Desktop releases are signed again, by a new update-signing key, `7DA247B3586A9245`.** Since the move to `183E3397DE42EB98` on 2026-11-12, every `desktop-package` run on `main` failed on every platform at signing with "incorrect updater private key password: Wrong password for that key". The password saved in the `desktop-release` environment did not open that key, and nobody had kept the right one. No desktop release was made in that time, so `desktop-v0.12.0` stayed the newest and no install ever trusted `183E3397DE42EB98`. `desktop/src-tauri/tauri.conf.json` now carries the new key's public half, and the new key and its password are the `desktop-release` secrets. An install checks an update against the key it was built with, so every copy up to `desktop-v0.12.0` still fails Update once and is reinstalled by hand from the first release this key signs. Updates work again from then on. RELEASING.md now says to sign a file with a new key before saving its secrets.

  Verified: with tauri-cli 2.11.4, the new key and its password sign a file through the same two environment variables `sign-update.sh` uses. `write-latest-json.py`'s own key-ID parse reads `7DA247B3586A9245` from that signature, from the new key's `.pub`, and from the pubkey now in `tauri.conf.json`. `write-latest-json.py --self-test` passes with the new key as the shipped one and `183E3397DE42EB98` as the key it must refuse. The `183E3397DE42EB98` key file does not sign with an empty password either, so it is unusable without the lost password. Both `desktop-package` runs on `main` since 2026-11-12 (the v0.14.0 and v0.15.0 promotions) failed at that signing step on Linux, macOS and Windows. The first signing in CI happens on `main`, because `desktop-release` admits only `main`.
