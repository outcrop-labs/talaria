- **An agent's or an API key's "last used" stamp lands at most once every five minutes and without waiting on the disk, a resource-sample tick is one asynchronous commit, and the approval, digest and Hermes job state is written only when it changes.** On a slow disk every synchronous commit waits its turn in the WAL flush queue, and these writers queued one on every agent call and every tick. `agent_keys.last_used_at` (stamped on every per-agent authentication) and `llm_api_keys.last_used_at` (on every `/api/llm/v1/chat` and `/models` call) now go through one coalescer per process: inside five minutes of a key's last stamp the call spawns nothing and checks out no connection. The stamp that does go out is `update … where id = $1::uuid and (last_used_at is null or last_used_at < now() - interval '5 minutes')`, so a second api process inside the window matches no row, takes no transaction id and commits nothing, and it runs in a transaction with `synchronous_commit = off`. The `::uuid` bind replaces a `::text` cast that kept the agent-key stamp off the primary key, and the TypeScript twin in `ui/src/server/agent-auth.ts` carries the same guard. A key's first stamp still lands on its first call, so the legacy migration status's `migrated` reads exactly as before; secret-health's agent-credential row and Settings → API keys' "Used N ago" may lag the truth by up to five minutes. The resource sampler parses a tick, then writes its rows in one multi-row `INSERT … SELECT * FROM unnest(…)` plus the seven-day samples prune, in one transaction with `synchronous_commit = off`; a Postgres crash can lose the last fraction of a second of samples, one tick at most. The leak check runs after the commit on the same rows, and the run-transcript prune (user data) stays its own synchronous statement, which matches nothing on almost every tick. The approval SLA's escalation state and the digest's sent-on ledger save through a new `talaria_settings::set_setting_if_changed`, which writes only a value that differs as jsonb compares (key order never counts) and takes no row lock when it does not; `set_setting` is unchanged, so an admin's save still moves the `updated_at` secret-health shows as "set at". The announce-mark prune writes only when it drops a mark, and computes the kept map from the row it updates, so a mark claimed while it waited for the row is never lost. The Hermes channel says a rollout's detail without writing or locking the state row when the detail is already what it says (an Upgrade waiting out its 48 h on stable rewrote the whole TOASTed state every minute), and a state patch that changed nothing and asks for no effects no longer rewrites the row. Everything a person or agent reads is otherwise the same values, written synchronously when they change. Verified: CI on this PR's checks, including the live integration modules against Postgres (a hundred concurrent authentications of one agent leave one stamp, committed with `synchronous_commit` off, and none after it; a six-minute-old stamp is refreshed while a second process's stamp inside the window matches no row; a never-used agent moves out of the migration status's pending list on its first call; the same for an LLM key through the real `/api/llm/v1/models` route; a six-agent tick is six rows with one `xmin`, `synchronous_commit` off inside it and on after, with the aged samples pruned in the same transaction; an equal setting in another key order leaves `xmin` unchanged while a different one and `set_setting` write; a prune that drops nothing leaves the row's `xmin` and `xmax` unchanged; two quiet Hermes steps leave the state row's `xmin` and `xmax` unchanged and the step whose detail changes writes it), and unit tests of the five-minute coalescer on an injected clock and of the tick's parse. Measured with `write_load_stamps_live_census` (one simulated hour of a six-agent instance on synthetic rows, through the writers' own functions, a CHECKPOINT every five simulated minutes) on a throwaway postgres:16-alpine with nothing else connected, three runs on each build, alternating, each on a fresh copy of the migrated schema: before, 781 write transactions an hour, every one synchronous (agent keys 267, samples 420, Hermes 60, approval SLA 24, LLM key 6, digest 4), and 1,005,296–1,009,848 bytes of WAL; after, 136, of which 135 commit asynchronously (agent keys 69, samples 60, LLM key 6) and 1 synchronously (the Hermes detail's hourly change, "0 h" to "1 h"), and 719,216–722,544 bytes of WAL. Most of the WAL left is the sample ticks' full-page images after each checkpoint (694 kB before, 618 kB after); the checkpoint and compression settings are the other pull request's. The census writes no instance data: its agents, keys and samples are synthetic.
