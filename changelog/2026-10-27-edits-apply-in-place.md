- **Editing a running agent no longer restarts it unless the edit needs a restart. A toolset or delegation-cap switch, a soul edit, an MCP grant, an assignment, a team or user grant, a connected account, a server or app turned on, off or removed, the org profile and the org toolset floor all reach the agent in place from its next turn. A container is recreated only when compose says its service moved.** Every one of those edits used to roll the agent: it went offline for about a minute and held a turn in flight, for a change Hermes would have read on its next turn anyway.
  - **Apply, not roll** (`apply_agent_change`, talaria-fleet-reconcile). An apply renders, then compares `docker compose config --hash` for the agent's service with the `com.docker.compose.config-hash` label on the running container (`container_fit`, talaria-fleet-docker). That hash is compose's own digest of the image, the environment (every `${VAR}` interpolated, every `env_file` read in), mounts, limits and labels. Only a container that no longer matches is rolled. On a running container, a digest that cannot be read reads as changed and rolls, as every edit did before. A stopped agent stays stopped and reads the render when it starts, and an apply never starts one: a container docker will not inspect (a timeout, a daemon error, anything but docker's own "no such object") is asked again with 30 s of patience, rolled only if it is then seen running, and otherwise left alone with a sentence that the change is rendered but not applied. The roll reads the container once more under the service's lock, so a stop made while it renders and pulls stands.
  - **The part of config.yaml Hermes reads only at start** (`model_routes` is parsed once in the API server adapter's constructor, and plugins load at boot) is a service label, `talaria.config-start-hash`. It is a digest of the rendered config minus the paths a running Hermes v0.22.4 takes from the in-place rewrite: `agent.disabled_toolsets`, `delegation.max_concurrent_children` and the `mcp_servers` names (`LIVE_CONFIG_PATHS`). An edit to anything else moves the label, so the agent rolls.
  - **A tool list that changes under a server name the agent keeps.** This covers a subset widened, a team or user grant, an app's new catalog and a connected account. The change is counted for each server it touches (`bump_tool_lists`, one `mcp.tool_list_count:<server>` per server), so only that server is listed again, and only by the agents that hold it. The MCP gateway answers that agent's next keepalive `ping` (every 180 s by default) with `notifications/tools/list_changed` ahead of the result, and Hermes lists the tools again. The Rust gateway does this, and its TS twin does the same for `app-*` servers. On a connection whose third-party upstream did not answer ping, Hermes keeps alive with `tools/list` instead, so the Rust relay also puts the notice ahead of a `tools/list` answer for an agent behind the count.
  - **A server connected after the agent saw it unconnected.** The in-house not-connected handshake now issues a `talaria-nc-` session id. Once the account is connected, a request on that session is answered 404, which Hermes reconnects on. The new session's first `tools/list` carries the notice, so the real catalog replaces the `connection_required` placeholder.
  - **The app's api proxy passes `mcp-session-id` through**, and `mcp-protocol-version` beside it. It had dropped the session header from every MCP gateway answer, so no agent ever held an upstream session, and every MCP server that keeps sessions refused the requests after its handshake. The gateway now also relays the agent's `mcp-protocol-version` and a resumed stream's `last-event-id` upstream; it had relayed only the session id.
  - **What still rolls:** the Developer switch, a key rotation, an MCP server's timeout or auth-mode edit, the operator's roll and restart, and the update job's fleet roll. **None of them starts an agent someone stopped** (`roll_running_agent`): each recreates a running agent, and leaves a stopped one stopped to take the change at its next start. A roll of a stopped agent from its controls is refused (409, start it instead), and a key rotation answers `rolling: false` for one. The fleet roll's *Also start and roll agents that are stopped* is the one roll that starts them, because a person ticked it.
  - **Removing a model or provider in Models no longer starts an agent someone stopped.** The cascade used to `compose restart` every agent it changed, and compose starts a stopped container as readily as it restarts a running one. Each changed agent now applies (`talaria-fleet-cascade`): a running one rolls at once, since the stripped tiers are start-time config, and a stopped one stays stopped and reads the render when it next starts, even when docker is too slow to answer the first inspect. The rolls run detached, so the save answers at once.
  - **A roll that runs out its time cleans up after itself, and the next roll recovers.** Compose recreates by creating the new container as `<old id>_<name>`, then stopping and removing the old one, then renaming the new one. A CLI killed in between leaves that container created and never started. Before this change, the next recreate of the service then failed on the name, after it had asked docker to stop (and remove) the running agent, and left one more stranded container. Now every `up` and stop-shaped verb first removes such a container (this fleet's compose project and service by label, never started, that exact name; one compose operation per service at a time). The removal is confirmed before compose runs, because a `docker rm` that ran out its time goes on in the daemon, and a `compose up` beside the half-removed container was seen to remove the agent's own container and create nothing, exiting 0. An `up` that reports success with no container is answered as a failure. **A control verb outlives its caller.** Every verb on the control route but `roll` runs whole on a task of its own (the render ahead of an `up`, the compose verb, which holds the service's lock inside that task, and the re-read after a failure), and so do the hire's `up`, a personal assistant's bring-up and restart, and the def and MCP edits' applies. A client that goes away, or the app proxy's own 300 s fetch limit, no longer kills compose halfway through a recreate or skips the verb altogether. The route answers with the verb's result when it settles within 210 s, and past that with 202 `{ok, pending, state}` and the container as it is so far. A failed `up` that was replacing a running container waits out a stop it may have started, then answers by what is there. If the old container still serves, the roll failed. If a new one runs, the render landed. If nothing runs, it starts the service on the current render.
  - **A failed control verb is answered by the container, not by compose.** `stop`, `restart`, `up`, `retire`, `unretire` and the hire's boot log compose's error (its stderr, or the timeout). They then re-read the container, and an agent that reached what was asked answers as the success it is. One that did not is answered by why compose failed: docker's own error (a host port already bound) with the container in the wrong state is the 500; a verb killed at its deadline, or a re-read docker will not answer, is a 503 that says the outcome is unconfirmed, because the daemon may still be carrying it out. A retire whose remove ran out its time after the stop issues the remove for the stopped container it left, and waits out a slow one.
  - `TALARIA_FLEET_COMPOSE_TIMEOUT_SECS` replaces every agent compose verb's deadline: longer for a slow disk, or tiny to drive the timeout paths on purpose.
  - **Also in this change:**
    - Every rendered config.yaml stamps `_config_version: 51`, the pinned image's own schema version (`HERMES_CONFIG_VERSION`, paired with the pin by a test). Hermes no longer reads the file as unversioned on every boot.
    - The agent control route logs compose's real stderr before its fixed 500 sentence. The personal-assistant bring-ups log theirs too, where they had dropped it.
    - The inert `connections` toolset leaves the governed vocabulary. The render pins Nous connectors off, so the switch did nothing. A stored list that names it still validates and expands to nothing.
    - The last writes to the retired `fleet_agents` table are gone. The table itself drops one release later, per the expand-contract rule.
    - The blue/green wording left in the UI, the user docs and comments is swept, and so is the copy that still promised a roll: the toolset grid, the delegation-cap tip, the MCP tab's progress line, the org toolset floor, the remove-server dialog, `docs/MCP.md` and the user docs now say a change reaches the running agent in place.
    - `docs/ARCHITECTURE.md` records the decision not to adopt Hermes's `HERMES_MANAGED_DIR` managed scope.
    - The render's file writes (`write_atomic`, the per-agent `secrets.env`) run whole on the blocking pool, the final close included. A tokio `File` dropped on the async side closed its descriptor on a runtime worker.
    - The unused `fleet/mcp-roll` waiting site is gone.
