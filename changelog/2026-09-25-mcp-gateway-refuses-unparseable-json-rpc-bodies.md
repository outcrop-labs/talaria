- **The MCP gateway answers a brace-led body that isn't valid JSON with a JSON-RPC -32700 instead of forwarding it verbatim.** The raw pass-through carried a malformed `tools/call` around the tool gate and the spend boundary — a body that never parsed upstream never hit either. A body that starts with `{` but fails to parse is now answered at the gateway with a -32700 parse error over HTTP 200 (the tool gate's own answer shape), carrying serde's wording, the whole-body byte offset, a caller-side hint (nested tool arguments need one `\` escape per JSON layer — the fix is on the sender's serialization), and a bounded diagnostic: a hexdump of the 8 bytes before through the 8 after the failing byte, hex pairs plus a printable-ASCII rendering, and nothing else from the body (bodies carry tool arguments). The same bounded diagnostic lands in a warn log server-side with the body size, so an operator can see which side mangled the payload. Every other unparseable shape — empty body, SSE framing, a `[`-led batch, a ping — keeps the pass-through untouched.

Verified: `bun run check`; `cargo test -p talaria-routes-fleet` with the seven new gateway tests: a raw 0x0a inside a string → -32700 with `0a` in the dump window; `{{{` → offset 2; an empty body forwards unanswered; a valid tools/call still reaches the tool gate (-32602, id preserved); the Sep 24 TALA-82 signature (markdown ticket body with raw newlines in nested arguments) → -32700 + the sender-side hint; a unicode payload (café/中文/🦀) renders only as hex pairs and dots, no text echo; a 12 KB payload gets a sub-450-char answer and the EOF offset clamps to the body's end; a line-2 failure walks to the right whole-body offset.
