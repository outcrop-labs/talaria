- **Fixed:** A Developer Agent's coding harness no longer fails to start with `env: 'bun': No such file or directory`. Oh My Pi is a bun program (`#!/usr/bin/env bun`), the agent image ships no bun, and the only step that installed one was `prepare_env` after a clone — which also reached the PATH only through a login shell's profile. So a fresh agent's `doctor`, and any command its terminal ran as a plain `bash -c` (Hermes's default), found no bun at all, and agents correctly refused to start jobs. The workbench now provisions the harness's runtime itself, idempotently and as the agent's user, before `doctor`, `start_job` or `prepare_env` hands the harness out: mise onto the volume if it is missing, bun `1.4.0` pinned and installed, and `bun` linked into `/opt/data/.local/bin`, which the container's own `PATH` carries. The doctor reports the runtime and probes the harness from a non-login shell; the boot hook also links an already-installed bun, so a rolled container has it before its first call. Verified: the bootstrap run in a throwaway `nousresearch/hermes-agent:latest` container on an empty volume — before, a non-login shell had no `bun`; after, `bun --version` answers `1.4.0`, a rerun is a no-op, and the harness probe `npx -y @oh-my-pi/pi-coding-agent@latest --version` answers `omp/18.8.3` from a non-login shell; the failure itself reproduced read-only in the live engineering agent's container (`sh -c 'command -v bun'` → nothing; `bun` there is an unpinned mise shim). `cargo clippy --tests -D warnings` and `cargo test` for `talaria-workbench-harnesses`, `talaria-workbench-mcp`, `talaria-fleet-render`.
