- **Added: when an MCP server a Developer Agent uses asks to confirm an action (for example "Delete record 42?"), the request becomes a card for the person whose chat it is, and the allowed action lands. Hermes' other human-only gates (an untrusted MCP server's write tool or spend limit, a saved card fill) would be carded by the same seam, but Talaria configures none of them today, so they do not come up. A protected-instruction write is never carded: it is refused at once and the agent is told why. Nor is an MCP server's request for fields to be filled in (a reason, an amount): a card can only allow or deny, so it is declined at once and the agent is told why. A reattached run's approval request now reaches the tap. In Comms, a conversation link you cannot open (it was deleted, or you are not in it) now says "Conversation not found" instead of opening an empty thread.** Every agent's file-tool write root is now rendered (`HERMES_WRITE_SAFE_ROOT=/opt/data`, the agent's data volume), with `HERMES_HOME` pinned to the same folder, and Hermes exempts that folder from its protected-instruction gate, so the gate only ever asks about a write the root refuses whatever the answer. The door recognises that gate by Hermes' own words, answers `deny` without offering it to a card, writes `reason: outside_write_root` on the `agent.approval_denied` row, and then steers the run with the real reason, because Hermes' own BLOCKED text says the user denied it. The note quotes the file Hermes named in backticks, on one line, with no control or invisible characters, and at most 120 characters. An open card holds only its own conversation; the agent's other conversations carry on. A failed answer to the agent no longer writes the agent's dial URL into the audit row. In Comms, a plan or work session opened as `/comms/agent/<model>/<thread>` (your own, or one you are a member of) is restored when you come back through the nav rail, instead of a fresh thread: a thread outside your chat list is put to the server, which decides who may read it. Before this, the fleet chat door answered every Hermes `approval.request` `deny`. That left the gates Hermes never auto-approves (an MCP server's confirmation request and a write to a project's AGENTS.md / CLAUDE.md / SOUL.md, plus, where they are configured, an untrusted MCP server's write tool and a saved card fill) unreachable on any streamed turn. Now, on an *attended* conversation turn (sent from `/api/chat`, or chained or resumed from one: the new `TurnAttribution::attended`), the door first offers the request to a card seam (`RAISE_CARD`, wired to the new `talaria-approval-cards` crate). A card is raised only for a Developer Agent, and only when the conversation's owner manages that agent (a named manager, its personal owner, or an admin). Every other request is refused at once, as before: an ordinary agent's, a non-manager's, or one on a channel, ticket, research, app, workbench or harness turn. The card is a `chat_approvals` row of kind `hermes_approval` and an `approval` chip on the turn's message. Only the owner sees **Allow once** / **Deny**, with a countdown; anyone else in the thread sees it read-only. The answer goes through `POST /api/chat/chips/approvals/{id}`, which re-checks the rule and sends exactly `{request_id, execution_generation, choice}` with `once` or `deny`, never `session` / `always`. A 409 or `already_resolved` from Hermes marks the card expired (the route answers 409). A Developer Agent now renders `approvals.timeout: 120`; everyone else stays at 60. The card closes itself at 115 s, answers `deny` and reads expired, and a boot sweep re-arms or closes the cards a restart left open. A person's answer is audited as `agent.approval_allowed` / `agent.approval_denied` with that person as the actor; an expired card is `agent.approval_denied` by `talaria`; an answer that reached an agent no longer waiting took nothing and is `agent.approval_expired` by the person, never an allow. Cards stay out of the approvals census. Separately, `reattach_session_run` now raises the parked run's `pending_controls` approvals as `approval.request` frames, once each, through the same tap. A run parked on an approval after its stream dropped is refused (or carded) within a poll instead of waiting out Hermes' timeout with the session's FIFO held. The projection does not say when a prompt was asked, so each rebuilt frame carries the earliest moment it can have been (the lost stream's last bytes, or the poll before), and a card raised from one counts its 115 s from then; one with under 10 s left is refused instead.
