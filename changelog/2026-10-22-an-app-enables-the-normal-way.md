- **Fixed:** An app scaffolded with `talaria app new` can be enabled from Manage → Apps again, in dev and in production, without anyone editing its build status or `app_settings` by hand. Five bugs stood in the way. (1) The app client build left Vite's `preserveEntrySignatures` at its default, so the built `app.js` had no default export. The production probe refused it ("app.js is not an ESM client bundle") and the host had no surfaces to mount. The build now keeps the entry's exports, and the probe asks for a default export rather than any `export`. (2) The built bundle imported `svelte/internal/client`, which every compiled component uses, from `/runtime/rt-svelte.js`, because the import mapping took the first shared specifier that was a prefix. That file has no `from_html`, so the app failed in the browser. Each shared specifier now maps to its own runtime file (`clientRuntimePath`), and an import of an unshared subpath such as `@lucide/svelte/icons/check` fails the build with a message that names it, instead of shipping a bundle the browser cannot link. (3) In dev the build probe loads `app.ts` in Node, and `@talaria/sdk` reached the router (ViewHeader → `lib/view-title`, and Markdown → AgentMediaImage → SaveDialog). sv-router reads `location` when it loads, so every dev rebuild failed with "location is not defined" and disabled the app. `lib/view-title` now gets the router's pathname from `router.ts` instead of importing it, and AgentMediaImage loads SaveDialog when it is first opened. (4) A fresh app's first database call failed with ENOENT because `db.env` was written before `app-data/<slug>/` existed. The directory is now created first, with mode 0700. (5) Two container-naming problems. `talaria dev` now passes `TALARIA_WORKTREE` to the Rust api, so in a worktree the api and the app side name the same app database container (`talaria-appdb-<worktree>-<slug>`) and uninstall stops the right one. Separately, a checkout install (`server-entry.ts` on the host) no longer counts as the product image, so it reaches the app database on the published loopback port rather than by a container name the host cannot resolve; only `TALARIA_INSTALL=image` means the image. A host outside the image that sets `TALARIA_APP_DB_NETWORK` dials the app database by container name too, because on that network the database publishes no port. An app built before this change is rebuilt, not reused. The build cache key now includes a build-recipe version (`BUILD_RECIPE` in `ui/src/server/app-build/key.ts`), which is bumped whenever `build.ts` changes what a build emits. Before, dev and checkout installs (no `TALARIA_VERSION`) kept the same key across the recipe change, reused the broken build still marked ready, and the first production probe turned the app off. Verified: `bun run gate` (svelte-check 0 errors; vitest 1894 passed; cli `tsc` and `bun test` 258 passed), including new tests. A real Vite build of a small app checks that `app.js` keeps `export{… as default}` and imports only host runtime files, `rt-svelte-internal-client.js` among them. A build with a deep `@lucide/svelte/icons/check` import fails and names it. Components compiled in runes mode and legacy mode, and a runes module, have every `$.<name>` and named import checked against the exports of the runtime file its import maps to. These tests fail under the old prefix mapping, and the build test fails without `preserveEntrySignatures`. A walk of the SDK's load-time import graph finds no route to the router or sv-router; before the change it printed both chains. Other new tests cover `writeDbEnv` creating a fresh directory (0700) and a 0600 `db.env`, `inImage`, and `apiEnv` lifting `TALARIA_WORKTREE` from ui/.env with the shell winning.
