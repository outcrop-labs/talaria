- **Fixed:** An agent's tool-event frames (the talaria-events plugin's `POST /api/agents/tool-events`) were attributed to the agent's NEWEST live work session, so with two sessions on one agent — or a session and a chat — the thrash brake could abort the wrong run and the two transcripts mixed (audit 05-F13.3, left open in #559). A work-session turn is now sent as a Hermes SESSION turn keyed by its run id (`session_for_turn` → the harness transport's `PersonaSession`, through `proxy_session_turn`): created on turn 1, resumed on every later turn of the same run, and a session the container has lost falls back to the full-prompt completion for that turn the way a pinned chat does. The plugin's `sessionId` is therefore the run id, and the tool-events door resolves it exactly through `live_work_session_for` — a chat conversation's id lands nowhere — falling back to the newest-session read only for a frame that names no minted key. The workbench MCP `wtool` line, where no plugin reports and no session id arrives, is keyed by the ticket the call names (`taskId`, or a `jobId`'s ticket) and takes the newest session only when the call names none. The liveness tap and the `run-watch:{run}` thrash watcher read the same channel as before; the retire-on-reclaim and interrupted-turn settle logic is untouched. A session turn refuses by name any request field its body cannot carry (`temperature`, `response_format`, `tools: none`) rather than dropping it. Verified: `cargo fmt`, `cargo clippy --tests -- -D warnings` and `cargo test` for `talaria-harness`, `talaria-runs-work-session`, `talaria-routes-fleet`, `talaria-workbench-mcp` and `talaria-gateway`, with new tests for the session-keyed turn (`a_turn_keys_the_persona_session_by_its_run_and_resumes_after_the_first`), the non-key short-circuit, the frame's named-session read and the session-arm request mapping; `bun run check`. Not exercised against a live Hermes.
