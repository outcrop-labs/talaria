- **Fixed:** Two worktree stacks running agents at once no longer collide. Every stack used to hand its first agent gateway port `8770` (each allocates from its own database, and every database starts with none), so the second stack's hire failed with `port is already allocated`. Every stack's api also spawned its toolkit MCP on `:5280` and its omp auth bridge on `:5276`. Both probe their port first and adopt whatever answers, so the second stack's agents had their tool calls served by the first stack's toolkit, which refused their keys (`401` from `/api/mcp/gw/talaria`). Now `talaria worktree` gives each slot its own toolkit port (`57xx`), omp auth port (`58xx`) and a hundred agent gateway ports from `20000 + slot·100`, written to the worktree's `ui/.env` as `TALARIA_MCP_PORT`, `TALARIA_OMP_AUTH_PORT` and `TALARIA_GATEWAY_PORT_BASE` and lifted into the api by `talaria dev`. A slot is free only when all of those are. The api allocates agent gateway ports from `TALARIA_GATEWAY_PORT_BASE` (default unchanged at `8770`), still continuing past the highest port ever assigned. The worktree seed clears the gateway ports copied from main's agents, so a worktree never publishes onto main's live fleet. Separately, the built-in Talaria toolkit row in `mcp_servers` now has its url rewritten on every boot: it was insert-only, so a seeded database, or any install whose `TALARIA_MCP_PORT` changed, kept pointing the MCP gateway at a stale toolkit port. Devboxes do not share the problem (their agents are dialled by container name and their api's children bind inside the box), so they are unchanged.
