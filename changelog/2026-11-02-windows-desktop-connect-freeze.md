- **Fixed: Talaria Desktop on Windows no longer freezes for good the first time you connect an instance. Windows users on desktop v0.11.0 must download and run the new installer by hand: the frozen launcher cannot reach Check for updates. The installer (NSIS, `Talaria_<version>_x64-setup.exe`) installs over the old copy and keeps your instances, sign-ins and settings.** Opening an instance created its WebView2 inside the launcher's own WebView2 IPC callback (`activate_instance` was a sync command), and WebView2 cannot finish creating a webview while one of its handlers is on the stack: the window kept repainting, but the Add dialog stayed at "Checking…" and no button, titlebar control or close answered again. The instance was already saved, so every relaunch reopened it and froze at once; the in-app switcher and a suspended instance coming back did the same. Now every path that makes an instance webview runs as a main-thread task of its own (the launcher, the switcher, a restore when the window comes back, a notification click, a tray row, the launch-time preload), and a second open of an instance still being created changes nothing. Also: the shell writes a log file — `%LOCALAPPDATA%\app.talaria.desktop\logs\talaria-desktop.log` on Windows, `~/Library/Logs/app.talaria.desktop/` on macOS, `~/.local/share/app.talaria.desktop/logs/` on Linux — rotated at about 1 MB, so a problem report can carry evidence; and HTML5 drag and drop works inside instances on Windows (boards, the Gantt, dropping a file on a composer), because the instance webviews no longer install Tauri's file-drop handler. CI now runs clippy and the tests on Windows and a Windows connect smoke on every desktop pull request, and `bun run check` fails any shell command that could create a webview inline.
