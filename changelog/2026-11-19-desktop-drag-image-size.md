- **Talaria Desktop on Linux: a drag's ghost is the web size again on a display scaled above 100%.** WebKitGTK snapshots a dragged element at the device scale and hands GTK the bitmap without saying so, so at 200% (and at GNOME's fractional scales, which GTK3 renders at 2) every ghost was twice the size a browser shows, with the cursor nearer its corner than the point grabbed. That covered ticket cards, list rows, Files rows, conversations and selections. The shell now stands in front of GTK's `gtk_drag_set_icon_surface`. It gives WebKit's image the web view's scale (read from the dragged widget, so it follows the monitor the window is on; the drag's own source window is a hidden popup whose scale on Wayland is the first monitor's) and scales the grab offset with it, then calls GTK's own function, so the ghost is drawn pixel for pixel at the CSS size under the point grabbed. Drag data and drops are unchanged. A window at 100%, and an image that already carries a scale (an upstream WebKitGTK fix), are left alone. The first fitted drag logs one line with the scale, where it was read, and the WebKitGTK version. Windows and macOS code is untouched: by code reading WebView2 and WKWebView already draw the web size, but no one has checked either on a scaled display for this change. One known cost on a scaled Linux display: a page that calls `setDragImage` with an `<img>` (ui/ never does; an app or an agent's HTML artifact might) now shows that image at 1/scale, because WebKitGTK passes it at its natural pixels (docs/DESKTOP.md, "Drag images on a HiDPI Linux display").
  Verified: CI (this PR's checks). The desktop job's unit tests build WebKit's surface in cairo and replay GTK 3.24's extents read: a 400×120 px image grabbed at (30, 10) on a scale-2 window reads as 200×60 logical px with the hotspot still at (30, 10). They also check that the call goes on into libgtk-3. A new step, `check-drag-icon-shim.sh`, shows that the built binary defines the symbol (readelf) and that libwebkit2gtk-4.1 binds its call to the binary (`LD_DEBUG=bindings`, no display). The connect smoke at `GDK_SCALE=2` with `--drag-icon` drags a 240×120 CSS px box with XTest under xvfb, measures GDK's drag window, and requires the shell's line to say the scale was read from the dragged widget (X11 gives every window one scale, so the size alone cannot show that); the plain connect smoke's page is unchanged. Run on the smoke's own commit, without the shim, the export check failed and the smoke measured 960×480 device px: 2.00× the web size, the bug. `desktop-package.yml` runs the same check on the binary the deb installs. Locally: the check script against a probe binary linked with the host's libwebkit2gtk-4.1 2.52.5 (bound to the executable's definition, and failing on a binary without one), a mocked run of the smoke's measuring code, rustfmt and `bun run check`; no Rust was compiled. Not yet run on a real scaled Linux desktop, and Wayland with monitors at different scales has no CI: that is on the owner's checklist in docs/DESKTOP.md.
