- **Fixed:** Adding or removing an agent on a team, adding or removing a person, and deleting a team never re-rendered or rolled anyone, though a team's MCP grants ride on `team_agents` and a personal assistant's rendered server set follows its owner's team access — the running container kept the old server set, and the on-disk config kept advertising a server the gateway would refuse. The team routes now render and roll the way `me/mcp` does: the named agents on a `team_agents` write (captured before a team delete, rolled after it), the person's assistant on a `team_members` write. At render, the `mcp_servers` block is BUILT rather than merged: an authored entry whose name is neither `talaria` nor a registry server was a raw endpoint from pre-gateway history that survived every render with its own URL and headers; it is dropped now and the render warning says which. Also: the preflight probe image is pinned (`busybox:1.37`, not `latest`), every `docker` child in `talaria-fleet-docker` and `talaria-fleet-preflight` is `kill_on_drop`, so a timed-out `compose up`, `exec` or probe dies with the future that was waiting on it instead of orphaning on a wedged daemon; the browser setup runs `docker exec -u hermes` (the runtime user that owns the volume it writes to) and the marker file records the installed version instead of an empty touch. `talaria-agent-crons` gains `remove_jobs_for_conversation` for the conversation delete/archive path to call before the rows cascade — the job in the agent's `jobs.json` otherwise fires forever with nobody listening. Verified: `cargo test -p talaria-fleet-docker -p talaria-fleet-preflight -p talaria-fleet-render`, `cargo clippy -p talaria-routes-integrations -- -D warnings`.
