- **A work session's step snapshot survives a `git gc` the agent runs at the same moment.** Two races with a concurrent `git gc` are closed. First, gc removes a loose-object directory (`.git/objects/xx/`) the moment it is empty, so one could vanish between the snapshot making it and moving a new object into it. The move then failed, the step was recorded as "snapshot failed: the checkout's object store could not be written", and there was no checkpoint to rewind to. The talaria-events plugin now makes the directory again and retries the move, up to five times, as git's own loose-object writer does. Second, a gc that had read the refs before the snapshot's ref existed could delete the snapshot's objects after the snapshot had reported its commit. That gc deletes every loose object no newer than its expiry, and a moved object kept the date git first wrote it with. Adopted objects are now dated two seconds ahead, past the expiry of any gc already running, the way git freshens an object it would write again. An object the store already had is replaced by the snapshot's freshly dated copy instead of being left with its old date. A gc that starts after the ref is written reads it; git stops a prune at a ref whose objects are not all in yet rather than delete anything.
  Verified: the plugin's self-test (`python3 -I snapshot_test.py __init__.py`, which `talaria-fleet-render`'s `the_events_plugin_snapshot_test_passes` runs) gains three cases. In the first, the directory vanishes before the first two moves: the snapshot lands and its commit is in the store. In the second, the directory never stops vanishing: the snapshot fails after five moves with the reason above and leaves no ref. In the third, a `git prune` with its expiry at the snapshot's own second runs while the snapshot's ref is hidden, as a gc that read the refs first would: every object of the commit survives. The same plugin without the dating loses the commit ("bad object"). Run against `testing`'s plugin, the vanishing-directory case fails with exactly CI's reason. On git 2.55: an object dated at the expiry is pruned and one dated two seconds later is kept; a prune with a ref to a missing commit, or to a commit whose tree is missing, exits 128 and deletes nothing. The whole self-test locally: 5 failures in 120 runs before the fix, each a `FileNotFoundError` on the move into the store (captured by an instrumented copy), and 0 in 150 after it. This PR's first CI run, with the retry alone, hit the second race ("… lost beside a running gc"). `bun run check` passes. CI: this PR's checks.
