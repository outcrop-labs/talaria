- **Fixed:** **An app's API and compiled client now admit only people granted the app, each app surface is its own grant, and the gate fails closed.** Before, `/api/apps/<slug>/*` checked only the work view `/x/<slug>`, so any member could call a manage-only or settings-only app, and a member granted only the work view could call the routes behind the app's Manage surface. A grant for only an app's Manage surface did nothing: the route gate, the nav and the gateway all denied it as a child of the denied work view. `/app-builds/*` served every build file with no session at all, including the compiled `server.js` and `mcp.js` and the `current.json` that names the build key. Now:
  - `GET /api/auth/session` serves `appGrants`, the app views the person holds (person and team grants together, from `talaria_users::view_grants`). The app gateway, the `/app-builds/` door, the nav, the manage sidebar, the route gate and the settings tabs open an app view only when that list names it, never because a view is missing from `deniedViews`. An admin holds every app by role and gets an empty list.
  - When the Rust api cannot read the enabled apps (a malformed `apps_enabled` setting, or an apps directory it cannot list), a member's session still answers 200 with their core `deniedViews` and `perms`, and serves `appGrants: null` with `appsUnreadable: true` instead of leaving the app views out. Every app reader treats that as no app at all: the nav, the route gate and the settings tabs show no app, and both app doors answer 503. The rest of Talaria stays open, and Rust's `require_view` still answers for core views such as `/teams` and `/observability`. The TypeScript host reads `apps_enabled` by the same rule and answers 503 too. An admin's session skips that read, so Admin → Apps stays reachable, and toggling an app there rewrites the setting. The TS session reader throws, and the gate answers 503, when `deniedViews`, `appGrants` or `perms` is missing or is not a list of strings, unless `appsUnreadable` is true. A `talaria.json` that isn't valid UTF-8 is not an app on either host.
  - The gateway passes the app `ctx.access { admin, work, manage, settings }`, `ctx.perms` and `ctx.can(perm)`. A settings tab follows the manage grant, and an app that ships settings without a manage surface has `/x/<slug>/manage` to grant. Admin → People and Manage → Teams name each app view for the app and what it opens, for example "CRM · work" and "CRM · settings". Teams can grant app views. A person's or a team's manage-view list takes up to 200 views of up to 80 characters.
  - `/app-builds/` serves only `app.js`, `app.css` and `assets/**`, behind the same gate, as `private` cache, and only under the key the app's current, ready build pointer names. An older key answers 404, because builds made before this change keep their server and MCP chunks under `assets/`. The server and MCP builds now write their split chunks to `_server/` and `_mcp/`, outside what the door serves. A successful build removes the app's superseded key directories.
  - One fixture, `api/tests/it/fixtures/app-grants.json`, pins the TypeScript grant rule to the Rust one, and both test suites read it.
