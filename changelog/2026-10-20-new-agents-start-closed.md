- **A new agent starts closed: no shell, no code execution, no file tool, no self-scheduling, and no cross-conversation recall on a shared agent — until a manager opens each one.** Every Hermes toolset used to be on for every hire and Talaria forced Hermes' approval gates to `approve`, so a default agent could run `env` and `curl` on a prompt-injected page with no confirmation step anywhere in the chain. `talaria-agent-defs` now carries `DEFAULT_DISABLED_FOR_NEW` (`terminal`, `code_execution`, `file`, `cronjob`), written into `disabled_toolsets` on INSERT only (an existing slug keeps what its managers opened; `browser`, `delegation`, `memory` stay on), plus `session_search` for an agent that is nobody's personal assistant (`SHARED_AGENT_DISABLED` — the personal create path opens it once the owner is marked). The Developer Agent switch opens `terminal`/`file`/`code_execution` when turned on and closes them when turned off (`apply_developer_toolsets`, on a change only). The rendered `approvals` block follows the same switch: a Developer Agent keeps `unattended_mode`/`cron_mode: approve`; every other agent renders `deny`, which refuses `execute_code` and a dangerous terminal command outright instead of waving them through — file, browser, web, memory and MCP calls are not approval-gated and are untouched. An org-level floor joins the mandatory pair: the `app_settings` key `agents.mandatory_disabled_toolsets` (a JSON array of governed names, set with SQL for now — no admin route writes it yet) and/or the env `TALARIA_MANDATORY_DISABLED_TOOLSETS` (comma-separated), merged ahead of every agent's own list by the renderer; strangers are logged and dropped. The toolset editor still shows the per-agent list; the org floor is not yet painted there.
