- **Added:** An app's code can now run with nobody calling it, and drive a fleet agent. The `triggers` an app declares in `talaria.json` run: a `cron` schedule (five fields or `@daily` and friends, read in UTC) fires the handler its `server.ts` names in `defineAppServer({ triggers })` within 30 seconds of its minute, through the api's one scheduler (`app-triggers` job, leased), and an `event` trigger fires on `ticket.created` or `ticket.moved`, the two changes the tasks engine already announces, with a payload of ids and column keys only. A triggered run acts as the app with no user: its context has the store, the secrets an admin gave the app and the cause, no `ctx.user`, no `ctx.api`, and it may not drive an agent. Every run is recorded (`app_trigger_runs`: queued, running, ok, failed or skipped, with the handler's own line or the error) and shown on the app's row in Manage → Apps; a failing trigger never turns the app off. Only an enabled app with a ready build fires; disabling an app or a failed build disarms its schedules, and turning it back on re-arms them rather than catching up. Install now refuses a schedule that does not parse, an event the platform does not emit and a reused trigger id, with the reason. Separately, `ctx.agents.turn({ agent, message, session?, watch? })` on the request and MCP tool contexts sends one turn to a fleet agent through the fleet's own chat door (`POST /api/internal/apps/agent-turn`), on a Hermes session the app keys (the agent keeps the transcript; Talaria stores none) or fresh, streaming the agent's words and tool calls to `watch` and resolving with the reply. The api decides who may drive whom from what the host authenticated: from a request only an agent that person may use, from an MCP tool only the proven calling agent, from a trigger none. The turn's spend is booked to the agent under ledger source `app`.
