- **Fixed:** Agent crons are driven through Hermes's own cron REST (`/api/jobs` on the agent's API server, the chat door and bearer) instead of `docker exec hermes cron` and a `jobs.json` read, so "Run now" stops reporting false failures and the admin frequency floor can no longer be slipped past. Since Hermes v0.22 the CLI's `run` executes the whole turn on the caller's thread, so any run longer than the exec's 30s bound came back as an error while the run carried on; REST `run` marks the job due for the next tick (≤60s) and answers at once. The floor used to read the schedule with a grammar of its own and allow anything it could not parse, which let `every minute` (Hermes's bare-unit interval), croniter's `0/1` and any 6-field cron through. Now a job is written paused, the floor judges the schedule Hermes parsed, and only then does the job start; any shape it cannot read is refused. A schedule edit pauses an armed job, patches it, judges it and resumes it, and a refused edit puts every changed field back. An edit that sends the schedule back unchanged (the edit form always does) no longer re-parses or re-times it. The floor also reads the hour field now, so a floor above an hour stops refusing a daily cron. "Run now" on a paused job is refused, because Hermes's `run` would resume it for good (an archived thread's schedules are paused so they stop spending), and the Run button is disabled on paused rows. Prompts are capped at 5,000 characters, Hermes's own REST limit, at every cron door and in the forms. The list asks for `include_disabled=true`, so paused jobs still show. `talaria-gateway` gains `fleet_chat::agent_request`, one json call on an agent's own door, and `talaria-agent-crons` no longer depends on the docker socket. Verified: `bun run gate` (check, ui typecheck and 1880 ui tests, clippy and `cargo test` for `talaria-agent-crons`, `talaria-gateway`, `talaria-routes-fleet` and `talaria-routes-comms`; the crons crate's new tests cover every schedule shape Hermes stores, the `N/STEP` and 6-field cases, the hour-aware gap, the refusal sentences and the job-id grammar); the workspace compile and test is CI's. End to end in the worktree stack on a `nousresearch/hermes-agent:v0.22.4@sha256:7a6920…` agent, a scripted run of 35 checks, all passing, each one read back from Hermes's own `/api/jobs`. `every minute`, `minute`, `0/1 * * * *`, `* * * * * *`, `*/2 * * * *`, `every 0m` and `every 4m` were refused with nothing left behind in Hermes. Create, both lists, edit, a refused edit restored with the job still armed, an unchanged-schedule rename that kept `next_run_at`, pause, resume, delete and a malformed id all behaved as described. Run-now answered in 49 ms and the scheduler claimed the job on its next tick 44 s later. Run-now on a paused job was refused and the job stayed paused. The conversation door was checked too: a refused schedule, a create, the merged live list, archive pausing, restore resuming and unschedule. With a 120-minute floor an hourly cron was refused and a daily one passed; with the floor at 0 a 1-minute job was accepted and edited. A stopped container came back as the per-agent error on the fleet list.
