- **The branch guards know `testing` again — as the integration lane — and a pull request can no longer reach rc on checks run against another base.** `scripts/flow-guard.mjs` stops refusing `testing`. A pull request into it passes, and a push to it must be a merge commit or a fast-forward to content rc or main already has. Deleting or rewriting it is refused, as for rc and main. `flow.yml` now checks pull requests into main, rc and testing. It refuses a title or body carrying `[skip ci]` and its variants, or a `skip-checks: true` trailer, because the merge commit carries both and the branch would move with no push checks run. It also refuses a pull request retargeted into rc or main until a push re-runs its checks, since CI does not re-run on a base change. Into main, the head must be this repository's `rc`, not a fork's branch with that name. The check is now named `pr target (flow)`, and the push check `branch push (flow)`. The promotion gate and `promote.yml` count only CI and rc-deploy runs made on rc as evidence; a pull request's run, a testing push or an offload of the same commit no longer counts. `promote.yml` wakes only for a push or dispatch run in this repository, and arms auto-merge when main's rulesets or its classic protection require the gate. Its roll and promotion bodies quote changelog leads and rc's commit subjects, so it now turns any bracketed skip marker in them into parentheses: its own pull requests never trip the new refusal, and their merges never skip rc's or main's push runs. `ci.yml` runs on pushes to `testing` in integration mode. A new invariant keeps the names `CI` and `rc-deploy` to their own workflow files, so no other workflow can stand in as the evidence.
