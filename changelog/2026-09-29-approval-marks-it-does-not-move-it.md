- **Approving a ticket marks it signed off; it no longer forces it to done.** Both approval paths dragged the ticket into the board's first done column, which was routinely a lie: the review passed, but the merge had not landed, the release had not shipped, and there was no column that told the truth. Approval now stamps a new `tasks.approved_at` and **leaves the status exactly where it is**, so a person can carry the ticket through whatever a board models between review and done — merging, releasing, waiting on someone else — and moves it to done when it really is. The ticket's gate says so in place ("Approved 2h ago. Move it on when the work has actually landed."), the header carries an `Approved` chip beside the status, and the rail lists the sign-off time. Requesting changes still moves the ticket back to the board's first working column, and clears the sign-off, because the work is going back for more. A sign-off SURVIVES column moves — that is the whole point of it — and is retired only by the ticket re-entering review from outside review, which is a fresh round on work that has changed since (`approved_at_for`, three unit tests).

  Two consequences worth naming. **The review queues stop nagging.** Home's queue, the daily brief's focus items and the inbox focus cards all read a ticket in a review column as "needs a human", so an approved-but-not-yet-shipped ticket would have asked to be reviewed for a second time, for as long as it sat there; all three now carry `approved_at is null` in the review predicate. **The workchain engine now advances on the real landing**, not on the sign-off: approval leaves the ticket non-terminal, so the next step in a chain starts when a person actually moves it to done.

  Two bugs found in the same code and fixed with it. The ticket's gate tested `status === 'quality_review'` literally, so **a board that renamed or re-keyed its review column had a review stage the server would accept a sign-off for and no gate to offer it** — it now asks the board through a new `isReviewStatus`, mirroring the server's own review predicate. And `COMPLETE_QUALITY_REVIEW`, the seam the inbox/brief review card resolves its Approve and Request-changes clicks through, **was never registered**, so every click on a review card in the brief panicked on an unset `OnceLock` and came back as an opaque 500. It is registered now, beside the two `GET_TASK` edges whose comment already described this exact failure.

  Verified, against a real migrated database, by running the statements this code actually issues: a ticket in `quality_review` approved through `set_task_approved`'s exact UPDATE comes back **still in `quality_review`, with `completed_at` still null and `approved_at` stamped** — which is the whole point of the change; the reject form of the same statement clears the mark; `complete_quality_review`'s CAS approve branch behaves identically; and the review-queue predicate returns 0 rows for that ticket while it is approved and 1 row once the sign-off is cleared. Also `cargo test -p talaria-tasks` 10 pass including the three new `approved_at_for` cases; `cargo check` clean across the touched crates; `bun run typecheck` 0 errors; 1304 ui tests pass; `bun run check` green; and the full 387-statement migration array replays from zero, with the schema snapshot showing exactly one added column. Migration is an additive `alter table tasks add column if not exists approved_at timestamptz`.
