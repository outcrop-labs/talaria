- **Fixed: Hermes sessions survive agent restarts.** A turn lost in a crash is repaired instead of wedging the session, a session that is gone is replayed instead of held, and a resumed turn the agent is still running is picked up instead of sent twice. This covers pinned conversations and every work session. Hermes v0.22 marks a turn that was running when its container died non-gracefully (an OOM, `docker kill`, a host crash) `unknown`. It then refuses every later turn on that session with `unknown_execution`, and leaves each refused turn queued. Talaria showed that refusal as the reply to the auto-resume and to every message after it, forever. The session arm now repairs it in place. It withdraws the refused turn (`POST /v1/runs/{id}/stop`), acknowledges the lost one with `hermes sessions discard <session> --yes` inside the agent's container, and sends the turn again. The discard is needed because `/v1/runs/{id}/resolve-unknown` answers 404 for a session turn once the container has restarted. Hermes' own boundary row ("This turn did not complete…") tells the agent the first attempt did not finish. Second, a session that has carried turns is now looked up rather than re-created. A deleted session (whose id Hermes refuses to reuse, `409 session_deleted`) used to hold every turn for two minutes and answer "restarting" while the agent was up. After a lost state volume, the next turn went into the empty session Talaria had just created and answered without the conversation. Both now replay the full history at once, on every later turn too. A work session starts its session again instead, since its steps carry no history. Third, the auto-resume asks `GET /v1/runs/{id}` before it re-sends. A v0.22 session turn keeps running when its stream drops, so a turn the agent still holds is followed to its end and its reply lands on the same row. Pinned sessions stay off by default: on a session a per-message tier runs the main model, and the session arm's usage frame (`input_tokens`/`output_tokens`) is not read, so its turns are ledgered as estimates. Verified: `bun run gate` (check, then clippy and tests for talaria-gateway, talaria-chat-persist, talaria-harness, talaria-conversations, talaria-fleet-docker and talaria-jobs), with new tests for the lost-turn watcher, the session answers, the run projection and the discard command. In this worktree's stack, on `nousresearch/hermes-agent:v0.22.4@sha256:7a6920…a4cf`, with a pinned agent on a scripted model behind the stack's gateway, the first three cases were reproduced on rc and then exercised after the fix. **Kill mid-turn** (`docker kill`, then start): on rc the resume and the next message both answered `(agent error: unknown_execution)`, and Hermes held three admissions (`unknown`, `queued`, `queued`). After the fix the resume withdrew the refused turn (`cancelled`), discarded the lost one (`interrupted`), and completed on a new run. The model saw the first attempt, Hermes' boundary, and the resent message, and the next message answered in 0.4 s with the whole history. **Deleted session:** on rc the next turn took 2 min 5 s and landed "Sessie is restarting (or down)…". After the fix it took 0.66 s and replayed the full history, and so did the turn after it. **Lost volume:** on rc the third turn answered from an empty session ("SEEN 1 user turns: volume hello three"). After the fix it replayed all three. **Frozen container** (`docker pause` until the 60 s idle ceiling fired, then unpause; not reproduced on rc, where the resume re-sends unconditionally, and a standalone v0.22.4 container finished a session turn after its client hung up): the resume reattached to the same run (`run_c5620840…`, one admission, one copy of the message in Hermes) and landed its reply, and the next turn saw each message once. The work-session paths (the shared repair, and restarting a lost session) are proven by compile and unit tests here; CI runs the full workspace.
