- **The GitHub permissions editor and the git host card now say what an agent's token actually carries, not only what the App's installation holds.** Before, every key in an agent's set showed as held whenever the installation had accepted it, and the host card's green "Installation accepted" chips listed workflows and actions. Neither surface read a minted token, so an agent could look authorized while every token it got lacked the key. In Fleet → agent → Workbench → GitHub permissions, each key now says one of four things. "On the agent's token (acme/widgets, 12 min ago)" means the last token minted for this set carries it, and the installation still holds it. "Granted; no token checked against this set yet" means the set changed since the last token, or the last token's row predates rows saying what was asked. "Not on the token (acme/widgets, 2 min ago): …" gives the reason: the installation has not accepted it (with the installation's page on GitHub), it accepted it only after that token was minted, GitHub refused it (GitHub's own words, told only to organization keys, since GitHub's refusal names no key), GitHub omitted it, or no token was minted (in the door's words). Otherwise the record answers. While nothing has been minted, that reads "The installation holds it; no token checked yet", and it is never green. When the installation does not hold a key (granted before an owner accepted it on GitHub, or never asked for by the App), the record's warning and the link to accept it stand whatever an older token said. Admins get a **Check token** button, with a repo picker when the agent has several repos. It asks for the token the agent's next push gets and says, in plain sentences, why any key is not on it. Keys the installation holds outside the agent's set are said once, in one neutral sentence, so a real gap stands out. A failed check shows the server's sentence verbatim, never a blank, and a check's answer goes away when the set is saved. When a workspace secret answers git ahead of the App, the editor says "Git at GitHub answers from the workspace secret <name> for this agent; these permissions don't apply to it." On the host card (Admin → Git hosts → GitHub), "Installation accepted" now reads "Installation accepted (the most any token can carry)". A new "Agents' tokens" list shows each agent with its default chip or custom set, what its tokens can carry, and its last token. An agent whose Developer switch is off, or that is disabled, reads "no git credential" and claims to carry nothing. A failed read of the list says so instead of drawing nothing. When the installation accepted keys that no agent's set names, the card says so: "Accepted by the installation, carried by no agent: actions, workflows. An admin grants them per agent (Fleet → agent → Workbench → GitHub permissions)." Nothing here grants or gates anything: grants stay admin-only and per agent per host. Every new field is optional, so against an api without them, both surfaces draw what they drew before (apart from the caption).
