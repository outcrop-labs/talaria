- **New: an app harness can declare a tool loop the runner holds, `loop: { tools, maxTurns? }`, and the fitness sweep dry-runs it when every tool has a `simulate`.** Each tool is a `ToolDefinition` plus exactly one road: `handler(args, ctx)` (the app's code), `mcp: '<tool>'` (the app's own MCP tool, through the same dispatch an agent's call takes) or `org: '<server>/<tool>'` (an org MCP tool, through the MCP gateway as the agent that called the app, presenting that agent's own key, so its grants, its owner's allowance and the call record apply; a request or a trigger has no agent, and the model is told so). The loop lives in the TS runner, because the tools are app code, and keeps the rules of research's tool-search loop and the fitness dry run: at most three calls a turn, a last turn's calls still dispatched, failures and unknown tools answered as tool results, calls on the tool channel, a closing turn with the tools taken away when the turns run out, a repair turn that continues the conversation. Results gain `toolCalls`, `calls` (the `EvalContext.calls` shape) and `exhausted`, and the guard is grounded in what the tools returned. Every field is optional: a harness with no loop runs exactly as before, `toolDefs` still only offers, and a loop does not stream. The app host checks a loop at load (one road per tool, real names, no clash with `toolDefs`, `maxTurns` 1–12) and lists each tool's road and `simulate` on the wire; the sweep sends a loop harness's fixtures to the host only when every tool simulates and the candidate takes tool definitions, the host replays with every tool answered by `simulate`, and the case keeps the calls. A loop with an unsimulated tool keeps #595's skip, naming the tools. `runHarnessOffline` scripts tool calls and runs handlers for real (or everything through `simulate`). Verified: `bun run gate`; the new `loop.test.ts` (dispatch and the tool channel, three calls a turn, an unknown tool, a failing tool, exhaustion and the closing turn, repair, mcp and org roads with and without a host, a dry run touching nothing real, grounding firing on an uncited link and not on a returned one, no streaming, no loop fields on a plain run); load checks, the wire and a simulated replay in `app-harnesses.test.ts`; the runner's per-context roads; Rust tests for the loop on the wire, `app_loop_skip_reason`, and a sweep that dry-runs the simulating harness through the host and skips the other. Live on a worktree stack with a mock gateway model and a mock org MCP server: a member's request ran a handler and the app's own MCP tool (which saw the harness run as its caller and the member as the person acted for); the org tool from a request answered the model that it needs an agent; an agent calling the app's MCP tool on its own key ran the org tool through the Rust gateway, recorded in `mcp_tool_calls` as that agent, and narrowing the agent's tool subset turned the same call into the gateway's refusal; `stream` refused the loop; an evals sweep scored the simulating harness through `simulate` (pass, its calls kept) and skipped the org one naming `search_docs`.
