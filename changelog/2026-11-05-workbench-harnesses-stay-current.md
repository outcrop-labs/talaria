- **New: every workbench harness stays current on its own. Oh My Pi and the harness's own bun now follow their upstream releases on every instance, the way the agent image follows Hermes stable.** #706 pinned Oh My Pi (`OMP_VERSION` 18.16.0) after its 28 Oct release raised its bun floor above the harness's bun and broke every `npx …@latest` job. That pin is now the bootstrap fallback, not a ceiling. A scheduled channel (`talaria-workbench-updates`, a step a minute) checks npm's version document for `@oh-my-pi/pi-coding-agent` and bun's GitHub releases every ~6 h. Each release soaks 24 h from the first check that saw it (`TALARIA_HARNESS_MIN_AGE_HOURS`). The channel checks the candidate's `engines.bun` against the harness's bun. When a candidate needs a newer bun, the bun moves first, smoke-tested with the Oh My Pi jobs already run, and Oh My Pi follows on the next step. A bun pinned under the running Oh My Pi's floor waits and says why. A candidate is installed beside what a workbench runs, using #706's versioned dir, atomic symlink swap and `.retired` prune. It is then started, and the provisioning preflight runs through a job-shaped launcher (no model call). Only after that is it what new jobs run, and the pair before it is kept as the fallback. A job never resolves a version itself: provisioning installs what the channel verified, else the bootstrap. A running job keeps the install it started on until it ends, because a ready job is no longer re-provisioned onto a newer release and the prune now keeps any install a job's launcher names. A release that will not install, start or pass the preflight is held, and every admin is told (`workbench_harness_update_failed`). Jobs keep what they run. A host failure (docker, a timeout, the install lock) is retried with backoff and never held. Other running workbenches get the verified pair in the background, and a volume that will not take it runs the previous pair and is reported. Admins get **Manage → Workbench harnesses** and `GET/POST /api/workbench/harnesses`: the current, fallback, pinned, candidate and held versions per harness, each workbench's pair, and Check now, Update now, Pin (up or down), Unpin, Allow again and Reset. mise is not moved: every repo toolchain's shims run through it and are shared by every job on a volume. agent-browser rides the Hermes image's own lock. Also fixed in the runtime script: a version's first install no longer stamps itself retired, and a release that will not start now reports what it printed (omp's `Bun runtime must be >= …`). The boot hook no longer pulls a provisioned volume's bun back to the compiled one.

  Verified on this branch's stack (app :5304, api :5404) with a real Developer Agent container (Hermes v0.22.4) on a fresh volume. Every install ran inside it through the product's own runtime script, fetching the real packages from npm and bun's GitHub releases. The channel's version checks read a local stub serving the real npm and GitHub release documents, plus one doctored `engines.bun`, with the soak set to 0. Pinning moved the instance down to Oh My Pi 18.13.2 on bun 1.3.14, both smoke-tested and adopted. A job slot laid out by the product's layout script and launcher then held 18.13.2. With 18.16.0 advertised as needing only bun >=1.3.14 (the doctored document), the smoke test installed it, and it failed to start with `error: Bun runtime must be >= 1.4.4 (found v1.3.14)`. It was held, an admin notification "Workbench harness update held: Oh My Pi 18.16.0" was filed, and the instance stayed on 18.13.2 on bun 1.3.14. With the real documents and Allow again, the next step adopted bun 1.4.4 first ("Oh My Pi 18.16.0 needs bun >=1.4.4: bun 1.4.4 first"), and the step after adopted Oh My Pi 18.16.0. Throughout, the running job's launcher still answered `omp/18.13.2`, on bun 1.3.14 by path, while new jobs' launchers answered `omp/18.16.0`. Its install, retired and aged three days, survived the prune because the job held it, and was pruned once the job's harness dir was removed. The panel rendered in headless Chromium with no page errors. Tests that fail without the change: the planner (soak, Update now, held, deprecated, withdrawn, bun-first, a bun under the running floor, unreadable ranges, pins up and down); the step on a scripted instance (adopt, bun first, hold and notify once, host backoff with no hold, no workbench means no adoption, prewarm and a volume that refuses); npm range matching; the runtime script run for real with a version-aware stand-in bun (a running job keeps its release until it ends, doctor's slot holds nothing, the first install is not retired, a release that will not start says why and leaves nothing); a ready job not re-provisioned for a newer release; the boot hook's gate; and the job table. Not verified: a real `start_job` on the new release (the job slot was laid out with the product's scripts, not by `start_job`), more than one workbench live (the prewarm ran on the one agent; two are covered by the scripted test), and reading registry.npmjs.org or api.github.com from the api itself (the stub stood in; the installs did use them).
