- **New: every workbench harness stays current on its own. Oh My Pi and the harness's own bun now follow their upstream releases on every instance, the way the agent image follows Hermes stable.** #706 pinned Oh My Pi (`OMP_VERSION` 18.16.0) after its 28 Oct release raised its bun floor above the harness's bun and broke every `npx …@latest` job. That pin is now the bootstrap fallback, not a ceiling. A scheduled channel (`talaria-workbench-updates`, a step a minute) checks npm's version document for `@oh-my-pi/pi-coding-agent` and bun's GitHub releases every ~6 h. On every check it also re-reads the documents of what the instance runs, falls back to and pins. Each release soaks 24 h from the first check that saw it (`TALARIA_HARNESS_MIN_AGE_HOURS`), and its document is read again just before its smoke test. A release deprecated or withdrawn meanwhile is never run; a 404 counts as a withdrawal only the second time in a row. A release that jobs run and that upstream later deprecates is said to admins, and new jobs move off it. The candidate's `engines.bun` is checked against the harness's bun. When the candidate needs a newer bun, the bun moves first, and Oh My Pi follows. A candidate is installed beside what a workbench runs, by its own versioned paths only (a candidate bun under a mise data dir of its own, so a repo pinning `bun = "1.4"` never resolves an unverified bun mid-job), using #706's versioned dir, atomic symlink swap and `.retired` prune; the volume's shell `bun` is not touched until a provision promotes a verified pair. The candidate is then started, and the provisioning preflight runs through a job-shaped launcher (no model call). Only after that is it what new jobs run, with the pair before it kept as the fallback. A Pin made during the smoke test wins over the move it raced. The smoke test's install writes a `bun.lock`. That lockfile must name npm's `dist.integrity` for the tarball, and it is kept with the verified pair. Every later install of that pair, on any volume, a reinstall or a new department, is `--frozen-lockfile` from it. So no transitive dependency of a verified pair moves after its smoke test. A fresh instance smoke-tests the compiled pair first so its lockfile is kept too, and until then a provision installs it unfrozen. Every step that runs or downloads a release is bounded by `timeout`, with the install lock's fd closed for it. A release that hangs can never keep the volume's install lock. A step past its bound is a strike, retried 15 min later on another workbench when there is one, and held only on the second timeout in a row. A step killed with 137 (the OOM killer) is the host's. The whole run sits under an in-container bound, and a run the client gave up on is killed in the container. Only a release's own fault holds it: not there to install, a tarball that is not the documented one, a start that fails, two timeouts in a row, or a failed preflight. Admins are told when it is held, and jobs keep what they run. DNS, connection and TLS errors (bun's own `DNSResolveFailed`, `FailedToOpenSocket` and `ConnectionClosed` included), a full disk, a 5xx or 429 from npm or GitHub, docker and the install lock are the host's: retried with backoff, never held. Other running workbenches get the verified pair in the background, each with its own backoff. A volume that will not take the pair is recorded, and its provisions go straight to the previous pair, then the compiled one. A running job keeps the install it started on until it ends: a ready job is not re-provisioned onto a newer release, and the prune keeps any install a job's launcher names. It also never prunes the current or fallback install, and clears a stale `.retired` stamp from an install that is current again. Admins get **Manage → Workbench harnesses** and `GET/POST /api/workbench/harnesses`. They show the current, fallback, pinned, candidate and held versions per harness, and each workbench's pair, refusal or backoff. Check now reads every document at once under a 30 s bound. The actions are Check now, Update now, Pin (up or down; never a deprecated release), Unpin, Allow again and Reset. `TALARIA_HARNESS_NPM_REGISTRY` now reaches the workbench's `bun install` too. mise is not moved, because every repo toolchain's shims run through it; it is now the pinned release binary, checked against its SHA-256, instead of `curl https://mise.run | sh`, in the runtime, `prepare_env` and the workbench image, and a volume's older unpinned mise is replaced at its next provision. agent-browser rides the Hermes image's own lock. Also fixed in #706's runtime script: a version's first install no longer stamps itself retired; a release that will not start reports what it printed (omp's `Bun runtime must be >= …`); and the boot hook no longer pulls a provisioned volume's bun back to the compiled one. Not covered: bun's own binary is checked only as far as mise checks its GitHub download, and the per-volume bun download cache is trusted with a job's trust.
