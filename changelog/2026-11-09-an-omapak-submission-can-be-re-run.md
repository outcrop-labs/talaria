- **Fixed:** A desktop release's omapak submission can be re-run for the same tag. The workflow says a re-run replaces the submit branch, but the push could only create one. The job's omapak checkout fetches `main` alone, so a branch an earlier attempt had pushed had no remote-tracking ref, and `--force-with-lease` read that as "expected absent" and refused the push as `stale info`. A submission that failed after its push, or a re-dispatched release, could not be retried without deleting the branch by hand. The job now fetches that branch before it pushes, so the lease compares against what is really there. A first attempt has no branch to fetch, and that failed fetch is allowed. Verified: under bash against a local bare remote set up the way the job's checkout is (a shallow `main` fetch, then the step's own fetch line pulled from the workflow file). A first attempt pushed. A re-run of the same tag replaced the branch, where the unpatched step had refused with `stale info`. The case came up while `desktop-v0.12.0` was submitted by hand (outcrop-labs/omapak#309), after its automated push got a 403 on the old `OMAPAK_SUBMIT_TOKEN`.
