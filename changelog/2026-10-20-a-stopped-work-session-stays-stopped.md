- **Fixed:** A work session that went silent during a long tool call was failed at ten minutes and re-opened by the redispatch sweep against an agent still mid-turn, and "stop work session" was undone the same way within six minutes, up to twenty-five times — by any board viewer. The agent's own tool-event frames now ping the turn's liveness tap (the thrash watcher subscribes to the run's watch channel already), a session that erred moments ago gets the same two-minute settle a reclaimed turn gets before a new generation starts, the stop route requires edit access and writes a `work_dispatch_blocks` row per (ticket, agent) that the dispatcher refuses until a person moves the ticket's status, and disabled agents are not dispatched at all. The thrash watcher is aborted whenever the turn's future is dropped (it leaked a task and a Redis subscription per interrupted turn), and `live_work_session_for(agent, session)` answers a tool frame's run by the session id it names — the tool-events route should call it before its newest-session fallback. The gateway hold re-POSTs a turn only when the connection was refused or reset before any byte; a 502/503/504 or silent headers after the request was sent come back as the error they are instead of a second copy of the same turn. Verified: `cargo test -p talaria-runs-work-session -p talaria-work-dispatch -p talaria-gateway -p talaria-routes-boards`, clippy `-D warnings` on the same, `bun run migrations:check` with the snapshot matching.
