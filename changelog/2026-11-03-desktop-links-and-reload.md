- **Fixed: in Talaria Desktop, links that open a new window now go somewhere, and an instance page can be reloaded.** Before this, a `target="_blank"` link or a `window.open` inside an instance did nothing on every OS: wry drops a new-window request when the shell installs no handler, and none was installed. That covered a Google Drive file, a GitHub settings page, a web source in chat, the coding-harness sign-in link and the MCP Connect button. Now an http(s) link opens in the default browser, whether it points at another site or at a page of the instance (a public artifact). The one exception is the MCP connect (`/api/mcp/oauth/start`): it opens as an in-app window that keeps the instance's session and `window.opener`, which the connect needs to sign in and report back, and on Linux that window closes when the connect finishes. A `mailto:`, `tel:` or `sms:` link goes to the OS only when the person clicks it in the instance's own page; on Linux a clicked `mailto:` did nothing before. The shell's own click script, in the page's main frame, catches that click. Neither a navigation, nor a script, nor an artifact's sandboxed frame can reach the OS. Every other scheme is refused and logged, as are `file:`, `javascript:` and `data:` windows. An app link's https form, such as a Zoom or Teams join link, goes to the browser, which asks before it opens the app. A page gets at most one hand-off a second, so a script cannot flood the browser with tabs. The hand-off goes through `tauri-plugin-opener`'s `open_url` on a background thread; the plugin is not registered, so no page gets an opener command. Reload had no way in at all. Ctrl+R and F5 on Windows and Linux, and Cmd+R on macOS, now reload any instance page; add Shift (or press Ctrl+F5) to skip the cache. The keys are the shell's own script, so they also work on a page whose Talaria UI never loaded, such as a gateway's 502 page. The in-app instance switcher has **Reload page** with its shortcut, and on macOS the menu bar has **View → Reload Page** and **Reload Ignoring Cache**.
  Verified: on a private headless rig (its own mutter, session bus and two fake instances), with real clicks and key presses through mutter's RemoteDesktop. Every launcher the opener tries was replaced by a shim that records its arguments and opens nothing. On rc's build, every link class did nothing: no shim call, no request, the page unchanged, and the Connect popup's `window.open` returned null. No key reloaded anything, and `desktop_reload` did not exist. On this build, three cross-origin links (`target="_blank"`, `window.open` and `window.open(…, 'noopener,noreferrer')`) each reached `xdg-open` with their URL, and the instance page stayed. A clicked in-place `mailto:`, a clicked `target="_blank"` `mailto:` and a clicked `tel:` each reached `xdg-open`. An in-place `zoommtg:`, and `javascript:`, `data:`, `ms-msdt:` and `file:` windows, opened nothing and were logged as refused. A same-origin `target="_blank"` page went to the browser. The MCP-style connect ran its whole round trip with the instance's session cookie: own origin, another origin's authorize hop, then the callback's `postMessage` to the opener, which received it; its window then closed, where before the window fix the empty window stayed until Talaria quit. Ctrl+R, F5 and the switcher's command each reloaded the page, Ctrl+Shift+R, Shift+F5 and Ctrl+F5 reloaded it with `Cache-Control: no-cache`, and Super+R and Ctrl+Alt+R did nothing. On a 502 page from the instance's origin, F5, Ctrl+R and Ctrl+Shift+R reloaded it; on another origin's 502 page, which has no grant, F5 reloaded it through the page's own fallback. `scripts/desktop-reload-keys.mjs` and `scripts/desktop-os-links.mjs` (both in `bun run check`) run the shell's two scripts against stub windows and catch mutations of each: the click script takes only a trusted, primary-button click on a `mailto:`, `tel:` or `sms:` link the page did not handle. Rust tests show that no scheme reaches the OS from either handler (mailto, IDE, Office, Java Web Start, installer, meeting-client and share schemes), that only the connect path stays in the app, and that a burst of hand-offs from one webview is cut to one a second. `bun run check` passes, including the webview-threading rule, and desktop fmt, clippy `-D warnings` and the tests pass in the rig image. Not verified on Windows or macOS at run time: the WebView2 and WKWebView popups, the hand-off through ShellExecute and `open`, the macOS View menu, and macOS's cache-skipping reload. On macOS a self-closing popup's window likely stays open until closed by hand. Also not verified: an installed release build, an AppImage's environment reaching the browser it launches, and a real MCP provider's sign-in.
