- **Fixed: web push no longer reaches inside the server's network — a push subscription's endpoint must be a public address (the safe-fetch policy, checked when the subscription is filed, before every POST and again when the socket connects), the push edge follows no redirect, a refusal reads back one sentence whatever it hit, and a person keeps at most 20 device browsers.** Any signed-in member could file `https://127.0.0.1:<port>/…`, an RFC1918 address or the 169.254.169.254 metadata service as a "device", fire the per-device test push, and read back how long the answer took and up to 512 characters of it (`POST /api/notifications/test`; `GET /api/push/devices` kept the same in `lastError`): an internal port scanner with a readable answer. The push client was a plain reqwest client that dialled anything https and followed up to ten redirects, and subscriptions had no per-person ceiling (500 filed in 1.3 s, every notification posted to all of them). Now `POST /api/push/subscribe` answers 400 "Push endpoint refused: not a reachable public address" for every inside target, by address or by name (`localhost`, `.internal`, `.local`, …), and for a name that does not resolve, and files nothing. The delivery edge runs the same check before each POST (rows filed before this release, a name that has moved since), dials through safe-fetch's validating resolver, takes a 3xx as the answer, and reads at most 2 KiB of an answer's body; a refused row records `refused: not a public push service address`, is never retried, and counts as a failure under the existing skip and prune rules. An operator whose push service really is on their own network admits it with `TALARIA_FETCH_ALLOW_HOSTS`, the same escape hatch every other user-supplied fetch uses. Filing a 21st device retires the one seen longest ago (a browser re-files every time it opens Talaria, so a device in use stays), and a delivery reads at most the 20 most recently seen rows, so a person filed past the cap before this release is bounded too.
