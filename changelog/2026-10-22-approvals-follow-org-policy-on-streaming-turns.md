- **Fixed:** Hermes' command approvals now follow the agent's Talaria policy on the turns Talaria streams, and Nous-hosted connectors stay off. On a streamed turn (every chat, channel reply and work session) Hermes v0.22 treats the turn as attended. A dangerous terminal command skipped `approvals.unattended_mode`, the key the render pinned, and went first to Hermes' default `smart` guardian, an LLM that could approve `rm -rf` on an agent whose policy is deny. It then went to an `approval.request` frame that nothing read, and the turn stalled for up to 300 s while the session's next turn queued behind it. The render now pins `approvals.mode` as well: `manual` with `deny` for an ordinary agent, so no model approves anything, and `off` with `approve` for a Developer Agent. `approvals.timeout` is pinned to 60 s as the backstop. The fleet chat door taps every turn's stream and answers each request `deny` through the agent's own `POST /v1/runs/{id}/approval`, with the `{request_id, execution_generation, choice}` body that v0.22's session authority requires. It never answers `once`, not even for a Developer Agent. Under `mode: off` the only requests a Developer Agent still raises come from the gates Hermes never lets anything auto-approve: a write to a project's AGENTS.md / CLAUDE.md / SOUL.md, an untrusted MCP server's write tool, a saved card fill. v0.22 strips the `pattern_key` that would tell those apart from a command. Each refusal lands in the audit log as `agent.approval_denied`, with the agent, the redacted command, the run and whether Hermes took the answer. The render also pins `tools.connectors.enabled: false` and `nous.guest: false`. Hermes ships both on, and `manage_connections` was offered to every agent on the api-server toolset, so agents could reach third-party accounts through a Nous identity that bypassed the MCP gateway. Verified: `bun run check` and `bun run gate` (fmt, clippy and tests for `talaria-gateway`, `talaria-fleet-render` and `talaria-jobs`; CI's api job is the full-workspace proof line, since `api/Cargo.lock` gained the `talaria-jobs` → `talaria-audit` edge). Reproduced the bug first on a standalone `nousresearch/hermes-agent:v0.22.4@sha256:7a69…a4cf` container carrying rc's approvals block and a scripted model: the `approval.request` frame went unanswered, the turn held, and the session's next turn queued behind it until the request was answered by hand. Then exercised the change in a worktree stack on that pinned image: hired an agent backed by the scripted model through the stack's own gateway, opened `terminal`, read the rendered `approvals` / `tools.connectors` / `nous` blocks back from `/opt/data/config.yaml` inside the container, and drove `/api/chat`. On the completions arm, `rm -rf` on a hermes-owned canary was answered `deny` by the door, with 0.6 s between the model's tool call and its next request, the command came back BLOCKED with the canary intact, and an audit row was written. The session arm (pinned sessions) behaved the same. `echo` ran with no prompt. A Developer Agent (`mode: off`) ran the same `rm -rf` with no request and the canary went. A Developer Agent asking to write `/tmp/hx-repo/AGENTS.md` raised Hermes' protected-instruction request (`<write to AGENTS.md>`, choices once/deny). An earlier draft of this change answered it `once`, and Hermes took that as consent; the write was then stopped only by the image's own `HERMES_WRITE_SAFE_ROOT`. Now it is refused within 10 ms, Hermes returns its own BLOCKED, no file lands, and the row reads `agent.approval_denied`. A Developer def still running a `manual` container (the window before a recreate) has its `rm -rf` refused too, with the canary intact. On the probe container, Hermes' defaults offered 19 tools including `manage_connections`, and the two pinned keys took it to 18. The hired agent's offer carried no `manage_connections` either.
