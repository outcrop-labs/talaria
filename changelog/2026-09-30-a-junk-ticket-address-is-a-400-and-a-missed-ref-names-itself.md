- **A junk ticket address is a 400 and a missed ref names itself.** TALA-36's second half — the ref resolution itself shipped Sep 22 (`22c345dd`): a ticket ref like `TALA-30` resolves on every `/api/tasks/{id}` route, the shared `uuid_gate` is untouched, and the MCP tool descriptions say `taskId` accepts a ref. What was still missing against the acceptance criteria were the error shapes and any test coverage for the door. A malformed id — neither a uuid nor `PREFIX-<n>` — used to fold into `Missing`, so `GET /api/tasks/nope` came back as a bare `"not found"` that read like a missing ticket and taught the caller nothing; it now answers 400, `task id must be a UUID or a ticket ref like TALA-30` — the fix is the caller's, and the sentence teaches both accepted shapes, and the string never reaches the database. A well-shaped ref with no ticket behind it now names itself in the 404 — `no ticket matches TALA-99999` instead of the same bare `"not found"` — because an address copied off a card that finds nothing is not actionable until the caller knows WHICH string found nothing; it is still pre-auth and still no existence oracle, since a uuid that misses keeps the bare 404, so the body only names an address when the address itself was ref-shaped. A ref two boards share answers 409 — naming the collision instead of picking one board's ticket — which closes the ambiguity gap the ticket listed (the 409 door itself was already in the resolver; the remaining items were the 400, the named 404 and coverage).

  The distinction lives in `ResolvedTaskId` (`Malformed` is now its own variant, so every consumer's match decides what junk means). The three other resolver doors — the workbench `ticket_arg` and the fleet report doors — keep their merged `Ok(_)` refusals unchanged: they must not distinguish "no such ticket" from "not allowed" (a ticket-existence oracle), and junk folding into that refusal is exactly what those surfaces want.
