- **Added: `talaria-app build` reports the app's triggers, and fails on one with no handler.** Each trigger `talaria.json` declares is listed with its id, its cron or event, and whether `server.ts`'s `defineAppServer({ triggers })` has a handler for it, and so is any handler that no trigger names. `--json` carries the same (`triggers: { declared, unanswered, undeclared }`). A declared trigger with no handler fails the build (exit 1, `ok: false`). The host loads such an app and then records a failed run every time the trigger fires, which nobody sees until afterwards on Manage → Apps; the kit is where that should be caught, before the pull request. A handler no trigger names is listed and fails nothing. Verified: `bun run gate`; kit tests for the report and its text (both found, a declared id with no handler beside a misspelled handler, no server at all, a handler that is not a function). Live, with the kit fetched from a worktree stack: the demo app built with both triggers found (exit 0, the host's build key), and a copy whose server answered `nighly` for a declared `nightly` failed with the trigger named and the stray handler listed (exit 1, and the same in `--json`). Two strings that described the loop now match it: `talaria-app scaffold`'s `next:` line gives the whole loop (`talaria-app check && talaria-app build && talaria-app eval`), and `prepare_env`'s kit answer says how a new app starts: write a seed `talaria.json` with the app's name and slug, call `prepare_env`, then `talaria-app scaffold`. It no longer says scaffold "starts an app in an empty repo", because the kit is installed only for a repo that has a `talaria.json`. A `talaria-workbench-mcp` test holds that order.
