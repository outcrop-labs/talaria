- **Fixed: the desktop app's launcher no longer stalls, and the shell around instances stops trapping people when something goes wrong.** The welcome screen ran ui's live dither engine over the whole window with a shimmer, which kept WebKit's main thread at 97 % and made every click, keystroke and IPC reply wait for a ~0.5 s frame. It now paints the same field once, as pixels, and idles at 0.05 % CPU (was 186 %). Opening the add dialog shows in 66–88 ms (was 538–612). IPC answers in 0–1 ms (was up to 534). Frames arrive every 16 ms (was ~500). A list of 25 instances idles at 0.06 % (was 203 %), helped by styled scrollbars instead of WebKitGTK's overlay ones, whose fade cost 300–400 % CPU for 3 s after each scroll on a GPU-less machine. IBM Plex ships inside the app rather than from fonts.googleapis.com, and the window and instance webviews paint the dark ground instead of GTK grey. Together those take first contentful paint from 1.02 s to 0.21 s and interactive from 2.2 s to 1.5 s, and the grey window before the launcher is gone. With Google black-holed, the launcher used to stay blank for 135 s; it now appears in under 3 s. The shell's other fixes: a notification is posted off the main thread, so a slow notification server cannot freeze the app (30 s before, 2 s now). A notification click no longer splits the window between stacked webviews. A corrupt `instances.json` or `settings.json` is moved aside and reported instead of crashing at startup. A relaunch into an unreachable instance shows the reason and a Retry on the launcher, plus Open anyway for an instance the shell's own check cannot see but the page can (a sign-in gate, a system proxy), and on Linux a page that fails to load mid-session returns there too. The page also survives a `mailto:` link or a download, where WebKit used to replace it with "The URL can't be shown". The add probe now allows 5 s to connect and 20 s in total, so a valid instance that answers in 10 s is added and a black hole fails in 5 s, not 8.5. Each failure says what went wrong, and Cancel and Escape stop a probe in flight without the instance landing later. The add error belongs to its dialog. The launcher follows switches and titlebar changes made inside instances, and the instances follow each other's titlebar choice. Remove is reachable by keyboard and both modals trap focus and close on Escape. A relaunch reopens only an instance you were in. A removed instance's data dir stays gone: the registry records the removal, and the next launch deletes the dir again if WebKit re-created it. No other data dir is deleted, so a damaged registry never costs the sessions of the entries it lost. The update check gives up after 10 s with plain copy (was 30 s, then an opaque error). The window fits a small or high-scale screen. A nameless instance no longer shows its host twice. Verified on a headless WebKitGTK 2.52 rig (mutter, tauri-driver, compositor screen capture), against the production build and, for before/after, the unmodified rc build on the same host. All 18 add kinds went through the real dialog. Cancel was tested by click, by dispatched Escape and by a real key. Five corrupt-file cases were launched, including a direct launch, and a recovered registry was relaunched twice more with a lost entry's data dir beside it, which survived. Each relaunch case was run: resume, vanished, black hole, a page whose beacon answers but whose page fails, and a mid-session failure. Keyboard order and the focus trap used real keys. The notification click and a 30 s-slow server were tested against a mock D-Bus service. The worktree's real Talaria UI was opened, Ctrl+Shift+H was tested on it, and an OS-titlebar change was made while it was hidden: rc's ui shows a double titlebar there, this one does not. macOS and Windows were not run. `bun run gate` was green; CI is the full compile and test line.
