- **Fixed:** A credential sealed out of an agent's own config no longer reaches the agent's `execute_code` scripts. Since federation started sealing inline config credentials as `CONFIG_*` per-agent secrets (#579), and the render started listing every per-agent secret in `terminal.env_passthrough` (#572), the two together handed a platform token or a named provider's key to every script the agent ran: Hermes admits a credential-looking name into `execute_code` only by passthrough, and the list now named them. `passthrough_names` leaves out the `CONFIG_` prefix, so only the secrets a manager gave the agent for its own tools are listed; the sealed ones still reach Hermes through `secrets.env` and the config's `${CONFIG_…}` handles. The plain terminal still inherits the container env as before: Hermes strips only its own names there, and the same literal sat in the agent's readable `config.yaml` before #579. Verified: `cargo test -p talaria-agent-secrets` (28 passed, including a new test that runs `plan_config_seal` and checks every minted name stays out) and `bun run gate`. Exercised on this branch's own stack with the pinned `nousresearch/hermes-agent:v0.22.4@sha256:7a69…a4cf`: a federated roster with an inline `providers.acme.api_key` and `platforms.telegram.token` sealed to `CONFIG_PROVIDERS_ACME_API_KEY` and `CONFIG_PLATFORMS_TELEGRAM_TOKEN`, plus a manager-set `FIGMA_TOKEN`. The rendered `terminal.env_passthrough` is `[FIGMA_TOKEN]`. Inside the running container, Hermes's own `_scrub_child_env` gave `execute_code` only `FIGMA_TOKEN`; with the list `origin/rc` renders it gave all three. Hermes's `load_config()` still resolved both handles to the original literals. CI is the proof line for the rest of the workspace.
