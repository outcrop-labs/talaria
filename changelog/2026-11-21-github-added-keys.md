- **A permission GitHub puts on an agent's token without being asked is kept and named, never a refused credential, and Check token stops listing a key the token carries as missing.** Talaria still never asks for more than the agent's set met with what the installation holds. Before this, a token that came back carrying any key the ask did not name (other than `metadata: read`) was revoked on GitHub and the agent's git got no credential. Now talaria-github's `check_reply` keeps that token and names those keys as `added`: every unasked key except `metadata: read`, which GitHub puts on every token, so `metadata: write` unasked counts. Still revoked and never used: a token whose repository selection is not `selected`, one that names any repo but the one asked for, one that carries an asked key above its asked level, and one whose permissions are missing or cannot be read. `added` rides on the minted token, the cached one (a serve says it too), `IssuedToken` and talaria-git-hosts' `AgentCredential`. The mint logs `installation … put … on a token for … unasked; kept`. The `git.credential` row writes `after.added` when there is any. `lastToken` on `GET /api/workbench/github-permissions/{agentId}` and `GET /api/workbench/git-hosts/{id}/agents` carries `added`. `POST …/check` answers `added` (`{}` when nothing, null when the host does not say what its token carries). `credential::reasons` no longer gives `notInSet` for a key the token carries, so Check token stops saying "not in this agent's set" about a key GitHub added. The ask, the credential door's order and note, and the revoke when an installation loses a permission (an added key it loses still revokes the token) are unchanged. docs/WORKBENCH.md says the new rule, and its GitHub-access wording follows the per-agent settings page the UI change adds. docs/api is regenerated.
