- **Added:** an app's MCP tool now learns who is calling and for whom, runs under a deadline, can answer structured results, and can be unit-tested with no host; the app gateway answers malformed and batched requests the way the Rust gateway does; and a changed tool catalog restarts the agents that carry it. The handler context gains `caller` (`name`, `id`, and `proven`, true only on the agent's own gateway key, false on the org-wide legacy key), `actingUserId` (a personal assistant's owner, else null), and `signal`, which aborts at the server's timeout (120 s unless an admin set one in Manage → MCP) or when the agent disconnects; a cut call answers a tool error at once and is recorded as cut off, or as cancelled when the agent left. Handlers can return `toolResult({ content, structuredContent, isError })`, and a tool can declare an `outputSchema`: its object return becomes `structuredContent`, every structured result is checked against the schema, and a result that breaks it is JSON-RPC -32603 naming the tool. `isUnresolvedHandle(value)` tells a handler that a `«secret:…»` handle reached it unresolved. The app gateway answers a body that is not JSON with -32700 and the Rust gateway's sentence and hexdump, a batch with -32600 per request (each `tools/call` in it recorded as refused), a non-object or method-less request with -32600, and, for an agent holding a tool subset, `resources/*`, `prompts/*` and `completion/*` with the Rust -32601, recorded under the method. When an app's probe writes a catalog that differs from the stored one, the api rolls the agents granted that server (talaria-apps `sync_app_mcp_servers`); an unchanged catalog rolls nobody. The new entry `@talaria/sdk/testing` exports `callAppTool(mcp, name, args, ctx?)`, which runs a tool through the gateway's own checks, deadline and result shaping, and `memoryStore()`; `TALARIA_APP_TESTS=<slug> bunx vitest run` from `ui/` runs an app's own tests. A platform stage can no longer call an app tool through the TS `callMcpTool`, which had no callers. Verified: `cargo test -p talaria-apps` (only a different probe catalog is a change, key order is not) and the live test `app_mcp_sync_live` against the worktree database (a changed catalog and a description edit retool the row, the same catalog and an admin-disabled row do not); vitest for the wire twins (the Rust gateway's bodies, codes and offsets), the call core (results, schemas, deadline, a caller leaving, a handler that ignores its signal), the gateway route (caller and acting person, legacy key, timeout, disconnect, structured result, -32700, -32600, BOM, subset method gate, records), the testing entry and `memoryStore`, the docs' mcp.md examples run through `callAppTool`, and mcp.md's fences typechecked by the SDK docs compile test. Live on a worktree stack, with an app scaffolded by `talaria app new` and enabled in Manage → Apps, and agents calling the gateway on their own keys: a whoami tool answered `proven: true` with the agent's id, `actingUserId` set for a personal assistant and null for an org agent, and `proven: false` with a null id on the legacy key; with the server's timeout at 2 s a slow tool was answered at 2.0 s as a tool error and its handler saw a `TimeoutError`, and a client that hung up at 0.7 s left the handler an `AbortError` and a `cancelled` 499 row; an `outputSchema` tool returned `structuredContent` and a bad value got -32603; a locked secret without `talaria-app://<slug>` reached the handler as an unresolved handle and one listing it resolved; 46 malformed bodies got byte-identical -32700 sentences from the app gateway and the Rust gateway; a batch, `42`, a method-less object, a BOM-prefixed call and a subset agent's `resources/list` were answered and recorded as above. Adding a tool and then editing a description each rolled exactly the three carriers (granted directly, as a personal assistant, and through a team) and not an ungranted agent, while enabling a second app and restarting the host and api rolled nobody. The same calls through the production build, whose built `mcp.js` imports `toolResult` through the host's runtime shim, answered the same.
