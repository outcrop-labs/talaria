- **Changed:** A repo's project env store reached the sandbox as plaintext files on the host — every granted repo's values unsealed into `fleet/agents/<slug>/workbench-env/<owner>/<name>.env` (0644) by the fleet render and mounted read-only into the agent's container for its whole life — so a job on one repo could read every other granted repo's env, and `docs/ENCRYPTION.md`'s "never in config files" was not true of them. The render no longer writes that directory or mounts it (an existing one is removed on the next render). Instead `prepare_env` — the step the agent runs on its fresh checkout — writes only the job's own repo env to `<workdir>/.talaria/env` (as the agent, 0600, through the exec's stdin, never a shell line) and answers with `projectEnv` (path, count, the `set -a; . …; set +a` line that loads it); `start_job` writes nothing, because a file in the workdir would make `git clone <url> <workdir>` refuse a non-empty directory, and its rules tell the agent where the env will land. `finish_job`, abandon and the sweep remove it with the job's processes, and a resumed job gets it again from its next `prepare_env`. A checkout at the workdir root gets `.talaria/env` added to `.git/info/exclude`. The work-session brief points at the new path. Values stay sealed at rest exactly as before.
