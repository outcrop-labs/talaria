- **Fix: reading a thread's replies now clears the channel's unread badge — the per-thread read cursor.** The bug: the thread panel posted no read at all, and the channel cursor advanced only on the main feed (`useChannelMessages` filters `thread_root_id is null`), so a reply's seq — drawn from the same `channels.msg_seq` counter — could never clear the badge counting it. The fix, mirroring `conversation_reads`: a `channel_thread_reads` table (PK `(thread_root_id, user_id)`, cascading FKs to `channel_messages`/`users`, monotonic `greatest` upsert `mark_channel_thread_read`), a thread arm on `POST /api/channels/{id}/read` — `{ threadRootId, seq? }`, seq computed server-side as the thread's newest complete reply when absent, root normalized `thread_root_id.unwrap_or(root.id)` and 404'd when not the channel's — and one clause, `thread_read_covers_sql!`, that every unread predicate (`list_channels`, `channel_unread_total`, `shared_rooms_sql!` — the rail pill, the rail badge and the profile drawer) and both caught-up gates share, so a reply a thread cursor covers is read everywhere at once. The whole-channel gate (`channel_read_caught_up`) counts a thread-read reply as read: it used to need the channel cursor past the newest message, which the main feed (no replies) never reaches when that message is a reply, so the badge read 0 beside a lit @mention or DM row. A thread read clears that thread's own bell rows by `group_key` (`reply:<root>`), never by href, so an @mention row on the same channel keeps waiting while anything on the channel is unread; when the thread read leaves the whole channel caught up, the channel's href sweep runs instead. The panel (`ThreadPanel.svelte`) posts the read on mount and as replies land, only while the person is looking (`lib/looking.ts`), keyed by root through `readCursorToPost` like `ChannelView`'s channel key: the panel is not remounted between threads, and a bare high-water mark skipped a second thread whose newest reply was older than the first's.
