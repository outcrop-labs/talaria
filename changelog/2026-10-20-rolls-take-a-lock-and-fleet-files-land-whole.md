- **Fixed:** Two rolls of one department could remove each other's live container: a roll read `active_slot` and `max(gateway_port)+1`, rendered, cut over and removed the old slot with nothing written back until the cutover, so a double click, a `roll_running_agents` racing `reconcile_fleet`, or two api instances interleaved into the same slot and port. `roll_agent` now holds a process-wide per-department set (`talaria-fleet-reconcile`'s `ROLLING`, the shape chat-persist's `CONTINUING` guard has) and a Postgres session-level advisory lock (`pg_try_advisory_lock(hashtext('fleet-roll:<department>'))`, released on every path) around the slot read → cutover → remove sequence; a second roll answers the soft verdict "already mid-roll", the control route answers 409 up front, and `reconcile_fleet` skips a department mid-roll instead of starting its steady-state service under the cutover. Also fixed: `fleet/.env`, `fleet.json`, every `config.yaml` and the compose file were rewritten in place (truncate, then write), so a process killed mid-write left an empty env file that started every container with no key at all, and fleet-brain's writer created the env file with the process umask. All five now go through `talaria_fleet_brain::write_atomic` — a sibling temp file opened with the target mode (0600 for `.env` and `fleet.json`), fsynced, renamed over the target. Verified: `cargo test -p talaria-fleet-brain` (a new test checks the bytes, the mode and that no temp file survives), `cargo test -p talaria-fleet-render`, `cargo clippy -p talaria-fleet-reconcile -- -D warnings`.
