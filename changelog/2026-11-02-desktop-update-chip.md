- **Changed: Talaria Desktop tells you when a new version is out. It checks on its own, 30 seconds after launch and then every 6 hours, and shows a small chip, "Talaria Desktop 0.13.0 is available", with Update and Later — on the launcher, and over whichever instance you have open, whatever Talaria version that instance runs. Later puts that version off for a day, everywhere at once and across a relaunch; a newer version shows straight away. Update downloads it, checks its signature, installs it and restarts Talaria (on Windows the installer runs on its own and reopens the app). Where the app cannot replace itself — a Linux .deb, .rpm, pacman or Flatpak install, a Windows .msi install, or a Mac copy still running from its disk image — the chip says how to update instead and offers only Later, and Check for updates no longer offers an Install that could not work (on a .deb or .rpm it downloaded the AppImage and then refused it).** The shell checked only when someone pressed Check for updates on the launcher or in Settings → Profile, so nobody learned about a release. The check is the same bounded one (10 s), off the main thread; a check that fails is only a log line, and tries again an hour later. The chip over an instance is the shell's own, put into the page by the shell (it needs nothing from the instance's UI and reappears after a reload, and is never put into a sign-in provider's page); a failed install says why in a sentence, in every view.
  Verified: on Linux, on a private headless rig (its own mutter and session bus, WebDriver on the launcher), with a test build of the shell (version 0.12.0) reading a fake `latest.json` on localhost and trusting a throwaway signing key. As a package install (no `$APPIMAGE`): the feed was asked 30.4 s after launch and the chip appeared on the launcher, bottom right, with Later only and the package sentence, and in the instance page opened next (0.6 s after the open; in a shadow root, styled by a constructed sheet, not focused); `install_update` refused with the same sentence; Later in the page took the chip down in the page and on the launcher and wrote `updateSnooze` for 0.13.0 exactly 24 h out; a manual check of the same version stayed put off; the feed saying 0.13.1 brought the chip back in both views at once; a feed answering 500 left it as it was and said "Could not check for updates" in a sentence; Later from the launcher put 0.13.1 off; and a relaunch with the feed on 0.13.1 checked again 30.5 s in and showed no chip in either view. As an AppImage (`$APPIMAGE` set, as the AppImage runtime sets it): the chip offered Update; with a signature that did not match, Update downloaded the payload once and the chip said "The download did not match Talaria's signature, so nothing was installed.", the AppImage unchanged and the shell still running; with the right signature, Update replaced the AppImage with the payload, the shell remembered its pages and exited, and the replaced file was relaunched. Unit tests cover the snooze (a day, a newer version, a pre-release, an unparseable version, a clock that went back), which copies are offered Update on each OS, the error sentences and the page script. The connect smoke passes on the rig. `bun run gate` passes its check and the ui typecheck and tests (the desktop typecheck passes on its own); its desktop clippy cannot build on this host, which has no GTK headers, so fmt, clippy `-D warnings` and the 142 tests ran in the Fedora 44 rig image. Not verified: Windows (NSIS passive install and relaunch, the .msi case) and macOS (the app's own replace, the disk-image case) at run time; the real GitHub feed; an instance page with a strict CSP; Settings → Profile's package sentence inside a real instance UI (it is a template branch, typechecked only).
