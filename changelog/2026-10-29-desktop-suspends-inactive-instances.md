- **Added: the desktop app suspends an instance you have not had on screen for a while, and brings back the exact page the moment you return to it.** Every opened instance used to keep its webview, and with it a WebKit web process, for the life of the app: 25 opened instances held 4.35 GB. Now an instance that has been off screen for the timeout (10 minutes by default; Off, 5, 10, 30 or 60 minutes in the launcher and in Settings → Profile) has its webview closed, and the same 25 drop to 0.7 GB once suspended. The instance the window shows counts only while the window is minimized or hidden, never when it is merely unfocused, so a page on a second monitor stays. Showing a suspended instance by any route recreates it at once, with no probe, at its last path, query and hash, with its sessionStorage and scroll put back: a launcher row, the in-app switcher, Ctrl/Cmd+Shift+H then a row, the window restored, or a relaunch (each instance's last page is kept on disk now, so a relaunch returns there too; sign-in and callback pages are never kept). A notification click opens the notification's own page. A page holding input a reload would lose is not suspended: text typed, a select or checkbox changed, or an attachment uploaded and not yet sent (the chat composer's text does not count: ui keeps the draft). Input inside an embedded frame, such as an artifact preview, cannot be seen. An instance whose Talaria predates this is not suspended either. While an instance is suspended, the shell posts its notifications itself, with that instance's own session, exactly as the page would have. If the shell cannot read them the way the page does, or within 30 s, the page stays, and a page on its way out is never asked twice. The session survives because ui's cookie is persistent. Separately, on GTK under Wayland the OS titlebar now shows "Talaria — <instance>" instead of always "Talaria". Verified on a headless rig (mutter on Wayland and Xwayland, WebKitGTK 2.52, WebKitWebDriver, a mock D-Bus notification server, mutter RemoteDesktop for real keys and clicks), against the production build and the unmodified rc build on the same host. 25 mock instances were measured process by process before and after. Every restore path was run on mock instances, with the URL compared before and after and window captures under X11. On the worktree's real Talaria UI, signed in inside the shell, the launcher row, the in-app switcher, Ctrl+Shift+H, a notification click and a relaunch were run, and so were a composer draft across a suspend, typed input keeping a page, and Off. Notifications were posted from a suspended instance on the real UI, and a banner click restored it at the notification's page. On screen but unfocused, minimized by the window manager, minimized by the shell, and restored by a taskbar or a banner were each run. The Wayland title was read through AT-SPI on both builds. After review, the rig was run again on the fixed build. On the real UI, a Comms channel with an uploaded, unsent attachment was kept 75 s off screen, and once the attachment was removed it was suspended at 65 s. On the same real UI in the shell's WebKit, a select picked, and the TLS checkbox toggled on its own, each counted as input, and each put back did not. These were driven through WebKit's own events, not real keys. A mock instance whose notifications read takes 12 s was read once and closed once, where the earlier build read it three times. One taking 45 s was kept at the 30 s bound and not asked again. The shell's own minimize on Wayland still suspended the instance on screen at 61 s. `bun run gate` ran `check`, ui svelte-check and 2539 vitest tests (18 new) green, then stopped at its desktop cargo step, which cannot build on this host (it has no GTK or WebKit headers). The same desktop commands ran in the devbox image instead: `cargo fmt --check` and clippy `--all-targets -D warnings` clean, and the test binary built there passed 64 of 64 (27 new) run on the host. Desktop svelte-check was clean. Nothing was run by hand on macOS or Windows: the packaging workflow's 20 s launch check is the only proof there, and CI is the full compile and test line.
