'talaria-postgres-dev'`. Nothing sets that variable in a worktree, so the reset worked on MAIN's database, and its fleet sweep removed every container whose name held `talaria-fleet-agent`, which only main's fleet produces. A new `cli/src/stack.ts` resolves the stack from the checkout's own `ui/.env`: a worktree's `talaria-pg-<name>`, `talaria-wt-<name>` and `talaria-wt-<name>-fleet`, with fleet containers picked by compose project label. `reset` prints those targets before its typed confirm. Before the first count, it checks that the postgres it would exec into belongs to the worktree's compose project, publishes `DATABASE_URL`'s port, and that `DATABASE_URL` names the `talaria` database and role that reset's `psql` runs as. It passes the fleet project to `compose down` with `-p`, and it refuses a rendered `fleet/docker-compose.yml` that names another project. Every command that acts on a stack now refuses, and says why, when the target would be a guess:
  - a shell variable naming another stack's container or worktree;
  - in a worktree, a shell variable that overrides a line its `ui/.env` owns with another value (`DATABASE_URL`, `REDIS_URL`, `PORT`, the api port and url, the gateway url, the fleet project, the toolkit, omp-auth and gateway ports), or a `TALARIA_PG_PORT`/`TALARIA_REDIS_PORT` that is not the URL's. `talaria dev` lets the shell win, so a stale `DATABASE_URL` from main's shell made the worktree's api a second server on main's database;
  - a worktree with no `TALARIA_FLEET_PROJECT`, or one that is not its own, whose agents would render into main's project. `dev` refuses it now, as `reset fleet` does;
  - in the primary, a `TALARIA_FLEET_PROJECT` that is a worktree's (`talaria-wt-*`), for `reset fleet`;
  - a linked git worktree with no marker;
  - the installed `talaria` shim run from inside another checkout. The shim always runs the primary's CLI, so in a worktree `talaria reset`, `dev`, `backup` and `restore` acted on the primary.

  More changes:
  - `talaria dev` no longer lets a shell `TALARIA_PG_CONTAINER` override a worktree's own container.
  - `deploy` and `service` in a worktree need a `COMPOSE_PROJECT_NAME` of its own instead of the production default `talaria`, and `service install`/`uninstall` refuse there. `deploy up`, `down` and `update` in a worktree need every multi-instance key CONTAINER.md lists (`COMPOSE_PROJECT_NAME`, `TALARIA_STATE_DIR`, `TALARIA_HTTP_PORT`, `TALARIA_FLEET_PROJECT`, `TALARIA_FLEET_NETWORK`) set to a value of its own and not a `talaria-wt-*` name. A project of its own alone still bound `/var/lib/talaria` and rendered into `talaria-fleet`.
  - `restore` in a worktree refuses blob restores into main's shared object storage, a bucket nobody named, a dir inherited from main's env, and, when no `--target` is given, a shell `DATABASE_URL` or a `TALARIA_ENV_FILE` whose `DATABASE_URL` differs from `ui/.env`'s. It reads the worktree marker from the checkout's own `ui/.env`, so an env file pointed at main's no longer switches those rules off.
  - `talaria worktree` takes its docker names from the same table.
  - A shell under a worktree's `talaria dev` no longer turns main's containers into that worktree's. A worktree's `talaria dev` sets `TALARIA_PG_CONTAINER`, `TALARIA_REDIS_CONTAINER` and their ports for itself, and its app and everything the app starts inherit them. `talaria box new` and `box seed` read `TALARIA_PG_CONTAINER` as main's, so from such a shell they seeded the box from the worktree. The refusal prints the `env -u …` command to run instead. An override naming main's own renamed container still works, and an empty one now means the default, as compose reads it.

The primary lets the shell win, so the printed `env -u` command, which unset only the container names and ports, started main's app on the worktree's `DATABASE_URL`, fleet project and api url. Every such refusal's `env -u` list now names each worktree line the shell sets (`TALARIA_WORKTREE`, `DATABASE_URL`, `REDIS_URL`, `PORT`, the api port and url, the gateway url, the fleet project, the toolkit, omp-auth and gateway ports). The primary's `talaria dev` now also refuses a shell `TALARIA_WORKTREE` and a `talaria-wt-*` `TALARIA_FLEET_PROJECT`, as `reset` already did. It refuses a `ui/.env` that marks a devbox while the shell sets no `TALARIA_DEVBOX` too, where it used to bring up main's dev compose. Its readiness probes exec into the containers it started, so an empty `TALARIA_PG_CONTAINER` no longer probes a container named `''`.
  - The name-substring `containerNames` and `containerRunning` had no users left and are deleted.

  Running `reset database` live turned up a bug that predates this change: the mode had not worked since the bash script was ported (3368cf6c). The bash script fed its statements on stdin. The port gave psql all three as one `-c`, which is one transaction, and Postgres refuses `DROP DATABASE` inside one. The mode had already terminated every connection by then. Each statement now runs as its own `-c`, and the drop is `with (force)`. Reset's counts each print on their own line again. Docs: WORKTREES.md, CLI.md and BACKUPS.md.
