- **Home's Inbox board shows up as soon as its reads answer, and asks only for what it shows; the MCP catalog's liveness check commits six times a run instead of three hundred.** The board could stay a skeleton indefinitely. Its loading check stopped at the brief before it read any other source, and its error check read only whether each source had failed. svelte-query tells a reader only about the result fields it has read, so the sessions, research and files lists heard nothing when their answers landed. Whenever the brief answered after them (always for someone without an assistant, and whenever the brief's read had a sweep to run first), the board kept its skeleton until each of those lists next changed. Both checks now read every source's data and failure on every call. The board's tickets come from a new `GET /api/home/queues`, which answers `{ queues }` from the same pass `/api/home` uses, without the live alert count, cost overview, activity feed and counts that `/api/home` computes for an admin. `/api/home` is unchanged; it stays the mobile app's landing read. `GET /api/artifacts` takes `?since=<ISO instant>` (only artifacts updated at or after it) and `?fields=heads` (every column but the body), under the same read filter, and a malformed value is a 400. The Inbox asks for the heads since the start of the reader's local day and keeps its own today filter, so its Files cards are the ones the whole list gave. At local midnight the previous day's heads stand in while the new day's load, so a board left open overnight does not fall back to its skeleton. The Files browser and KB attachments still read the whole list. The `mcp-library-liveness` job writes its verdicts 50 at a time, each chunk one `UPDATE … FROM unnest(…)` in a transaction with `synchronous_commit = off`, so a run no longer queues 300 WAL flushes in front of every other writer, a person's click included. A crash can lose the last fraction of a second of verdicts, and the next pass derives them again. Each chunk binds its rows in name order, so it takes its row locks in one fixed order, and a chunk that Postgres aborts in a deadlock with the catalog sync is tried once more. A run cut off at its time limit keeps every chunk already written. Lanes, what Mark handled does, the verdicts and the order entries are checked in are unchanged. Verified: CI on this PR's checks, including in-crate live tests against Postgres and Redis (the queues answer equals `/api/home`'s for the same admin, while the alert hook counts zero calls and the cost table is held under an exclusive lock; `since` and heads never widen the read filter and drop only the body; 120 verdicts written through the job's own writer leave 3 distinct `xmin`, and each of the 3 chunk transactions reads `synchronous_commit` as `off`), unit tests of the heads column list, the chunking and the chunk's name order, and vitest (the board issues no `/api/home` and no bare `/api/artifacts`, it builds the same cards from the new sources as from the old ones, it leaves its skeleton when the brief settles last, and it keeps its cards through local midnight; the last two fail against the old getters and without the stand-in heads respectively). Measured on a worktree stack seeded at a production instance's shape (synthetic rows: an admin reader, 7 boards / 115 tickets, 317 artifacts with 1.9 MB of body, 7 updated today), with Postgres in RAM because this host's disk stalls, over 20 curl runs spaced 16 s apart so each `/api/home` missed its 15 s alert cache as the 30 s poll does: the board's ticket read went from `/api/home` at p50 140 ms / p90 149 ms to `/api/home/queues` at p50 5.5 ms / p90 6.5 ms; its files read went from 2,155,230 bytes (p50 34 ms) to 3,579 bytes (p50 4.8 ms). At a busy shape (13 boards, 4,000 artifacts, 53 MB of body): 133 ms to 6.8 ms for the tickets, and 55,959,294 bytes at p50 659 ms to 10,150 bytes at p50 10 ms for the files. In headless Chromium, over 10 fresh loads, the board on testing never left its skeleton within 60 s (5 of 5 loads, a reader without an assistant); with the getter fix alone it appeared at p50 1,393 ms (busy: 1,985 ms); with the whole change at p50 1,146 ms / p90 1,172 ms (busy: 1,190 ms / p90 1,399 ms). Liveness, 300 hosted entries at a loopback stand-in, scheduler off, one triggered run, three runs each: distinct `xmin` across the 300 rows 300 → 6; `pg_stat_wal.wal_sync` +270–302 → +4–15 (the walwriter's own asynchronous flushes, which no backend waits on); `xact_commit` +310–317 → +15–25, of which about 10–19 are the measurement's own reads in both cases.
