- **Changed:** An MCP server's org-level headers — the API key or auth header an admin types into its Credentials form — are now sealed at rest like every other secret (`mcp_servers.headers_sealed`, SecretBox, one JSON object per server) instead of plaintext jsonb. One module in `talaria-mcp` (`org_headers`) is the only code that opens them, for the gateway's upstream call, discovery and the platform's own tool calls; every write (register, replace, the Credentials editor's merge) opens, applies, re-seals and empties the plaintext column under the row lock, so two concurrent saves cannot lose each other's key. Header values no longer leave the api at all: the registry answers `headerKeys` (names only) in place of the masked `headers` map — the register response used to echo the values back unmasked, and now cannot — and the register audit records the key names. A seal the instance cannot open (a database restored onto other key material) lists no keys, and the next Credentials save replaces it instead of failing with a 500. Rows written before this change are sealed once the instance has been up past a self-update's drain (`TALARIA_ROLL_DRAIN_SECONDS` + 180s — the old slot still serving reads only the plaintext column, so sealing under it would send its calls upstream without the key), idempotently and safely across instances (each row's update is conditioned on the plaintext it read), and the same sweep re-runs on every registry read after that; DEK rotation now re-seals the new column with the rest. An agent that calls a server it may use but whose account nobody connected yet no longer gets the same 403 as a refusal: the gateway answers the handshake itself (so the harness keeps the server), lists the cached catalog filtered to the agent's allowance (a `connection_required` stand-in when there is none), and answers every call with JSON-RPC -32001 and one sentence the agent can repeat — "Your Notion account isn't connected to Talaria. Connect it at <instance>/settings/connections, then try again.", "The workspace's Linear connection isn't set up yet. An admin connects it on the MCP page at <instance>/mcp/external.", or "Notion is a per-user server; only a personal assistant can use it." The link uses the verified hosting domain, else `AUTH_PUBLIC_URL`, else the request origin as a browser opens it (an agent reaches a host-run app as `host.docker.internal`, which the link turns into `localhost`). The in-house answers keep JSON-RPC's rules: no `id` is a notification (202, no body) whatever the method, a batch gets an array, and an unknown protocol revision is negotiated down instead of echoed. Such servers now stay in the agent's rendered config (an org agent carries a per-user server only when granted to it by name), and a personal assistant no longer carries a server its owner is denied, connected or not. The agent's MCP tab now shows a server as carried exactly when the rendered config lists it, and says why a granted server is left out (`withheld`: the owner is denied, or a per-user server needs a direct assignment on an org agent). Connecting an org account, or any other registry change, now also rolls agents that carry the server through a team grant, so they leave the in-house answer for the live upstream.
