So it was served for up to 55 minutes after Talaria said the permission was held or granted. Now a cached token that went without something the installation did not hold reads the installation's record again on every serve, past the process cache. Once the record holds it, the token is dropped and the next one is minted with it, in whichever api process serves it. A token with nothing short is still a pure cache read. Second, the mint now checks that GitHub put every asked key on the token. A key GitHub leaves off joins the shortfall with "GitHub did not put … on the token", and a token wider than asked is still refused. Third, nothing on the push path said why a token was short or missing. Now a token short of a key the agent was given comes with a `note`, which the credential helper prints on git's stderr (git push and `git credential fill` alike; stdout stays the login). The note names each missing key and why: the installation on the account has not accepted it, or GitHub's own words. A granted repo the host will not mint for (GitHub refused, the token came back wider than asked, the installation holds none of the set) answers 502 with that sentence, which the helper passes on, instead of an opaque 500. Each such refusal writes one `git.credential_refused` row per agent, repo and sentence per ten minutes, and admins see a warning in Alerts linking to Admin → Git hosts. The `git.credential` row now records what was `asked`.
