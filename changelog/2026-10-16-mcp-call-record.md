- **Added:** The MCP gateway now keeps a record of every tool call it answers, so "which agent called which tool, how often, and did it fail" has an answer that is not a log grep. Each `tools/call` through `/api/mcp/gw/{server}`, and each refusal (no access to the server, a tool outside the allowed set, or a refused batch), writes one `mcp_tool_calls` row: the agent, the acting person when the caller is a personal assistant, the server, the tool (capped at 200 characters), an outcome (`ok`, `error`, `denied`, `not_connected`, `upstream_error`, `spend_error`, `cancelled`), the HTTP status answered, the latency, and the error sentence the caller or the upstream was given, capped at 300 characters. A row never holds the call's arguments, its result, a header or a token. An upstream's error sentence can quote an argument back, so two rules keep arguments out of the error column: a call the spend boundary put a credential into keeps only the JSON-RPC code and a fixed sentence, never the upstream's text, and on every other call each argument string the agent sent (6 characters or more) is replaced with `«argument»` before the row is stored. A tool that reports `isError: true` is recorded as an error under a fixed sentence, because its own text is a result. A caller that hangs up before the answer finishes is recorded as `cancelled`, which does not count against the server's errors. Handshakes, `tools/list`, pings and notifications are not recorded. A failure inside the gateway before access is known (the access lookup failing) is recorded as an error, so an outage shows up in the record instead of as silence. The record is written by a background task, so a tool call never waits on it: each row is one insert statement with the owner and server lookups inside it, at most four inserts use a database connection at once, past 10,000 waiting rows new ones are dropped with a warning, and a failed insert only logs a warning. A streamed answer is recorded when its stream ends: the relay passes every byte through unchanged and classifies the call from a bounded tail, so the latency covers the whole call and the outcome is what the upstream actually replied. Admins read the record at `GET /api/mcp/calls`, newest first, filtered by `server` (id or name), `agent`, `tool`, `outcome` and `since` (epoch ms), with `limit` (default 100, max 500). `GET /api/mcp/calls/summary` reports, over `since` (default the last 24 hours) and optionally one `server`, each server's calls, errors, denials, not-connected answers, p50 and p95 latency and five busiest tools, plus each agent's calls and errors. The percentiles leave out refusals and not-connected answers, which the gateway answers itself in a few milliseconds. Observability has a new MCP tab with a summary strip, a by-server table and the call table (time, agent, server, tool, outcome, latency, error). Its filters are server, agent, outcome and a 1h / 24h / 7d window, and they live in the URL. Each server card on the MCP page gains one line, "Last 24h: 142 calls · 3 errors · 1 denied", which opens that tab filtered to the server. The leased `mcp-calls-prune` job runs every six hours and deletes rows older than the retention, default 30 days, in batches of 5,000. Admins set the retention from the MCP tab ("Keep for") or with `PUT /api/mcp/calls/retention` `{days}` (a whole number from 1 to 3650; `GET` reads it). It is stored as `app_settings` `mcp_calls_retention_days`; a stored value that is not a positive whole number falls back to 30 days, so a bad value can never prune everything. - **Fixed:** A JSON-RPC batch carrying a `tools/call` or a `tools/list` is now refused at the MCP gateway with a -32600 for each member. The tool allow-list, the credential spend boundary and the tool-list filter only read a single-request body, so a batched call used to reach the upstream unchecked and unrecorded. Each `tools/call` inside a refused batch is recorded as its own denied row. Batches of other requests (pings, notifications) still relay as before, and current MCP clients do not send batches.
