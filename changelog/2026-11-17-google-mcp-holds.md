- **Google Workspace MCP writes wait for a person: the `mcp_call` approval.** On a Google Workspace MCP server (the pack's `google-<product>` rows, Developer Preview, off by default), a tool the pack holds is no longer refused: the gateway queues the exact call — server, tool, the arguments as the agent sent them, what Google's catalog said of the tool — in the confirm-sends queue as a new kind, `mcp_call`, and answers the agent with an ordinary tool result, `Queued for approval as <id>. Not done yet: …`. Google's MCP servers hear nothing until a person approves. Held: every write (Gmail `create_draft` and the label tools, Calendar `create_event`/`update_event`/`delete_event`/`respond_to_event`, Drive `create_file`/`copy_file`, the Docs/Sheets/Slides updates, Chat `send_message`) and any tool Google adds later. Reads that are on the pinned list and marked read-only by Google still run; trash, untrash, spam, unspam and `apply_sensitive_*` are still refused. A tool Google's catalog does not list, and a call whose arguments name a workspace secret, are refused, never queued. Who approves is the principal's, as for every Google action: a personal assistant's owner alone, an admin for the org account and for an agent's own identity. The row reaches them as a **Google tool call** card in the conversation, in the Inbox focus and the brief (`APPROVAL · GOOGLE TOOL`, with the server, the tool and the arguments), in the approvals census and its nudges, and in the agent's own `list_pending_sends`. Approving replays the call once, after re-checking that the arguments name no secret, that the registry row still exists, is the pack's and is turned on, that Google's catalog still lists the tool, and that the policy is not deny now. It vends for `Purpose::HostedMcp` through the one door (a grant minted by a client declared unticked never reaches Google) and sends one stateless `tools/call` to the product's endpoint as the code names it. A completed result marks the row executed and keeps the result; a refusal or a tool failure fails it in Google's words; an elicitation or a multi-round-trip request fails it quoting what Google asked (Talaria answers none until one is captured live); a 401 hands it back to pending with the cached token dropped; no answer fails it saying it may or may not have run. A retried identical call converges on the row still waiting. Approving a personal assistant's held call leaves a grant in that conversation keyed `<server>/<tool>`: for thirty minutes, one more call of that tool on that server runs at once in the owner's name. An org-account or agent-identity call never rides one. Admin → Org → Google Workspace MCP gains a per-tool policy selector (`PUT /api/admin/google/mcp/{product}/tools/{tool}` with `{policy: "allow" | "hold" | "deny" | null}`, audited as `google.mcp_tool_policy`, stored in the new `mcp_tool_policies` table); the deny list is a floor no override lifts, and an override never reaches a tool Google adds later. A held tool is listed to the agent with the hold said first and without Google's `outputSchema`. The call record has a new outcome, `held`. The product `google-workspace` skill says held calls await approval.
