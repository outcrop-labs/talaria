- **Fixed: Talaria Desktop always has a way back when an instance's page does not come up. While an instance restarts behind Cloudflare, its page could hang for 100 seconds and end on Cloudflare's 524, show Cloudflare's 502 or a firewall's 403 at once, or, on Windows, WebView2's network error page — each in a window with no close, minimize or drag and no way to the launcher, because the styled titlebar is drawn by the page itself (it is the default on every OS). Now a page on the instance's own address that is not Talaria brings you back to the launcher a few seconds after it loads, saying what answered, with Retry and Back to instances; and a page that has not loaded in 25 seconds brings you back with "<instance> is not answering", Retry, Keep waiting (another minute; if Talaria comes up while the card is up, it opens) and Back to instances. A page with Talaria up is never interrupted — a failed download or a link that goes nowhere leaves it as it is — and that includes instances on an older Talaria; pages on other addresses, such as a Google or GitHub sign-in, are never judged; and an instance loaded in the background at launch that does not come up is tried again later instead of losing its notifications for the session.** Only Linux had a hook for a failed load before, and it missed a 5xx page, a 4xx page and a request that never ends. Talaria is "up" when its UI's desktop hook is there, or, on a Talaria from before the hook, when its titlebar asks the shell for its settings, which every version does as it loads. What WebKitGTK (Linux) and WebView2 (Windows) say about a failed load only gives the card its words; macOS needs none. Nothing is done inside the engine's own callback.
  Verified: on Linux, on a private headless rig (its own mutter and session bus, WebDriver on the launcher, fake instances whose beacon answers so the launcher's probe passes and the open reaches the webview, each open a click on the launcher's row), against rc's build and the first version of this change. A request held 100 s and then answered 524 (the review's B1): the not-answering card at 25.3 s, then "Fake A answered 524 (Cloudflare: a timeout occurred): it may be restarting." at 103.9 s, still up 5 s later. A Cloudflare-style 403 page, a 404 page and an HTML page with no Talaria in it: the card at 4.1 s each ("answered 403 (Forbidden)", "answered 404 (Not found)", "answered with a page that is not Talaria…"); the first version showed none of the three. A page without the hook whose titlebar asked for its settings (an older Talaria): left open. A working page whose same-origin download answered 500: left open, its page still answering. A JSON file opened in the window: left open. A navigation to another origin answering 502, and one that never finished: no card; the first version closed the first with a 502 card and the second with a stall card. A 502 at once: the card at 4.1 s; a page whose every connection drops: "did not load: Connection terminated unexpectedly." at 4.1 s; the origin answering with Talaria while the not-answering card was up: opened by itself 3.6 s later, and the launcher's card gone; Keep waiting, then the answer: open, no card; a page whose UI was up while an image held its load: left open. An instance loaded hidden at launch whose page hung: closed at 25 s and "loading it again in 60 s (try 1)", and the retry loaded it; the first version closed it and never tried again. On rc's build a held page and a 502 page got no card at all. The rig found two bugs on the way, both fixed: a page whose every connection dropped got no card (WebKitGTK raises no Finished after a load failure it is told was handled, so that failure is now judged where it happens), and the watchdog dropped a failed first load as "another origin" (a webview whose first load failed shows no http page). Unit tests cover each rule, the watch (in time, stalled, a commit, Keep waiting, a UI that is up, two pages), the prewarm backoff, the words for each status and WebView2's cancelled and download navigations. The Windows hook compiles and passes clippy for `x86_64-pc-windows-msvc` locally, with its error codes asserted against webview2-com's; `bun run check`'s threading rule covers the new callbacks, including the closure WebView2 runs. The connect smoke passes on the rig. `bun run gate` passes its check (the desktop typecheck passes on its own); its desktop clippy cannot build on this host, which has no GTK headers, so fmt, clippy `-D warnings` and the 145 tests ran in the Fedora 44 rig image. Not verified: Windows and macOS at run time (WebView2 on a real 502, 524, 403 or network error page; WKWebView), a real instance behind Cloudflare, and an older Talaria instance's real UI (the rig's stands in for its titlebar's call).
