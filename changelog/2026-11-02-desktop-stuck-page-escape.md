- **Fixed: Talaria Desktop always has a way back when an instance's page does not come up. While an instance restarts behind Cloudflare, its page could hang for 100 seconds and end on Cloudflare's 524, or show Cloudflare's 502 at once, and on Windows a network failure showed WebView2's error page — each in a window with no close, minimize or drag, and no way to the launcher, because the styled titlebar is drawn by the page itself (it is the default on every OS). Now a page that has not loaded in 25 seconds brings you back to the launcher with "<instance> is not answering" and three choices: Retry, Keep waiting (another minute; if the page loads while the card is up, Talaria opens it), and Back to instances. A page that fails — Cloudflare's 502 or 524, any 5xx, or a connection that fails — brings you back at once, with Retry and Back to instances.** Only Linux had a hook for a failed load before, and it missed a 5xx page and a request that never ends. The watchdog runs on every OS and stands down when the page's Talaria UI is up even if one slow image holds its load. A 5xx is read from WebKitGTK's main resource on Linux and from WebView2's `NavigationCompleted` on Windows, and on macOS, where the engine does not say, the shell asks the server again for a page that finished without the Talaria UI in it. Nothing is done inside the engine's own callback.
  Verified: on Linux, on a private headless rig (its own mutter and session bus, WebDriver on the launcher, fake instances whose beacon answers so the launcher's probe passes and the open reaches the webview, each open a click on the launcher's row). On rc's build, an instance whose page request is held stayed a blank window with no card for 45 s, and one answering 502 showed the 502 page with no card. With the fix: the held page brought the "not answering" card after 25.3 s (Back to instances, Keep waiting, Retry); Keep waiting showed the page again, and it loaded when the origin answered; Back to instances closed the page; with the card up, the origin answering opened the instance by itself (0.3 s and 1.3 s after the answer, on two runs) and took the card down; Retry, with the origin back, opened it at once; a page whose every connection is dropped gave "Fake A did not load: Connection terminated unexpectedly." in 0.8 s; a 502 gave "Fake B answered 502 (Bad gateway): it may be restarting." in 1.6 s; a 524 after 10 s gave the 524 card at 11.1 s; a 524 after 40 s gave the not-answering card at 25.3 s and then the 524 card at 40.9 s; a loaded page reloading into a 502 gave the card 0.2 s later; and a page whose UI was up while an image held its load stayed open, with no card. The rig found one bug on the way — a held page that answered while its card was up did not open, because its commit restarted the watch — fixed, with a unit test that fails on the first version. WebKitGTK 2.52 has no Navigation Timing `responseStatus`, which is why macOS asks the server instead. Unit tests cover the watch (in time, stalled, a commit, Keep waiting, a UI that is up, a failed page's own Finished, two pages), which answers are failures (5xx, no answer; not a 4xx; WebView2's cancelled navigation), and the macOS server look against a local server. The Windows hook compiles and passes clippy for `x86_64-pc-windows-msvc` locally, with its error codes asserted against webview2-com's; `bun run check`'s threading rule covers the new callbacks, and catches a mutation that opens an instance inline from the WebView2 handler. The connect smoke passes on the rig. `bun run gate` passes its check (the desktop typecheck passes on its own); its desktop clippy cannot build on this host, which has no GTK headers, so fmt, clippy `-D warnings` and the 143 tests ran in the Fedora 44 rig image. Not verified: Windows and macOS at run time (WebView2's NavigationCompleted on a real 502, 524 or network error page; WKWebView and the macOS server look), and a real instance behind Cloudflare.
