- **Fixed:** App-published MCP servers are governed exactly like every other server, which `docs/sdk/mcp.md` had promised and the TypeScript gateway had not kept. Team grants work: the resolver behind `/api/mcp/gw/app-<slug>` now reads `mcp_team_access` joined to `team_agents` for the agent and to `team_members` for the acting owner, with the Rust resolver's rules (a team grant counts as assignment on a scoped server; a person's own deny wins; a team deny with no allow anywhere denies; null is all tools, `[]` is none), so an admin granting an app to a team no longer gets `403 no access to this MCP server` from every agent on it. Every app `tools/call` — the refused ones too — lands as a row in `mcp_tool_calls` with the same columns and the same never-the-arguments rule as the Rust gateway's call log (tool name capped at 200, one sentence capped at 300 and scrubbed of the agent's argument strings, a fixed sentence when the call spent a credential), so Observability shows app calls beside the rest. The registry row's tool catalog, which Rust seeds as `[]` and cannot fill, is written from the module on the first load after enablement and on every build, so Manage → MCP's tool-subset picker has something to pick. A call's `arguments` must be a JSON object, and app tool arguments are checked against the advertised `inputSchema` (zod's `fromJSONSchema`, extra properties allowed; a schema it cannot compile is passed through) before the handler runs, so a wrong shape is a tool error naming the field rather than a `TypeError` naming nothing. Verified: `bun run test -- src/server/mcp-registry.test.ts` (13 tests over the agent- and owner-side grant rules, the tables faked by query shape), `bun run typecheck` (svelte-check, 0 errors), `cd mcp && bun run build`; not exercised against a live stack in this change — the call-log insert statement is the Rust one verbatim against the same schema snapshot.
