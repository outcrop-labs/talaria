- **Fix: a chat, work, plan or research reply now announces its start on the firehose, not only its end, so the tab bar's agent glyph lights when the reply starts.** The app refetches `/api/working` on the firehose's `conversation` event, and a reply sent that event only when it finished, so a reply shorter than the bar's 30-second idle poll could stream and end with no glyph. The chat route and the queued-turn path now insert the streaming reply and ring the same readers its end rings: the sender of a chat, the owner and members of a shared thread. A reply whose row is never inserted rings no one, and a reply that fails (the agent refuses, or its stream dies) now rings its end like a finished one, so the glyph its start lit goes dark at once.
  Verified: `bun run gate`. Live-DB tests ring the sender of a chat, the owner and member of a plan and not an outsider, with an id-only payload; ring the readers again when a reply is resumed; and ring no one when the write fails, even for a thread with readers. A reply that ends in an agent error or a dead stream is heard ending on Redis. Moving the fan before the write, or removing any of the start or end rings, fails a test. On a worktree stack with real agent turns, an in-page firehose log showed `conversation` at each reply's start and end, and the Comms glyph lit within 40 ms of send.
