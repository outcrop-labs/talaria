- **Fixed: an app's grants belong to the repository installed under its slug, so a different repository installed under the same slug starts with no grants; app code can no longer read or run on another app's model setting; and the harness docs' free probe now sees the harness's own.** Uninstall used to leave every person's and team's grants on the app (`/x/<slug>`, `/x/<slug>/manage`) on their rows. A different repository installed later under the same slug, even after `keptData: "wipe"`, then inherited every one of them: its members reached the work and manage surfaces nobody had granted it, against "enabling one gives members nothing". Grants are named by slug alone, so they are now tied to the record of the repository that the slug's data directory keeps (`source.json`, repository identity = host plus the owner/name path, compared without case). Short of a wipe, uninstall keeps that record, alone when the app stored nothing, and keeps the grants with it, so uninstalling and reinstalling the same repository leaves who may use the app as it was. A wipe removes them and their denials from users and teams along with the data. An install keeps them only when the record names its own repository, even when it wipes its own data. Another repository starts with none whether it adopts the data or wipes it, and so does any install of a slug whose grants no record vouches for, which covers grants an uninstall left behind before this release. Before it places the new app, the install also removes the other repository's record, so a failed write can never leave that record vouching for the new app's grants. A renamed or transferred repository has a new URL and counts as another repository: `keptData: "adopt"` hands its data over but not its grants, so grant the app again. Other apps' views, a slug that begins with this one's included, and core views are never touched. Install and uninstall answer `grantsRemoved`, and their audit rows carry it. Manage → Apps says it after an install, and the uninstall prompt says that deleting the data takes the grants too. **What an admin should do:** this release does not clean up a grant that another repository already inherited, because that repository's own record now vouches for it, and no migration can tell an inherited grant from a given one. Where a slug was reused for another repository before this release, review who holds `/x/<slug>` and `/x/<slug>/manage`. The free probe `resolveHarnessModel` and the free `runHarness` used to take a `model.slot` from app code as written, so an app could resolve or run on `app:<other>/<id>`: another app's admin-assigned model. Both now keep a slot only when it is the calling app's own, as the host knows it (`appInScope`), and log the rest as ignored. The harness docs' bridge example guarded its run with `resolveHarnessModel(triage.model)`. That spec carries no slot, while `ctx.harness.run` resolves `app:<slug>/<harness id>` first, so wherever the admin's assignment was the only model that routed, the probe answered null. The example, the export table, the SDK reference and the apps skill now probe with `{ ...def.model, slot: \`app:${ctx.app}/${def.id}\` }`.
