- **GitHub tokens are never wider than Talaria asked for: a refused mint now fails with GitHub's own reason instead of falling back to every permission the App holds, and each token is checked against what was asked.** Before it mints a repo token, Talaria reads what the App's installation holds (`GET /app/installations/{id}`, kept five minutes per api process and cleared when the host changes) and asks only for the ask met with that. An installation that lacks a permission gets a token for the rest, and the gap is logged. The old 422 retry, which re-asked with no permissions block and so got a token carrying everything the installation held, is gone, along with the code that could build a body without one. On a 422 Talaria reads the holdings once more and asks again only if that changes the ask. Otherwise the mint fails with GitHub's message and what the installation lacks. The `pr_status` read token no longer widens either: an installation without Checks gets a token for the other reads, and the answer names the missing permission. Every token GitHub returns is checked. If it covers anything but the one repository, carries a key no repo token may carry (`administration`, `members`, every `organization_*` key, the account keys) or carries an asked permission above the asked level, Talaria revokes it on GitHub with `DELETE /installation/token`, logs an alert line and never uses it. Any other key that was not asked for, apart from `metadata`, is logged and not refused. A token is served from the cache only while it has more than five minutes left, and the cache keys on a canonical permission set, so one set spelled in two orders is one mint. On a host with several App installations, a repo none of them lists is now refused, where before it was minted on the first installation, which belongs to another org. The repository listing and repo creation still mint installation-wide tokens inside the api, and each such mint is logged with its installation and purpose. `talaria-git-host-types` gains the host-neutral `Level` and `PermissionSet`. `talaria-github` gains the permission catalog: `NEVER_ON_REPO_TOKEN`, and a `GRANTABLE` table that stays empty until a Talaria surface spends a key. The sandbox token still asks for `contents:write`, `pull_requests:write` and `metadata:read`.
