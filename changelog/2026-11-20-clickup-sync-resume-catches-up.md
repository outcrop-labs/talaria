- **Resuming a paused ClickUp sync now catches the board up within a minute, not one interval later.** When a board owner presses **Resume** on a scheduled sync, its next sync is set to now. The scheduler's next tick (it runs every minute) claims it and reads everything that changed in ClickUp during the freeze. The sync then carries on at its 15-minute, hourly or daily cadence. Before, Resume set the next sync one interval out, so a daily board stayed stale for up to a day after the freeze. A manual sync stays unscheduled on Resume and waits for **Sync now**. A due sync also no longer loses its run when the board's live run reads no list (a remap or a one-ticket re-sync), which covers fixing the mapping while paused and pressing Resume while that remap still runs. The scheduler leaves the sync due and claims it at the first tick after that run ends; before, it pushed the read a whole interval out. The Resume toast, in the chip's panel and in Board settings → Sync, now says what happens next: "Syncs within a minute, then every hour" (or every 15 min, or once a day), "Syncs after this run, then every hour" while a mapping change's remap still runs, "Manual — press Sync now to catch up.", or "Scheduled syncs are off — press Sync now." on an instance with the schedule switched off. It replaces "The schedule is back on". The Pause toast now reads "Nothing reads ClickUp until you resume it." and the mapping-saved toast "Tickets follow it; ones people moved stay.": the toast host shows a body on one truncated line, and both older bodies were cut off mid-sentence. docs/BOARD-SYNC.md, the user guide (including the wait for a mapping change that is still moving tickets) and the API reference for `paused` say the same.
