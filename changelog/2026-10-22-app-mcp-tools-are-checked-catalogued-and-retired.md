- **Fixed:** an app's MCP tools are checked when the app loads, its server row carries them from the moment the app is enabled, a broken build takes the server off every agent, and app tools are never picked as the org's web-search supplier. The build probe checks each tool (a unique name of at most 200 characters using letters, digits, `_` and `-`, a description, an object `inputSchema` of at most 32 KiB, a handler). A tool that fails is left out of tools/list, tools/call and the catalog, and the reason shows on the server's card in Manage → MCP. It never disables the app. The probe writes the checked catalog beside the build (`app-builds/<slug>/mcp-catalog.json`), and the api copies it into the row on enable, at boot, and when the host asks. That ask goes through a new internal route, `POST /api/internal/apps/mcp-sync`. It accepts only a credential both processes derive from the encryption root, and the host's proxy answers 404 for `/api/internal/*`. "Discover tools" on an app server answers the stored catalog instead of a 502. When a failed build turns an app off, the host asks the api to reconcile, which removes the row and rolls the agents that carried it, and the app MCP gateway refuses every tool of an app that is not enabled. The api's boot sync now runs every time, not only when it disabled a broken app. The web-search supplier lookup drops app rows in both the api and the TS harness runner, so a pin to an app tool falls through to the platform's own engine. Verified: `cargo test` for talaria-config (the shared HMAC vector), talaria-capability-reach, talaria-apps, talaria-session and talaria-mcp; clippy `-D warnings` on every touched crate; vitest for app-mcp (new), app-health, capability-reach, rust-proxy and secretbox. Live in a worktree stack, with a throwaway app whose mcp.ts declared `mcptest_echo` and an invalid `Bad Tool`: after Rebuild and Enable, the row held only `mcptest_echo`, and its probe read `1 tool; 1 left out: "Bad Tool" has a name with characters other than letters, digits, _ and -`, which Playwright saw on the card. Discover tools answered 200 with the catalog, and the access modal's subset picker listed the valid tools. An agent with its own `tak_` key got the tool from tools/list and an echo from tools/call through `/api/mcp/gw/app-mcptest`. `Bad Tool` answered "not available here". With the row present but the app off, the gateway answered 403 `app "mcptest" is not enabled` and recorded the denial. Breaking mcp.ts and rebuilding turned the app off, deleted the row and its assignment, and left the agent's whoami with no servers. With an app tool `mcptest_web_search` ("Search the live web online") registered, and also with it pinned as the search supplier, `POST /api/search` answered from the platform's own engine (`via: null`). The internal route answered 404 through the app origin and 403 to a direct call with no token, an admin cookie or a wrong token. With the right token it answered 200. After a restart with the enabled set cleared behind the api's back, the boot sync removed the orphaned row. A dev edit to mcp.ts reached the row on the next gateway load.
