- **Fixed:** an app's MCP tools are checked when the app loads, its server row carries them from the moment the app is enabled, a broken build takes the server off every agent without losing a single grant, and app tools are never picked as the org's web-search supplier. The build probe checks each tool (a unique name of at most 200 characters using letters, digits, `_` and `-`, a description, an object `inputSchema` of at most 32 KiB, a handler). A tool that fails is left out of tools/list, tools/call and the catalog, and the reason shows on the server's card in Manage → MCP. It never disables the app. The probe writes the checked catalog to the app's data directory (`app-data/<slug>/mcp-catalog.json`), which is never served over HTTP, and the api copies it into the row on enable, at boot, and when the host asks. That ask goes through a new internal route, `POST /api/internal/apps/mcp-sync`. It accepts only a credential both processes derive from the encryption root, and the host's proxy answers 404 for `/api/internal/*`. "Discover tools" on an app server answers the stored catalog instead of a 502. When an app is turned off or its build or database fails, its row is no longer deleted (the delete cascaded every agent assignment, team grant and user grant). The row is marked off in a new `app_off` column with the reason, the agents that carried it roll and stop listing it, and the app MCP gateway refuses its tools. When the app is enabled and passes its probe again, the same row serves the same grants and those agents roll back. Only uninstalling an app deletes its row. The sync never touches the row's `enabled` flag after creating it, so an admin's **Disable server** on an app server (which the api now accepts; it used to answer 500) survives every boot and resync. Syncs run one at a time under a Postgres advisory lock, and a failed read of the enabled set fails the sync instead of taking every app server off. The web-search supplier lookup drops app rows in both the api and the TS harness runner, so a pin to an app tool falls through to the platform's own engine. Verified: `cargo test` for talaria-apps (the off/serve plan), talaria-mcp (`serving`, the wire's `appOff`), talaria-session (`require_internal` refuses no header, a session cookie, an agent key, a wrong or truncated token), talaria-config (the shared HMAC vector) and talaria-capability-reach; the new live tests `app_mcp_sync_live` (an agent assignment, a team grant and a user grant kept through an admin disable, two resyncs, a failed build and an app gone from disk, then deleted by uninstall) and `internal_routes` (403 without the token, 200 with it) against a real database; vitest for app-health (`failHealth` asks the api to resync and writes no row), the app MCP gateway route (a disabled or off app answers 403 with the reason, recorded in `mcp_tool_calls`, and its module is never loaded), app-mcp and mcp-status. Live on a worktree stack, with a throwaway app granted to a hired agent directly, to a second agent through a team, and to a person: the admin's Disable server took it off both agents, and after an api restart (the boot sync rewrote the row a second later), an internal-route resync and an app rebuild, it was still disabled. Re-enabled, both agents called the tool. Breaking `mcp.ts` and rebuilding turned the app off and marked the row off with the build error, both agents' rendered configs, whoami and MCP tabs dropped the server while their containers rolled, all three grants stayed, the gateway answered 403 and recorded it, and Playwright saw the card read APP OFF with the reason and "1 agent · 1 person · 1 team". Restoring `mcp.ts`, rebuilding and enabling the app brought the tool back to both agents with the grants intact. Uninstalling the app then deleted the row and its grants. The catalog file was in `app-data/`, and `/app-builds/<slug>/mcp-catalog.json` answered 404.
