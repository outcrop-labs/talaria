- **An agent can take a ticket out of quality review when the person it is answering asks, and a refused move leaves an Approve card any board editor can click.** Until now the api refused every agent path out of review (`triage_ticket` and `move_ticket`), so "this needs revisions, send it back" got the agent a 403. Now the agent's call carries `conversationId`, the thread it was asked in, and the api proves the ask before the move (`talaria-tasks` `asked.rs`). The caller must use its own agent key, not the org-wide shared key. The agent must be replying in that thread now: talaria-chips' new `live_turn` reads streaming rows only, so a cron, a work session or a finished chat cannot be cited. The asker must be the author of a message that live turn answers, and nobody else: a channel reply now carries the id of the message it was started for (a new `channel_messages.answers_message_id`), so a person who posts while the reply is still being decided is never taken for the asker, and a turn answering more than one person, or two of the agent's replies streaming in one channel, cites nobody. Words the agent wrote that the person only clicked (an ask option, a tool chip, a reply sent from a draft) never count: those rows are now marked `drafted`, in `messages.metadata` and a new `channel_messages.drafted` column. The asker must be able to edit the board, or both boards for a board move. The message must name the ticket by its ref, an old ref, its id or a link, unless it was written in the ticket's own discussion room. Each message moves a ticket once, claimed under a new `task_asked_exits` key. Done, failed and cancelled stay refused, asked or not. An asked exit may go to any other column, an agent-start one included, because the person chose it, and an exit back to work clears an earlier sign-off, as "request changes" does. The activity line reads "moved to inbox (asked by <email> in chat)", and a `task.review_exit` audit row (or `askedBy` on `task.board_move`) records the person, the message and the thread. A failed proof says why and points at the card. The card's gate is now the ticket's board, any editor or an admin, not the agent's personal owner, so a teammate of an org agent is no longer refused. It grants nothing an editor could not do on the board, and the card's owner can still decline it. It runs as that person, with their email and "(approved <agent>'s request)" on the line, and it resolves a ref in its payload. A new `ticket_board_move` card does the same for a refused `move_ticket`. The cards match the bare tool name, so a client's `mcp_talaria_` prefix no longer drops them, and only a refusal (a 403 or the api's own error) leaves one, never a move that landed, whatever its ticket's text says. A card names the ticket as the agent did, and a board-move card has a link to the destination board beside it, titled by each reader's own access. The `triage_ticket` grant a `ticket_move` approval used to post is gone, since nothing consumed it. Chat turns now list `triage_ticket` and `move_ticket` among the tools that take `conversationId`. Channel turns get a matching "THIS CHANNEL'S ID" line, and a channel id passed as `conversationId` now lands chips in that channel. The toolkit, the fitness catalogue, whoami's guardrails, the ticket-room prompts, the toolkit skill and the user docs say the new rule. A channel reply must start within 15 minutes of the move it makes, the window every chip resolver already uses.
  Verified: on a worktree stack (its own api on :5407 and its own Postgres), an org agent with its own `tak_` key, three boards and minted sessions, with each live turn staged as the rows the chat and channel doors write. Through the real channel door, a clicked option in the ticket room was refused and a typed "send this back to the inbox" with no ref moved it ("in the ticket's discussion"). An `ask` chip addressed by a channel id landed on the agent's reply in that channel.
