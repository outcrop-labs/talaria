- **Fixed:** **Kept app data goes back only to the repository it was kept from, opening Manage → Apps no longer spends a workspace secret, and an update keeps its record true when it fails.** These are the review findings on #588. (1) The automatic update check no longer asks a source that is read with a workspace secret. Each check spent a use of the secret and wrote a `secrets.spend` row, so viewing the page could use up a limited secret and leave the app unable to update. Such an app now shows **update not checked**, and Update fetches with the secret. Sources read with a GitHub-minted token, and public ones, are still checked. (2) Install now writes the repository into the app's data directory (`app-data/<slug>/source.json`), and an uninstall that keeps the data keeps that record too. For an app installed before this change, uninstall writes it from the source record. A reinstall from the same repository adopts the data as before. A different repository installed under the same slug, or kept data with no record, is refused with a 409 that names both repositories, until the request says `keptData: "adopt"` or `"wipe"`. Before, it silently got the old app's store and database password. Manage → Apps shows both choices as buttons. (3) A host typed with capitals (`https://GitHub.com/…`) now gets its credential. Git is pointed at the parsed URL with the host lowercased, so askpass answers for it. Before, the token was minted and git never received it. (4) Install now takes the same per-slug lock as update and uninstall, so it cannot race either one. (5) When the new version fails and swapping the old one back also fails, the answer now says `rolledBack: false`. The UI says that `apps/<slug>` holds the new commit, and the record follows. (6) A failed update no longer deletes `apps/.<slug>.prev`. The version an update replaces stays at `.next` until the new one is live, so `previousSha` always names what `.prev` holds. (7) A released update now discards the build its stage made. On a platform without the atomic swap, update is refused before it fetches anything. (8) The published schema and both validators now agree on `triggers`. A trigger has exactly one of `cron` or `event`, and that one is a string that is not only whitespace. Verified: new `#[ignore]`d live tests in `talaria-apps` (`lifecycle::live`) run against a freshly migrated scratch database. They use local bare git repositories and a mock app host over HTTP. They drive install → update (lands, fails to build, the stage call errors, fails to load, swap back fails) → uninstall (keep and wipe), and the trees and `app_sources` are asserted after every step. They also cover the kept-data refusal, adopt and wipe, the legacy record, and the slug lock: all 4 pass. Before this change, a new `git_credentials` test failed with git's own `could not read Username for 'http://LocalHost:…': terminal prompts disabled`; it passes now. There are new unit tests for the passive check, which must not touch credentials when a secret is named, and for the kept-data decision. The shared manifest fixture has new trigger cases that both hosts assert. A schema test reads `triggers.items` case by case against the validator, and it fails on the old schema. `update.test.ts` has a release test. `cargo test`/`clippy -D warnings` pass on `talaria-apps`, `talaria-app-manifest` and `talaria-routes-admin`, and `bun run gate` is green.
