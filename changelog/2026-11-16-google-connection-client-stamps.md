- **Every Google connection remembers the OAuth client that minted it, and refreshes with that client wherever it now sits.** OAuth binds a refresh token to the client it was issued to (RFC 6749 §6), but until now every stored grant refreshed with whichever client was in the connections slot, so moving a client between slots would have broken every grant it minted. The three token stores (`google_connections`, `google_org_connection`, `agent_google_connections`) gain `oauth_client_id`, `reconnect_reason` and `reconnect_flagged_at`. Each connect callback records the client its exchange ran on. If Google sends no new refresh token on a reconnect, the old token stays, and so does its client. The upgrade stamps existing grants with the Admin UI's connections client when that record is complete, because every refresh so far ran on it. On an env-configured install, a grant with no recorded client tries each configured client in order (connections, the env pair it shadows, sign-in, its env pair) and records the first one Google accepts. Refresh now goes through one door, `vend_grant`, which uses the recorded client in either slot or a shadowed env pair. A grant whose client is configured nowhere is never sent to Google: agents, Home, a person's artifact export to Drive, the brief and approvals read "This Google connection was granted to OAuth client `<id>`, which is no longer configured on this server. Reconnect it, or an admin can add that client back under Admin → Google Workspace." Routes answer it as a 409 `reconnect_needed`, and an approval goes back to `pending` (`not_connected`). When Google refuses the client (`invalid_client`, or `unauthorized_client` from the client the grant names), the grant is kept and flagged with Google's own words. It is never cleared, because one bad secret paste would otherwise disconnect everyone and open the login domain gate. A successful refresh clears the flag, and so does saving a new secret for that client. `invalid_grant` still clears the grant. A grant with no recorded client is cleared only when a client answered `invalid_grant` and every other answered `invalid_grant` or `unauthorized_client`, read by its code: RFC 6749 §5.2 defines it as "The authenticated client is not authorized to use this authorization grant type.", a client saying the grant is not its own. So a dead grant is cleared whichever of the two Google gives a client that did not mint it. A flagged grant with no recorded client asks the person to reconnect first and an admin second. Every write after a refresh is checked against the refresh token it used, so a reconnect that lands mid-refresh is never re-stamped, cleared or flagged by an answer about the old token. `GET /api/integrations/google`, `GET /api/integrations/google/org` and `GET /api/fleet/defs/{id}/google` carry `clientId` and `reconnectReason`. The Connections, Assistant, org and agent cards show the reason with a Reconnect button, and the org and agent cards show the client. `GET /api/admin/google-client` carries `census`: live grants per client, with the slot that client is in now (`shadowed` for the `ui/.env` pair behind a slot's Admin record, which only refreshes), how many are flagged, and the grants not yet recorded. The connections card lists it as **Stored connections by client**. docs/GOOGLE-WORKSPACE.md gains "Which client a connection refreshes with". Its advice for an install whose client missed the agentic lock changes from "do not swap the connections client" to the swap: move the old client to the sign-in slot and save the new agentic one as connections.
