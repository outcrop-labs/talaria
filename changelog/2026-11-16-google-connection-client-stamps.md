- **Every Google connection remembers the OAuth client that minted it, and refreshes with that client wherever it now sits.** OAuth binds a refresh token to the client it was issued to (RFC 6749 §6), but until now every stored grant refreshed with whichever client was in the connections slot, so moving a client between slots would have broken every grant it minted. The three token stores (`google_connections`, `google_org_connection`, `agent_google_connections`) gain `oauth_client_id`, `reconnect_reason` and `reconnect_flagged_at`. Each connect callback records the client its exchange ran on. If Google sends no new refresh token on a reconnect, the old token stays, and so does its client. The upgrade stamps existing grants with the Admin UI's connections client when that record is complete, because every refresh so far ran on it. On an env-configured install, a grant with no recorded client tries each configured client in order (connections, the env pair it shadows, sign-in, its env pair) and records the first one Google accepts. Refresh now goes through one door, `vend_grant`, which uses the recorded client in either slot or a shadowed env pair. A grant whose client is configured nowhere is never sent to Google: agents, Home, the brief and approvals read "This Google connection was granted to OAuth client `<id>`, which is no longer configured on this server. Reconnect it, or an admin can add that client back under Admin → Google Workspace." Routes answer it as a 409 `reconnect_needed`, and an approval goes back to `pending` (`not_connected`). When Google refuses the client (`invalid_client`, `unauthorized_client`), the grant is kept and flagged with Google's own words. It is never cleared, because one bad secret paste would otherwise disconnect everyone and open the login domain gate. A successful refresh clears the flag, and so does saving a new secret for that client. `invalid_grant` still clears the grant, but a grant with no recorded client is cleared only when every configured client answered `invalid_grant`. Every write after a refresh is checked against the refresh token it used, so a reconnect that lands mid-refresh is never re-stamped, cleared or flagged by an answer about the old token. `GET /api/integrations/google`, `GET /api/integrations/google/org` and `GET /api/fleet/defs/{id}/google` carry `clientId` and `reconnectReason`. The Connections, Assistant, org and agent cards show the reason with a Reconnect button, and the org and agent cards show the client. `GET /api/admin/google-client` carries `census`: live grants per client, with the slot that client is in now, how many are flagged, and the grants not yet recorded. The connections card lists it as **Stored connections by client**. docs/GOOGLE-WORKSPACE.md gains "Which client a connection refreshes with". Its advice for an install whose client missed the agentic lock changes from "do not swap the connections client" to the swap: move the old client to the sign-in slot and save the new agentic one as connections.

  Verified: proven by tests. `cargo test --lib` on talaria-google-client, -connections, -errors, -pending, -org, -agent and -oauth passed 65 unit tests locally. They use only bodies captured from Google on 2026-11-12. They show that a recorded client in either slot or a shadowed env pair is the only client asked, and that an unknown recorded client makes zero calls to a counting stub token endpoint. A grant with no recorded client tries each client in order, stops at the first Google accepts and records it. A refused client flags the grant in Google's words and never clears it. A dead grant is cleared only when every client says so. A transport fault writes nothing. The named reconnect survives being carried as text, so Home's routes, the agent routes and the executor all answer it. An `#[ignore]`d live-DB test (`stamp_live`) passed locally against the worktree's Postgres. It uses a loopback token endpoint that records the `client_id` of each refresh, and the token tables copied from the migrated schema. In it, a grant recorded with client A refreshed with A after A moved to the sign-in slot, and the stub saw only A. A grant with no recorded client asked C, then A, and recorded A. A grant recorded with a client configured nowhere made no call. The org grant, refused with `invalid_client`, kept its refresh token and stored `invalid_client: The provided client secret is invalid.`. The login gate's own read still saw the org account. Clearing the flags and fixing the secret let it refresh. `pending/tests/release_live` against Google's real token endpoint, with a client Google does not know and no real credential, released the approval and flagged the grant `invalid_client: The OAuth client was not found.`. Upgrade, exercised in the worktree's Postgres: a database with the 6 new statements rolled back and an Admin record for `upgrade-client-a` was migrated (`applied: 6`), and every grant in all three stores was stamped. With only a half-saved record, the grants stayed unstamped for the trial. The schema snapshot diff is the nine new columns. Clippy `-D warnings` on the ten touched crates passed locally. **Not proven live:** a real consent through two real clients, a real cross-client refresh, and old grants still refreshing after a real orientation-N swap.
