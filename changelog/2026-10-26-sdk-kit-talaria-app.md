- **Added: an app can be checked, built and evaluated outside the host — the instance serves an SDK kit and a `talaria-app` CLI, and a workbench job on a Talaria app gets them from `prepare_env`.** `@talaria/sdk` resolved only inside a Talaria checkout, so an app in a repo of its own — a Developer Agent's plugin repo above all — had its first compile on the host, after a merge and an install, where a failure turned it off. `GET /api/sdk/kit.tgz` now serves a kit built with the ui and versioned with the host build (`x-talaria-kit-version`: the host build stamp, then a digest of the kit's contents): declarations for `@talaria/sdk`, `/server` and `/testing` generated from the host's own SDK (so `ctx.harness`, `ctx.agents` and `triggers` included), the shared-module list, `talaria.json`'s schema, the host's own build recipe, load probe and harness replay bundled to run with no host and no database, and `talaria-app scaffold | check | build | eval`. `scaffold` writes the skeleton `talaria app new` writes (one source; `talaria app new` gains `--harness` too). `check` holds `talaria.json` to the host's rules, typechecks against the kit's declarations (only what an app may import resolves) and runs the app's own tests. `build` runs the host's recipe and probe and reports per surface, per MCP tool and per harness, skipped harnesses named as Manage → Apps names them, on the host's own build key. `eval` replays every harness fixture against replies recorded in `harnesses/recorded/`, or through the instance's gateway with `--gateway --model <id>` (`--record` keeps the replies). A signed-in member or an enabled agent on its own credential may fetch the kit. For a repo with a `talaria.json` at its root, `prepare_env` fetches the kit as the agent, installs it once per version on the department volume, links `talaria-app` onto the terminal's PATH, gives the repo a node for the checkers, and records an eval session; the relay now books a workbench-key call that carries a recorded session to that job and its ticket. The host's build recipe now refuses, by name, a bare import it does not share (`"zod" is not shared with apps: …`) — the same failure as before on the host, said the same way in the kit even where the package would resolve. Verified: vitest suites for the kit (arguments, scaffold, the slug an install would take, the declarations' rewrite, a reproducible tar, the checkers' configs, both eval transports, the eval run over recorded, failing and gateway replies), the kit route, the build guard and the proxy; the client-docs typecheck compiles the starter harness; `cargo test` for the workbench MCP (the kit block run in a shell against a stub instance) and the relay; and, on a stack running this branch merged with rc, the whole loop — the kit fetched with a session and with an agent key (and refused without either), an app scaffolded with a harness in an empty repository outside any checkout, checked (typecheck, its own MCP test), built, evaluated against its recorded reply, a trigger using `ctx.harness` typechecked and built, the app installed from a local bare repository on the same build key the kit reported, enabled, served and rendered; then `prepare_env` for a workbench job in a sandbox container running the agent image, which installed the kit and node, after which `talaria-app check`, `build` and `eval --gateway --record` ran from the agent's login shell and the gateway turn showed on the job's ticket usage.
