- **Fixed: a Developer Agent's job now starts with a working coding harness. Before, the agent had to repair the harness itself first.** On the live engineering agent, the five work sessions of 3 and 4 November spent 13 to 75 turns each, about 12 to 18M tokens in all, on harness repair before their first coding step. TALA-83 took 55 minutes to reach one. The agents hand-downloaded bun 1.4.4 because `npx …@latest` omp refused the repo's pinned bun 1.4.0. They copied the shared, root-owned `PI_CODING_AGENT_DIR` into private dirs, and TALA-93 then ran on the dir made for TALA-92. They also pasted the persona's key into `models.yml` to get past a 401. Now `start_job` provisions the job before it hands out a single command, as the agent's user inside its sandbox, in five steps: sandbox, clone, toolchain, harness, preflight. It clones the job's branch, installs the repo's toolchain, installs a pinned Oh My Pi (`OMP_VERSION` 18.16.0) once per volume, and gives the job its own harness dir and launcher (`/opt/data/workbench/harness/jobs/<jobId>`). The launcher runs omp on the harness's bun by path, so a repo that pins an older bun no longer breaks it. The preflight then checks, without a model call, that the launcher starts omp, its dir is writable, the model is in omp's catalog and the gateway accepts the workbench key. The harness lines are handed out only after the preflight passes. A failure goes on the job (`workbench_jobs.provision`: the failing step, its error and the tail of its output), in the `start_job` / `job_status` answer, on the ticket's activity, on the ticket strip and in `GET /api/workbench/jobs`. The agent never discovers it by running the harness. `job_status` provisions a job that started from the queue or after approval, and takes over a provision whose run died; `prepare_env` provisions again. Also: the stale-sandbox token now lives in the container's env (`TALARIA_SANDBOX_SHAPE`), because the old file sat in a live bind and so called a container from 22 September current. A failed sandbox command now reports its exit status and output, so doctor no longer prints `the probe could not be run in the sandbox: .`. The workbench image no longer bakes in an unpinned omp. The `oh-my-pi` and `workbench-driving` skills say to run harness turns in the background, which avoids the terminal's 420 s foreground cutoff.

  Verified: on this branch's own stack (app :5305, the Rust api :5405) with a real Developer Agent (Hermes v0.22.4, Z.ai GLM 5.3 through the gateway) on a local Forgejo fixture repo that pins bun 1.3.14 (`mise.toml`). The agent was given a ticket. It called `start_job`, got `provision.state: ready` (sandbox, clone, toolchain, harness, preflight all ok), and its next tool call was the given launcher line, run in the background. That was its first coding step, with zero install, PATH, auth or harness-dir calls before it. omp added `multiply` and its test, and `bun test` passed (2 pass) on the repo's own bun 1.3.14. In the same checkout, the old `npx -y @oh-my-pi/pi-coding-agent@latest --version` printed `error: Bun runtime must be >= 1.4.4 (found v1.3.14)`. A fixture that pins `node = "0.0.1"` failed provisioning at `toolchain`. `start_job` returned no harness lines, the error read `mise ✗ node@0.0.1 … failed: HTTP status client error (404 Not Found)`, the output carried mise's log, and the ticket got the line `Workbench provisioning FAILED at toolchain: …`. Unit tests: `cargo test -p talaria-workbench-harnesses -p talaria-workbench-mcp -p talaria-fleet-docker -p talaria-fleet-render -p talaria-routes-workbench`. They cover the launcher, the runtime and preflight scripts, the preflight verdict, the record, the claim, `next`, the error-line pick, and a real `git clone` of a branch that leaves an existing checkout untouched.
