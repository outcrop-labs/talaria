- **Fixed: a Developer Agent's job now starts with a working coding harness. Before, the agent had to repair the harness itself first.** On the live engineering agent, the five work sessions of 3 and 4 November spent 13 to 75 turns each, about 12 to 18M tokens in all, on harness repair before their first coding step. TALA-83 took 55 minutes to reach one. The agents hand-downloaded bun 1.4.4 because `npx …@latest` omp refused the repo's pinned bun 1.4.0. They copied the shared, root-owned `PI_CODING_AGENT_DIR` into private dirs, and TALA-93 then ran on the dir made for TALA-92. They also pasted the persona's key into `models.yml` to get past a 401. Now `start_job` provisions the job before it hands out a single command, as the agent's user inside its sandbox, in five steps: sandbox, clone, toolchain, harness, preflight. It clones the job's branch, installs the repo's toolchain, installs a pinned Oh My Pi (`OMP_VERSION` 18.16.0) once per volume, and gives the job its own harness dir and launcher (`/opt/data/workbench/harness/jobs/<jobId>`). The launcher runs omp on the harness's bun by path, so a repo that pins an older bun no longer breaks it. The preflight then checks, without a model call, that the launcher starts omp, its dir is writable, the model is in omp's catalog and the gateway accepts the workbench key. It checks the model the job's lines will actually name: the ticket's pinned plan, else the agent's, else the org default. The harness lines are handed out only after the preflight passes. A clone, toolchain or harness step that fails quickly is retried once. The clone goes to a temp dir that is renamed into place only once it has a HEAD. omp installs are swapped in by symlink, under a lock that never falls through, so a running job's install is never deleted; an install is pruned only two days after it was retired, and only when no process maps it. A provision stops as soon as its job ends. A failure goes on the job (`workbench_jobs.provision`: the failing step, its error and the tail of its output), in the `start_job` / `job_status` answer, on the ticket's activity, on the ticket strip and in `GET /api/workbench/jobs`. Its output is scrubbed first, string by string: credential-shaped text, and the secret values the sandbox was given (never a `CI=true`). The agent never discovers it by running the harness, and is told to retry once, then comment and call `report_outcome` with `errorMessage`; it never moves the ticket. `job_status` provisions a job that started from the queue or after approval (a resumed revise round starts with no provision), takes over a provision whose run died, rebuilds one whose model moved after its preflight, and provisions a failed one again when asked (`retry: true`); `prepare_env` provisions again. The Work view recognizes the new launcher line as a harness turn. Also: the stale-sandbox token now lives in the container's env (`TALARIA_SANDBOX_SHAPE`), because the old file sat in a live bind and so called a container from 22 September current. A failed sandbox command now reports its exit status and output, so doctor no longer prints `the probe could not be run in the sandbox: .`. The workbench image no longer bakes in an unpinned omp. The `oh-my-pi` and `workbench-driving` skills say to run harness turns in the background, which avoids the terminal's 420 s foreground cutoff.
