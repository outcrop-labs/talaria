- **Fixed: `implied_completion` now judges an app's harness runs.** The relay skips its guard pass for an app's key, because the app host's runner guards the reply. But the runner only ran the structural rules, so the semantic rule, the one the operator's decision model judges, ran nowhere for an app. After its own pass, the runner now hands the run's final reply, with the tool record that pass read, to a new internal door, `POST /api/internal/apps/{slug}/guard` (root-derived service credential only, never forwarded by the proxy). It does this once per run. The api judges the semantic rules the harness keeps (all of them when `guard.rules` names none) while an admin has them on, detached, and files any finding under the run's caller stamp. Each rule is still judged once: the structural ones in the host, the semantic ones in the api, and the relay runs neither for an app's key. The host's rule registry declares `implied_completion` as a judged rule, so an app harness may now name it in `guard.rules`; that used to fail the load check as a rule that "does not exist". A fitness replay and `talaria-app eval` judge nothing, as they file nothing. Porting the rule to TypeScript was not an option: the decision model and its key live in the api. Judging each relay call was not either: a call cannot tell a run's answer from a repair or loop turn, and never sees a tool record the harness grounded itself. HARNESSES.md's note of the gap is gone. Verified: `bun run gate` (the ui typecheck and suites, and clippy and tests for every api package this touched), TS tests (the registry matches guard.rs's rule table, judged ones marked; `runGuardrails` never runs a judged rule; the runner hands over the final reply, tool record, model and caller once per run, also after a repair, carries a harness's own grounding, and asks nothing when the admin has the rule off, the guard is off, the harness does not keep it, or the reply is empty), `cargo test -p talaria-decide` (95, plus the semantic ids matching the registry's) and the door's body tests in `talaria-routes-admin`. Live on a worktree stack, with a mock upstream registered as a gateway endpoint and set as the `gateway` decision model, an app's harness run returned a reply claiming a finished deploy. The decision model was asked once with an empty tool record, and `guard_findings` recorded `implied_completion` (medium, 0.93, caller `app:w5demo:w5demo:report`) beside the runner's own `zero_tool_claim`. A reply that claims nothing was judged and filed nothing. With the toggle off, no judgment was asked for.
