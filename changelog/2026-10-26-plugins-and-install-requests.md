- **A Developer Agent can ask for the app it built to be installed, and the installed app remembers who maintains it, who it is for and where its tickets go; repos Talaria creates get their default branch protected.** A new `plugins` record links an installed app (through its existing `app_sources` row, so repo, branch and installed commit are never repeated) to the maintaining agent, the person it was built for, the board of the ticket that started it, a git host (`github`) and an admin-set update policy (`approve` by default, or `auto`). The workbench gains `request_app_install(repo, ref?, why?, taskId)`: the repo must be one the agent is granted, the ticket is required, and a repo already installed or already requested is refused. It raises a new `app_install` approval (admin-only, its text bounded to the ticket's board like `repo_request`). Manage → Apps → Installed lists the requests: **Install** runs the same credentialed install as Install from Git, records the plugin and lands the app disabled (enabling and granting stay admin steps), kept data from another repository asks adopt or wipe first, and **Reject** takes a reason. Every outcome is one line on the requesting ticket. A read-only `plugin_status` tool reports the installed and latest commits, the repo's open PRs with their checks and review decision, the app's enablement, build and manifest refusal, and its harness report. A plugin's card shows its maintainer, owner, board and ticket, and an admin changes its update policy there (`PUT /api/admin/apps {app, updatePolicy}`, audited). Approving a `request_repo` now adds a ruleset that blocks force-push and deletion on the new repo's default branch (no required reviews or checks); the approver can untick it, and when GitHub refuses (a private repo on a free plan) the repo is still created and the answer, the request row and the ticket line say why.
