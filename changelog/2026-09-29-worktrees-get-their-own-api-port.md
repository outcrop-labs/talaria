- **A worktree gets its own Rust api port, so two stacks can no longer share one database.** `talaria worktree` gave each stack its own app, Postgres and Redis ports, but the Rust api stayed on the fixed `:5274` for every stack — and `talaria dev` deliberately **adopts** an api already listening there rather than double-binding. So the second worktree to start proxied every `/api/*` request to the *first* worktree's api, which is pointed at the first worktree's database: two app servers on one database, which is the single thing [`docs/WORKTREES.md`](./docs/WORKTREES.md) and AGENTS.md most insist cannot happen. It was silent, too — the app answered normally throughout, because it was serving someone else's data rather than failing.

  The slot now allocates a fourth port (`app 53xx · api 54xx · Postgres 56xx · Redis 65xx`, all four probed free together) and writes `TALARIA_API_PORT` into the worktree's `ui/.env`. Two halves had to be joined for that to mean anything: `talaria dev` now reads `TALARIA_API_PORT` from `ui/.env` and not only from the shell — the file was previously ignored, so the port the proxy dialled and the adopt-probe tested both fell back to `:5274` — and the variable joins the lift list into the cargo child, because the api reads it for its own **bind** (`talaria-config`, same 5274 default). Without both, an api would bind one port while the app dialled another. The shell still overrides the file, as it does for the S3 lift. `TALARIA_API_PORT` also joins the strip-list when main's `ui/.env` is copied: `envValue` returns the *first* match, so a line inherited from main would have shadowed the appended one and put the worktree quietly back on the shared port.

- **`talaria worktree` waits for main's database, not just its container.** The precondition was `docker inspect` on main's Postgres, which only proves the container exists. The seed then runs `pg_dump` against the `talaria` **database**, and a postgres still running its entrypoint has not created it yet — so a worktree created moments after `talaria dev` died with `psql: FATAL: database "talaria" does not exist` half way through: after the git worktree and both containers existed, and before `ui/.env` was written, which is the one step that makes the checkout usable. It now waits on `pg_isready -d talaria`, which answers for the database the seed is about to read, and says so distinctly when the wait runs out.

- **`node_modules` is ignored as a symlink as well as a directory.** The pattern was `node_modules/`, which matches a directory only, and a worktree shares the primary's by symlink — so every worktree showed `?? ui/node_modules` in `git status` for ever, noise in front of real changes and one careless `git add` from committing a link that resolves on one machine.

  Verified: `bun test` in `cli/` — 8 worktree cases and 20 dev cases pass, including new ones for the four-port slot, the api port landing in the generated `ui/.env` at `slot + 100`, main's inherited `TALARIA_API_PORT` being stripped rather than shadowing it, `ui/.env`'s port being read by `talaria dev` with the shell still winning, and `pg_isready` against main being called *before* `pg_dump`. `bun run gate` green. The symlink fix confirmed with `git check-ignore -v ui/node_modules` in a live worktree.
