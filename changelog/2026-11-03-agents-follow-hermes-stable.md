- **Added: agents keep themselves on Hermes' stable releases — each instance checks `nousresearch/hermes-agent:stable` every six hours, waits until a new release has been on stable for 48 hours, tests it in a throwaway canary, and moves its agents onto it one at a time in a 02:00–05:00 maintenance window, watching each before the next, and puts every agent back by itself if the release fails. No Talaria release is needed for a Hermes release.** Until now every agent ran the Hermes pin compiled into the release (`v0.22.4`), so each Hermes release waited for a Talaria pull request, release and upgrade. Now the check is an anonymous manifest HEAD, which Docker Hub does not count against its pull limit. A new digest is downloaded in the background (through the agents' own download, after any other download finishes) and read with networking off for its own config schema version, the env names its Hermes strips, and its drain tools. Every agent always runs a resolved digest, never `stable`, and its config is stamped with its own image's schema version instead of the compiled one, so a newer Hermes never tries to migrate the read-only config. A release waits 48 hours from this instance's first sight of it (`TALARIA_HERMES_MIN_STABLE_HOURS`), so one the community finds broken is usually replaced first. Then, in the window (the workspace time zone; configurable) or on **Roll now**, it boots as a canary with a rendered config and no channels, users, credentials or model to call, and stays up for a 5-minute soak. Agents then restart onto it one at a time. An agent that is working or about to — a turn, a long tool call, a cron run or one due within 15 minutes, a work session or workbench job, a conversation message in the last 10 minutes — is passed over and tried a minute later, and one busy all window moves in a later window instead of holding the release. Each moved agent is watched (healthy, its restart count unchanged, no new config error in its log) for 10 minutes after the first and 3 after each later one before the next moves, and the whole rollout soaks 15 minutes before the release is called good. A failure the host caused (docker timing out, a saturated disk) is retried later and never counts against the release. A failure the release caused puts that agent back at once and is tried once more; the second time, the release is marked bad, every agent it reached moves back, and every admin is notified. **Allow again** lifts a ban. An admin's Roll back or Pin pressed mid-rollout stops it where it stands and moves the fleet as asked. The channel's state is read strictly: a row that cannot be read moves nothing and alerts the admins, as do checks failing for 3 days and a rollout open for 7. **Manage → Agent image** (admins) shows the version each agent runs, the channel, the last check, the rollout, the versions marked bad and why, and the history, with Check now, Roll now, Roll back, Pin (any version not marked bad, or a `vX.Y.Z` tag) and Allow again. The previous version stays on the server for three days after the new one is good, then images the instance downloaded itself are removed. **To opt out:** Pin a version on the panel, or set `HERMES_IMAGE` in `fleet/.env` as before; a chassis image of your own also turns the channel off. A server that cannot reach Docker Hub keeps its agents where they are and shows the failed check. A server upgrading from an earlier release runs the compiled pin first, then moves to stable in a later window, so pre-pulling the pin before upgrading (`docker pull nousresearch/hermes-agent:v0.22.4@sha256:7a69201726bc64db2072a1371557137c23312d29705cda2b8ea2a0214a50a4cf`) still makes the upgrade quick.
