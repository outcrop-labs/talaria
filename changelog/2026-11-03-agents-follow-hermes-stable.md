- **Added: agents keep themselves on Hermes' stable releases, unattended — so before upgrading, an operator who wants every agent held where it is sets `HERMES_IMAGE` in `fleet/.env` (or Pins a version on the panel afterwards), and sets the workspace time zone so the 02:00–05:00 maintenance window falls at night. Otherwise each instance checks `nousresearch/hermes-agent:stable` every six hours, waits until a release has been on stable for 48 hours, tests it in a throwaway canary, moves its agents onto it one at a time in the window, watching each before the next, and puts every agent back by itself if the release fails. A Hermes release needs no Talaria release — unless it changes something Talaria relies on, and then it is held for an admin.** Until now every agent ran the Hermes pin compiled into the release (`v0.22.4`), so each Hermes release waited for a Talaria pull request, release and upgrade. The check is an anonymous manifest HEAD, which Docker Hub does not count against its pull limit. A release is not even downloaded until stable has named it for 48 hours (`TALARIA_HERMES_MIN_STABLE_HOURS`, counted from the first check that saw it there and started again whenever stable moves), and a waiting release that stable stops naming is never rolled out: it gives way to whatever stable names now. The download goes through the agents' own, after any other download, and never past the disk's room — the docker disk must hold the image and keep a tenth free (a rollback's, a fiftieth), or the release waits and the admins hear it; a disk the api cannot read holds the download until Roll now. The image is read with networking off for its own config schema version, the env names its Hermes strips and its drain tools, and its contract with Talaria is checked, in a container with networking off, read-only, as nobody and with no capabilities: Hermes' own config migration must change nothing Hermes reads of any agent's rendered config — MCP servers, platforms and toolset lists included, a credential typed in literally replaced by a stand-in (Talaria stamps the image's own version, so Hermes never migrates the read-only config) — sealed `CONFIG_*` credentials must stay out of an agent's commands, a scheduled job Hermes claims must still read as running, and the canary must answer the fields Talaria reads to tell whether an agent is working. A release that fails one is **held for review** on the panel, with what changed, until an admin presses **Accept and roll out** — which covers those problems only; a new one holds it again. Then, in the window (the workspace's time zone, else the server's `TZ`, else the zone most admins chose, else UTC — the panel says which) or on **Roll now**, it boots as a canary with a rendered config and no channels, users, credentials or model to call, and soaks for 5 minutes. Agents then restart onto it one at a time. An agent that is working or about to is passed over and asked again a minute later: a reply being written or a conversation in the last 10 minutes, a turn in flight in its Hermes API server, a messaging-platform turn, a scheduled job running (the claim Hermes refreshes every minute while the run lives) or due within 3 minutes, a work session or workbench job. One whose Hermes does not answer is not restarted on its own — Roll now and Pin restart it — and a Hermes from before the channel (v0.21.4, with no live run counts) is judged by the rest of its answer; one busy all window moves in a later window, and one left behind three windows in a row is said to the admins, again every week. An agent that is down — stopped with **Stop**, `docker stop` or `compose stop`, removed by `compose down` — is assigned the new image and starts on it when someone starts it: the channel never starts it. It recreates a down agent only when docker says it crashed (seen twice), or when the channel's own recreate left it down; a Stop pressed during a recreate stands. (A chassis whose agents run `restart: no` leaves a crash exited, which reads as stopped.) No agent is moved onto an older Hermes than it runs, and an agent that fails goes back to what it ran. An agent counts as moved only once its container runs the image, so a roll that did not land is moved again, and one running another image than its own opens a catch-up onto it; one that fails a catch-up is left on what it ran, and the admins told, until the image changes or Roll now. Each moved agent is watched (healthy, its restart count unchanged, no new config error in its log) for 10 minutes after the first and 3 after each later one, and the whole rollout soaks 15 minutes before the release is called good. A failure the host caused (docker slow or refusing, the network between the api and the fleet, a pull that failed, a full or saturated disk) is retried after 15 minutes, then twice as long each time to six hours, and the third in a row tells the admins once. A failure the release caused puts that agent back and is tried once more; the same thing failing again, or a third failure of anything, marks the release bad, rolls back every agent on it, and notifies every admin. A reboot or docker restart during a soak is the host's; a release no agent ran is not called good; a release stable withdraws after some agents moved onto it takes them back first. **Allow again** lifts a ban. **Roll back** moves every agent on the version being left now, mid-turn included. A version already known good here is never banned; a Pin to one stops at its first agent that will not come up healthy. A channel state this release cannot read (one a later release wrote) pauses only the updates — hiring, starting and editing agents never read it — and **Reset** on the panel sets it aside and starts afresh. **Manage → Agent image** (admins) shows the version each agent runs, the channel, the last check, the rollout, held and banned versions with their reasons, and the history. The previous version stays on the server for three days after the new one is good, a candidate nobody rolled out for a week; then images the instance downloaded itself are removed. `TALARIA_HERMES_MIN_STABLE_HOURS` and `TALARIA_HERMES_STABLE_REF` pass through `docker/compose.yml`. A server that cannot reach Docker Hub keeps its agents where they are and shows the failed check. **On a server upgrading from an earlier release, the channel keeps what it finds.** Its first step (1½ min after boot) records the stop of every agent found down, so each stays stopped, and assigns every running agent the image it runs (`:latest`, recorded as found), so nothing but the channel changes an agent's Hermes. On image installs, the deploy's own fleet roll waits for that step (at most 30 min) and restarts each running agent on its own Hermes. Agents on an older Hermes than the compiled pin (main's `:latest` was v0.21.4 on most hosts) move onto the pin in the first window: the pin is inspected and canaried, the agents move one at a time, each watched, and the move stops at the first agent that will not come up, which goes back on what it ran while the admins are told. Agents at or above the pin stay where they are. Stable's release then takes the whole fleet on, once it has been on stable for 48 h (typically night 3). The old `:latest` is pruned a week after it was found, once no container uses it. Pre-pulling the pin (`docker pull nousresearch/hermes-agent:v0.22.4@sha256:7a69201726bc64db2072a1371557137c23312d29705cda2b8ea2a0214a50a4cf`) saves night 1 its download.
