- **Fixed: an agent with the browser toolset on now really has a browser.** On the pinned Hermes v0.22.4 image, a hired agent was offered no browser tool at all, even though its `browser` box was ticked. There were two causes, both inside Hermes. First, the image ships Chromium but not the `agent-browser` CLI that drives it. The CLI is pinned in the image's own package lock, but Hermes only offers browser tools when the CLI is already installed. Second, Hermes's default browser is `browser_exec`, which it offers only to an agent that also has the `terminal` toolset. In that default mode it also withholds the built-in `browser_*` tools, and a new Talaria agent starts with the terminal closed.
  - **Each start now installs the engine first.** Before an agent whose rendered config keeps `browser` on starts (hire, start, roll or reconcile), Talaria runs `hermes pm install agent-browser` in a one-shot `compose run --rm` of the agent's own service, as the image's `hermes` user. The engine lands on the agent's state volume. It is the image's own pinned, sha256-checked package, installed by the image's own package manager, and it drives the image's own Chromium. Nothing is exec'd into a running agent and no browser is installed. On a roll the install runs before the drain, so the agent keeps serving while it runs. A failed install is logged with Hermes's own reason, and the agent starts anyway, without browser tools. The render lists which departments need the engine in `fleet/browser-engine.json`.
  - **A start waits at most 90 seconds for the install.** On a host whose network drops packets instead of refusing them, pm's own retries would otherwise hold every start for minutes. A one-shot that runs past 90 s is removed. Every start then skips the install for 5 minutes, so a reconcile of many agents pays the wait once. A fast failure, such as no DNS, is not remembered, so the first start after the fix installs.
  - **The render picks the browser that can work.** An agent with the terminal closed gets `browser.backend: 'off'`, which gives it Hermes's built-in `browser_navigate`, `browser_click`, `browser_vision` and the rest. An agent with the terminal open, such as a Developer Agent, keeps Hermes's default, `browser_exec`. A def that authored its own backend keeps it. A backend Hermes itself reads as unset, such as an empty string, is filled like a missing one.
  - **That browser can reach your own network, and the docs now say so.** Hermes refuses private addresses to `web_extract`, but not to its built-in browser while the terminal backend is local, even when the agent has no terminal. A terminal-less agent's browser can therefore open the host, other agents' containers and the LAN. Talaria writes that agent a `security.website_blocklist` of the host names that can only be private: `internal` (which covers `host.docker.internal`), `localhost`, `local`, `home.arpa`, and the loopback literals. That list matches names only, so an IP address still gets through. It is a speed bump, not a boundary: turn `browser` off for an agent that must not reach your network (`docs/AGENT-NETWORKING.md`).
  - **The toolset grid says which browser the agent has.** It names the backend a def authored when there is one, says "none" for a `browser-use` backend with the terminal closed, and says that the engine needs the npm registry.
