- **Admins can give a Developer agent the GitHub `workflows` permission on a git host: every repo the agent holds there gets it on its git token, narrowing the grant revokes the tokens already handed out in every api process, and grant changes are now audited.** GitHub permissions above the base (`contents: write`, `metadata: read`) are now set per agent and per host in a new table, `agent_github_permissions`, and apply to every repo the agent is granted on that host. `workbench_repos` stays the repo gate. `GET /api/workbench/github-permissions/{agentId}` shows, per host, what the agent holds, what the host's App asks for, and each granted repo's installation, holdings, shortfall and default-branch protection. The agent's managers can read it. `PUT` with `{host, from, to, acknowledge?}` is **admin only**: an agent's managers get 403. It is a compare-and-set, so a stale `from` gets 409 with what is there now. It accepts only what talaria-github's catalog allows: `workflows`, at write, the one key git itself spends. A key the App's registration does not ask for is refused. A PAT or Forgejo host takes nothing, because its own token decides. Adding `workflows` reads each granted repo's default-branch protection (the branch's ruleset rules, then its classic protection flag, both readable without `administration`). A repo not known to require a pull request needs `acknowledge: true`, which the `workbench.github_permissions` audit row records with every repo's state. The credential door now mints each agent's token separately (two agents on one repo are two tokens) and asks for the base plus the agent's token-spent permissions, never one a Talaria tool spends. After a mint it re-reads the grant, the Developer switch and the permissions, and revokes a token minted against a grant that changed meanwhile. Taking a permission back, removing a repo grant, turning the Developer switch off, and retiring or deleting the agent each revoke the agent's tokens (`DELETE /installation/token`) in this process and, through a Redis broadcast on `git:token-revoke`, in every other api process, with `github.token_revoked` and `github.token_revoke_failed` audit rows. An admin alert covers a revoke GitHub did not confirm, and another covers agents given a permission their installation has not accepted. A holdings refresh that finds the installation newly accepting it writes `workbench.github_permission_activated`. The repo grants editor now keeps the grants on a host whose repository listing failed (a GitHub listing that reads nothing is now an error, not an empty pool). It writes a `workbench.repo_grant` audit row for every add and removal, revokes a removed grant's tokens, and makes branch-rule changes admin-only while the agent holds permissions on that host. Approving a repo request now adds that one grant instead of rewriting the agent's grant set. docs/PERMISSIONS.md states the admin-only carve-out, and docs/WORKBENCH.md documents the whole flow and the risks that remain.

Narrowing one agent sends a `DELETE` for that agent's token alone, filtered by host and repo, and its next ask mints again. A token taken back is revoked and never served again.
