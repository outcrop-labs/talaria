- **Admins now set each Developer agent's GitHub permissions per git host — its whole set, any permission GitHub's App catalog knows, organization keys and `administration` included — and the agent's git token carries exactly that set as far as the App's installation holds it; narrowing it revokes the tokens already handed out in every api process.** A new table, `agent_github_permissions`, holds one set per agent and host, applying to every repo the agent is granted there (`workbench_repos` stays the repo gate). An agent with no set carries the default, `contents: write`, `pull_requests: write` and `metadata: read` — what every agent's token carried before #742, so `pull_requests: write` is back and no agent regresses. `GET /api/workbench/github-permissions/{agentId}` shows, per host, the set and whether it is the default, each key with its scope and whether the installation holds it, what the host's App asks for, and each granted repo's installation, holdings and shortfall, beside the default and the catalog. The agent's managers can read it. `PUT` with `{host, from, to}` is **admin only** (managers get 403) and a compare-and-set: `from` is what the editor read (`null` for the default), a stale `from` gets 409 with what is there now, and `to: null` puts the agent back on the default. The only check a set passes is talaria-github's new `CATALOG` of GitHub's repository and organization permission keys and the levels GitHub takes each at: an unknown key or level, or an empty set, is a 400. What the App does not ask for yet is said in the answer's `notes`, not refused. A PAT or Forgejo host takes no set: its own token decides, and the PUT says so. Every write is a `workbench.github_permissions` audit row. The credential door mints each agent's token separately (two agents on one repo are two tokens), asks for the agent's set met with what the installation holds, and after a mint re-reads the grant, the Developer switch and the set, revoking a token minted against a grant that changed meanwhile. If GitHub refuses organization keys on a token for one repository, the mint asks once more without them, and the agent gets the rest with the organization keys as its shortfall and GitHub's message in the `git.credential` audit row (`shortfallWhy`). The credential is never failed over them. talaria-github's `NEVER_ON_REPO_TOKEN` refusals and the empty `GRANTABLE` allowlist are gone. The reply check still revokes a token for anything but the one repository, carrying an asked key above the level asked for, or carrying a key that was not asked for (`metadata: read` aside, which every token carries). Narrowing an agent's set, removing a repo grant, turning the Developer switch off, and retiring or deleting the agent each revoke the agent's tokens (`DELETE /installation/token`) here and, through a Redis broadcast on `git:token-revoke`, in every other api process, with `github.token_revoked` and `github.token_revoke_failed` audit rows. An admin alert covers a revoke GitHub did not confirm. Another, informational, covers agents set a permission their installation has not accepted. A holdings refresh that finds the installation newly accepting it writes `workbench.github_permission_activated`. The repo grants editor now keeps the grants on a host whose repository listing failed (a GitHub listing that reads nothing is now an error, not an empty pool), writes a `workbench.repo_grant` audit row for every add and removal, and revokes a removed grant's tokens. Approving a repo request now adds that one grant instead of rewriting the agent's grant set. docs/PERMISSIONS.md states the admin-only carve-out, docs/WORKBENCH.md documents the model and the risks that remain, and the agents' talaria-toolkit skill no longer says the GitHub credential carries contents alone: it carries the agent's set, by default contents and pull requests to write and metadata to read.
