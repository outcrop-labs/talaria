- **Fixed: one broken file in an app's `harnesses/` no longer fails the app's build and switches the app off, one malformed app harness no longer drops every app's harnesses from Models → Fitness, and Manage → Apps' harness lines follow the enabled set.** Since #589 the harness build sat in the same try as the client, server and MCP builds, so a syntax error, an import that does not resolve, or a shared package bundled into one harness file failed the whole build, and reconcile disabled the app (build recipe 3 rebuilt every installed app on upgrade, so an app with a stray harness file was switched off at boot). The build now compiles `harnesses/` on its own terms: when the combined build fails, each file is compiled alone to find the ones that break it, the rest are built into `harnesses.js`, and each file left out is named in its new `skipped` export with the compiler's sentence (one line, the app's own path, no code frame). If even that fails, the app still builds, with no harness. The host reads `skipped` and reports each file as "it failed to compile: …" on the app's row. Build recipe 4. The load probe's checks now cover every field the listing puts on the wire: a JSON harness's `repair` must be a whole number from 0 to 5 (NaN and Infinity reached the api as null, and past a u32 the api failed the whole listing and fell back to the builtins), the `model` spec's pin, role and chain must be names and a list (`chain: 3` threw inside the listing route, which answered 503), and `floor.suppliable` and `widen.requires` must be lists. A definition whose checking throws is a problem on that harness. On the api side, `talaria-app-harnesses` decodes the listing one entry at a time: an entry it cannot read is skipped with a warning and reported on its app, and the others still register. The harness reports in Manage → Apps are rewritten for every enabled app whenever the enabled set changes: after each live load probe, when a failed app is switched off, and when the api enables, disables or uninstalls an app (a new `POST /api/app-host/harnesses`). So when an app that sorts first is enabled and claims the same id, the app that held it now shows the skip, and gets the id back when that app is switched off. A disabled app's chip reads "N harnesses · not registered". A skipped harness is logged once per distinct app, file and problem per process, in the host and in the api, instead of on every listing the fitness matrix's polling triggers. The fitness sweep's skip for an app harness that wants its own tool loop now names the real reason (an app harness cannot be dry-run in the api's sandbox) instead of saying the model can neither run its own loop nor be handed tool definitions.
