- **Fixed: creating an agent on a server that does not have the agent image yet no longer stalls and fails — the download is its own step of the hire, the roster shows it moving ("downloading the agent image — 412 MB so far, 36 of 38 layers ready (4 min)"), the hire finishes when the image lands however slow the link, and a hire that fails anyway has a Retry on its row.** The Hermes image is about 1.1 GB to download and 4.5 GB on disk, so the server needs about 6 GB free. A server downloads it for its first agent, and every server downloads it again on its first start after a pin bump (this release moves the pin). To make the first hire after upgrading instant, pull the pin on the server first: `docker pull nousresearch/hermes-agent:v0.22.4@sha256:7a69201726bc64db2072a1371557137c23312d29705cda2b8ea2a0214a50a4cf`. On main the download ran inside `compose up`'s 120-second deadline, so on a link slower than about 9 MB/s or a busy disk the first hire was killed mid-download every time, and so was every Start after it. On rc it ran ahead of `up` with a 20-minute deadline, but inside the hire's boot step, which the run engine files as an error at 10 minutes and never retries. A download slower than about 2.5 MB/s failed the hire with "step exceeded maxStepMs (600000ms) at phase "starting the container"", and the roster said "starting the container" the whole time. Now the pull is one per service in the api process, on a task of its own. The hire's new pull stage waits 15 seconds at a time on it and shows its bytes and layers as the phase, or "waiting for docker to start downloading the agent image (2 min)" while docker has not begun. A Start, roll or re-entered hire of the same agent joins the download in flight instead of starting another (two different agents run two pulls, and docker downloads each layer once for both), and a caller that goes away no longer cancels it. A Start now downloads the image before it takes the agent's lock, so a Stop or Retire pressed during the download lands at once, and the start it interrupted does not happen afterwards. "Start all agents" answers within 75 seconds and finishes in the background, instead of holding the request past Cloudflare's 100 seconds; its outcome and each agent that would not start are logged and written to the audit row. A Start the stop cancelled says "Not started: a stop was asked while the agent image downloaded", on the agent and on the hire alike. The pull reads compose's `--progress json` events, and is stopped only when docker says nothing for 10 minutes or after 3 hours, never for being slow. A hire that fails says what to do: Docker Hub's pull limit, a full disk, a download that stopped, docker never starting, or docker's own error for a container that would not start (not compose's first line of progress, "Container … Creating", which is all the row used to say). A failed hire's row now has a Retry (`POST /api/fleet/hires/{id}/retry`). It runs the hire again on the same agent, which the create modal refused before, because the failed hire had already taken the handle and the department. Only the agent's managers and admins can retry it, and only its newest hire. An agent deleted since can be retried only by an admin, or by the person who ran that hire if they still hold `agents.manage`. A second Retry of the same row is refused, and so is a retry of an agent that has run since: that agent is its people's to start. The newest failed hire of an agent that is still a draft stays on the roster whatever its age, so drafts left by hires that failed before this upgrade (on main, a cold server's first hire always did) appear there with a Retry: press it, and the roster shows the download and the start. Deleting the draft and hiring again also works. An `up` killed at its deadline that left the container half-created waits for docker to show the container, then runs once more, which starts it. The boot step's ceiling is 15 minutes, up from 10. The roster drops a failed row once a newer hire of the agent exists or the agent runs.
