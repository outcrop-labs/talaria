- **Fixed: creating an agent on a server that does not have the agent image yet no longer stalls and fails — the download is its own step of the hire, the roster shows it moving ("downloading the agent image — 412 MB so far, 36 of 38 layers ready (4 min)"), the hire finishes when the image lands however slow the link, and a hire that fails anyway has a Retry on its row.** The Hermes image is about 1.1 GB to download and 4.5 GB on disk. A server downloads it for its first agent, and every server downloads it again on its first start after a pin bump (this release moves the pin). On main the download ran inside `compose up`'s 120-second deadline, so on a link slower than about 9 MB/s or a busy disk the first hire was killed mid-download every time, and so was every Start after it. On rc it ran ahead of `up` with a 20-minute deadline, but inside the hire's boot step, which the run engine files as an error at 10 minutes and never retries. A download slower than about 2.5 MB/s failed the hire with "step exceeded maxStepMs (600000ms) at phase "starting the container"", and the roster said "starting the container" the whole time. Now the pull is one per service in the api process, on a task of its own. The hire's new pull stage waits 15 seconds at a time on it and shows its bytes and layers as the phase, or "waiting for docker to start downloading the agent image (2 min)" while docker has not begun. A Start, roll or second hire that asks meanwhile joins the download in flight instead of starting another, and a caller that goes away no longer cancels it. The pull reads compose's `--progress json` events, and is stopped only when docker says nothing for 10 minutes or after 3 hours, never for being slow. A hire that fails says what to do: Docker Hub's pull limit, a full disk, a download that stopped, docker never starting, or docker's own error for a container that would not start (not compose's first line of progress, "Container … Creating", which is all the row used to say). A failed hire's row now has a Retry (`POST /api/fleet/hires/{id}/retry`): it runs the hire again on the same agent, which the create modal refused before, because the failed hire had already taken the handle and the department. An `up` killed at its deadline that left the container half-created waits for docker to show the container, then runs once more, which starts it. The boot step's ceiling is 15 minutes, up from 10. The roster drops a failed row once a newer hire of the agent exists or the agent runs.

  Verified: live on this branch's own worktree stack (app :5311, api :5411, a fresh database). Both then hit FLEET-4 under the stall: `up` timed out creating the container, and the second `up` hit a name conflict while the create was still landing. That is why the second `up` now waits for the container and the row shows docker's error. Retry on each row answered 200, and each agent was up and healthy 20 s and 30 s later.
