- **Changed: the `talaria-apps` product skill teaches a Developer Agent to build, ship and maintain an app as a plugin, with what the instance now does, and `talaria-app scaffold` fills in a new repo around a seed `talaria.json`.** The skill said a new app "starts as a new repo a human creates and grants you" and knew nothing of the SDK kit, `talaria-app`, `request_repo`, `request_app_install` or upkeep. It now walks the whole path: `request_repo` with `appSlug` for a new app (an admin approves; the GitHub App creates and grants a private repo), `start_job`, a seed `talaria.json` and `prepare_env` (which installs the kit only for a repo with a `talaria.json` at its root, so an empty new repo got no `talaria-app` before), `talaria-app scaffold`, the `check && build && eval` loop before every `finish_job`, `request_app_install` after a person merges, and the job sweep's upkeep (a red PR resumes the maintainer, a merge becomes an update approval, breaks and eval regressions become maintenance tickets on the originating board), with `plugin_status`, `pr_status` and `app_harness_fitness` as the read-only tools. Its references cover every tool argument and refusal sentence, the manifest (slug, surfaces, triggers, the `sdk` range), harnesses (`ctx.harness.run`/`stream` on the request, MCP and trigger contexts; model choice by the admin's per-app slot or `role`, `pin` naming a platform agent; who may pin an agent; tool loops; `ctx.agents.turn`; the `app:<slug>` budget and its refusal), the shared imports (`"zod" is not shared with apps: …`) and the rule as shipped for `package.json`: an app has none, and the kit's is the only one. The skeleton reference is generated from `cli/src/cmd/app/skeleton.ts` — the source `talaria-app scaffold` and `talaria app new` write from — by `bun run docs:api`, and `bun run check` fails when it drifts. `scaffold` now treats a `talaria.json` with none of the app's other files beside it as a seed, keeping every key it declares, and names an app after its checkout's `origin` repository rather than a workbench job's directory. `workbench-driving` and `talaria-toolkit` point at the skill; `docs/APPS.md`, `docs/sdk/README.md`, `docs/sdk/outside-the-host.md` and `docs/WORKBENCH.md` link it and no longer say a harness runs through `runHarness` or that an app imports zod. Verified: `bun run gate` (check, the ui typecheck and the whole ui vitest run); the sdk-kit vitest suite (the seed kept, a broken seed refused, an app named from its origin); `bun run check` passing, and failing on a hand-edited `skeleton.md` and on a `skeleton.ts` change left ungenerated; the generator and `bun run check` run in a copy of the tree with no `node_modules` anywhere (and `bun --no-install`), regenerating the reference byte-identical; on a worktree stack, the kit fetched with a minted session and, in a fresh directory outside any checkout, the skill followed in order on a clone of a one-README repo — seed, kit install as `prepare_env` runs it, `talaria-app scaffold --harness`, `sdk` declared, `check && build && eval` all passing — plus every failure sentence the skill quotes (the shared-import refusal on the server and in a surface, also with a `package.json` and `node_modules` beside the app, the scaffold refusals, the missing slug, `MISSING`, the eval usage errors and a build that stops eval), and every code example in the skill's references typechecked, built and its tests run by the kit.
