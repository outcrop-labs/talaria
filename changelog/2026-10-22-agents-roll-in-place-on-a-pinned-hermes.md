- **Fixed:** Rolling a running agent works again, config edits reach a running agent without a roll, and every host runs the same pinned Hermes. Three things were wrong.
  - **Rolls of running agents could never succeed.** The blue/green roll started a second container on the agent's state volume while the first still ran. Every Hermes since v2026.4.30 holds an `flock` on `/opt/data/gateway.lock` in that volume, so the second gateway logged "Cannot reserve gateway profiles: Gateway runtime already owns profile /opt/data" on every s6 respawn and was discarded after about two minutes. Rotate-key therefore left the agent on a revoked key, and every MCP call it made returned 401 until someone stopped and started it by hand. The Developer switch, Roll and Roll all failed the same way. A roll now recreates the container in place (`compose up -d --force-recreate --no-deps`) and waits up to 180s for health. Slot-B rendering, port churn and the `-b` cutover are gone. An agent an old roll left in `agent-<dept>-b` moves back to `agent-<dept>` on its next roll. The home service's image is pulled while `-b` is still serving, so a failed pull puts the agent back on `-b` instead of leaving it with no container.
  - **Stops can now drain.** A plain `docker stop` never drains a Hermes agent, whatever the grace: s6-overlay revives the SIGTERMed gateway and KILLs everything 3s later. Every stop, restart, remove and roll now stops the gateway through s6 inside the container first (`s6-svc -d`, then `s6-svwait -D`), so Hermes holds cron and `/v1` runs open for up to its 30s drain floor before exiting. The render gives every service `stop_grace_period: 45s` as the outer bound, and nothing is retired with `docker rm -f` any more. A stop, restart or recreate that fails before it reaches the container brings the gateway back up (`s6-svc -u`), so a failed step never leaves an agent running without one.
  - **Config edits never reached a running agent.** Since 2026-10-20, `config.yaml` was replaced by an atomic rename under a single-file `:ro` bind, so the container kept reading the inode it started with. The render now rewrites `config.yaml` and `SOUL.md` in place (`write_in_place` in `talaria-fleet-brain`): same inode, under an `flock`, skipped when the bytes are unchanged, never truncated first, with the mtime bumped last so Hermes's stat-signature cache always sees the final write. The file ends in a YAML `...` document end, so the stale tail a shrinking rewrite briefly leaves is a parse error, and Hermes keeps serving its last good config through it. Because a written config is live at once, the render widens each agent's gateway scope to its old and new models before it writes any `config.yaml`, and narrows it to the new set afterwards. A model change therefore never meets a relay that refuses the id Hermes just switched to.
  - **The image floated.** `nousresearch/hermes-agent:latest` was never pulled, so each host ran whatever it had cached first. The chassis now pins `nousresearch/hermes-agent:v0.22.4@sha256:7a69…a4cf`. A host's `fleet/chassis.yml` is copied once and never rewritten, so the render treats every stock default a template ever shipped (the old `:latest`, and from now on each past pin) as not chosen and renders the current pin. A pin bump appends to that list, so it reaches hosts seeded on an older pin too. An image an operator wrote stays theirs, and `HERMES_IMAGE` still overrides both. A host pulls a pin it lacks before any start or roll (`compose pull --policy missing`; a failed pull leaves the running container untouched). The workbench image builds `FROM` the same pin, and the chassis CI smoke pulls it. To bump the pin, see `docs/ARCHITECTURE.md`, "The fleet".
  - **`LLM_MODEL` is no longer provisioned.** Hermes ignores it (it reads its model from `config.yaml` alone), and a spec-less agent's gateway scope no longer falls back to it.

  Agents started before this change are still reading an orphaned `config.yaml` and need one roll. On an image install the post-deploy fleet roll does it. Checkout and dev installs never roll the fleet on upgrade: run **Roll all** (`POST /api/fleet/roll`) once after upgrading.

  Verified on the worktree stack against the pinned v0.22.4 image, with a Z.ai endpoint behind the gateway:
  - **Before (unmodified rc).** A roll of a healthy agent failed after about 2 minutes ("replacement never became healthy"). The incoming container's gateway log showed the profile-ownership error on every respawn. A render-only toolset edit changed the host's `config.yaml` (new inode, 716 bytes) while the container still read the old one (727 bytes), and Hermes's `GET /v1/toolsets` still listed the old set.
  - **Roll.** Done in 49s. The new container ran the pin rendered from a chassis with the legacy `:latest` line and no `HERMES_IMAGE`, with `StopTimeout=45`. Its `config.yaml` was the host's inode, and `/v1/toolsets` showed the edit.
  - **Edit without a roll.** Closing `file` and `image_gen` by render alone landed in the same running container (same id and start time). The file kept its inode, and `/v1/toolsets` dropped both at once. Reopening them shrank the file cleanly to `...\n`, and Hermes logged no parse error. A re-render with nothing changed left the mtime untouched.
  - **Key rotation.** The old key answered 401 at once. The roll finished in 23s, and the new container's `TALARIA_AGENT_KEY` matched `fleet/.env` and got 200 from `/api/agent/whoami`.
  - **Drain.** A plain `docker stop -t 45` took 3.9s and cut an in-flight `/v1/chat/completions` off. With the s6 drain, a roll started 4s into a 400-word turn finished the turn (200, the whole reply; Hermes logged `drain took 21.37s … api_at_start=1, api_now=0`), and the new container came up healthy. An idle stop took 4.9s and exited 0.
  - **Legacy slot.** An agent placed in a running `agent-rolls-b` container rolled home: `active_slot` went to `a`, `-b-1` was drained and removed, `-1` came up healthy on the same port, and chat answered.
  - **Legacy slot, failed pull.** With `HERMES_IMAGE` pointed at a tag that does not exist, a roll of an agent in a running `agent-rolls-b` failed in 3s with "could not pull the image for agent-rolls … not found". `active_slot` stayed `b`, and `-b-1` kept its container id and start time, stayed healthy with its gateway up, and answered chat. With the override removed, the next roll moved it home in 23s, healthy, and chat answered.
  - **Failed stop.** With `fleet/.env` unreadable, compose failed after the drain. The control-route stop answered an error, the container kept running, its gateway came back up within seconds, and chat answered. For contrast, a gateway drained the same way and left alone was still down 20s later (health unreachable) until `s6-svc -u`.
  - **Scope order.** A render-only model switch on a running agent (`glm-5.3-flash` to `glm-4.5-air`) was run with a trigger logging every write to the scope row. The widened row (both models) landed at 22.677s, the `config.yaml` mtime is 22.697s, and the narrowed row (`glm-4.5-air` alone) landed at 22.700s. The container was not restarted, and its next turn went upstream as `glm-4.5-air` (usage row).
  - **Roll after these fixes.** Done in 22s, with a new container id, healthy, and chat answered.

No past pin exists yet, so a host seeded on one was not exercised live. `ui/src/server/chassis.test.ts` (10 tests) checks the pin, the workbench `FROM` and the grace. Not exercised: a real pull of a missing pin, because the image was already on the host. CI is the compile and test proof for the Rust crates.
