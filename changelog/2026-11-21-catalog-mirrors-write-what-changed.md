- **The catalog mirrors write only what changed, and Postgres ships with WAL settings for a slow disk.** The MCP catalog's liveness job stamped `live_checked_at` on every entry it probed, changed or not, and that column was indexed: each of the 3,600 probes an hour rewrote a ~1.2 kB entry row and all six of its indexes, the bulk of a production instance's WAL. The probe's time now lives in a new `mcp_library_liveness` table (one narrow row per entry, its primary key the only index, fillfactor 50), so a re-stamp is a HOT update in place, and the entry row is written only when the verdict or its detail changes. The table is backfilled from `live_checked_at` in the run's own order; `live_checked_at` stays for one release, unread and unwritten, so a rolled-back image still rotates; its index is dropped, and expression statistics on `entry->>'url'` let the run's selection hash-join the stamps instead of probing them 45,000 times. The catalog sync drops an entry's stamp in the same statement when the entry is new or changed, so a changed entry is still asked first and shows no check time until then, and each run sweeps stamps whose entry is gone. Search and the featured shelf read `checkedAt` from the stamp table by key for the rows they return. The skills index sync keeps a sha256 of the parsed rows and writes nothing when they match the mirror's, which the docs site's ETag (new on every deploy) never told it; otherwise it updates only the rows that differ, inserts new ones and deletes vanished ones, in one transaction as before. A price refresh writes each endpoint in one synchronous transaction instead of one autocommit a statement; if a statement fails it redoes that endpoint with each statement in its own savepoint, so a refused price still records its `source_failed` lookup. `docker/sidecars.compose.yml` starts Postgres with `wal_compression=lz4`, `checkpoint_timeout=15min` and `max_wal_size=1GB` (the default, spelled out); `synchronous_commit`, `fsync` and `full_page_writes` stay on, and the flags reach an instance at its next `talaria deploy up` (the in-app updater rolls only the app). Verdicts, details, `checkedAt`, dead counts, the install gate, the 300-per-5-minutes cadence, skills rows and ranks, and price values are unchanged. Verified: CI on this PR's checks, including the in-crate live tests against Postgres (a second identical liveness pass leaves every entry row's xmin alone and its 120 re-stamps are all HOT in 3 async commits, a flip rewrites exactly its own row, an entry re-pointed mid-probe keeps its row and its stamp, the never-stamped go first and orphans are swept; the sync drops a changed or re-listed entry's stamp and keeps an identical one, and search and the shelf return the stamp's time; an identical skills index writes 0 rows, one changed entry is one row version, a vanished one is deleted, and every listing matches the old store's row for row; a refresh's rows for an endpoint carry one xmin, and a refused upsert still records `source_failed`), and `cli/src/sidecars.test.ts` (the three flags pinned; no durability flag in any compose file). Measured with three new `#[ignore]`d census tests (`TALARIA_WRITE_CENSUS=1`) over synthetic data shaped like a production instance (65,133 catalog entries, 45,685 of them hosted https; a 19,742-row skills index; one endpoint with 175 models), on a throwaway `postgres:16-alpine` with nothing else connected, one CHECKPOINT per 5-minute step: one hour of liveness at a 3% verdict flip rate went from 72 async commits, 3,600 non-HOT entry rewrites and 66.9 MB of WAL to 72 async commits, 108 entry rewrites and 3.29 MB (0.60 MB with no flips, 8.99 MB at 10%), and to 1.97 MB with the new flags; an identical skills sync went from 19,742 rows and 61.7 MB to 0 rows and 0 bytes, 1% changed from 63.3 MB to 3.2 MB (198 rows), and one row inserted at the top still rewrites the 19,742 shifted ranks (65.1 MB to 61.1 MB, the worst case); a price refresh went from 339 synchronous commits to 1.
