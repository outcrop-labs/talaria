- **Fixed: a stable server release no longer takes GitHub's "Latest" flag from the desktop updater feed, and the release pipeline now proves each shipped desktop build can open an instance.** The desktop updater reads `/releases/latest/download/latest.json`, so GitHub's Latest release is the feed, and today that is `desktop-v0.11.0`. `release.yml` opened a stable `vX.Y.Z` release with no Latest flag, and GitHub makes a new release Latest by default. The first stable tag would have moved the feed to a release with no `latest.json` until its installers were attached (and with none at all if a desktop job failed), and every installed app's update check would have answered 404. `release.yml` now creates and edits every `v*` release with `--latest=false`. `desktop-package.yml` creates its `desktop-vX.Y.0` mint with `--latest=false` and marks it Latest explicitly (`gh release edit --latest`), after its `latest.json` is uploaded. Before, GitHub's default made the mint Latest when it was created, so the feed also 404'd while its assets uploaded. `bun run check` holds both flags (`release-latest-is-the-desktop-feed`, `scripts/release-latest.mjs`): it fails on a dropped `--latest=false`, a mint left to GitHub's default, a Latest flip before the `latest.json` upload, or any other workflow marking a release Latest. RELEASING.md, the cut-release skill and docs/DESKTOP.md say that the server release is never Latest. `desktop-package.yml`'s installer smoke only asked whether the app was still running after 20 s, which a frozen app passes. It now runs the connect smoke (`desktop/packaging/connect-smoke.mjs`) on what ships: the exe the Windows installer put on the runner, the binary inside the macOS `.app`, and the binary the Linux deb installed. A release build that cannot open an instance now fails before anything is attached. CI gets three changes. The e2e job now runs on any crate under `api/crates/`, since the api binary it boots depends on all 243 of them; shared crates such as `talaria-db` and `talaria-state` used to skip it. The migrations job runs the compensating git-hosts statements (#651) on the fresh and the upgraded database, not only applies them. `scripts/gate.mjs` runs the ui suite for the same files ci.yml's ui surface lists, and its self-test fails when the two lists differ. The release docs no longer say the notes link is pinned to the tag (it is `blob/main/CHANGELOG.md`). They now say what a stable rolls under (its own version) and what to do when the roll refuses on an empty `changelog/` right after an RC: skip it.
