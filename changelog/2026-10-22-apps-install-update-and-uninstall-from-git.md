- **Changed:** **An app installed from git can now come from a private repository, be updated to a newer commit with automatic rollback, and be uninstalled without losing its data; a manifest the rules refuse is turned away at install with the reason.** One manifest validator (a new `talaria-app-manifest` crate, mirrored by `ui/src/server/app-build/manifest.ts` and pinned to the shared fixture `api/tests/it/fixtures/app-manifest.json`) runs on install, update and discovery: a required `name`, the `surfaces` shape, an optional `slug` (held to the install rule and the reserved words), an optional `sdk` range the host checks against its SDK version (1.0.0, one constant on each side pinned by the fixture), and reserved `harnesses`/`triggers` keys. It is published as `docs/sdk/talaria.schema.json`. An installed directory whose manifest fails is listed in Manage → Apps as **broken manifest** with the reason, cannot be enabled, and can be uninstalled; before, a manifest without a name installed "successfully" and left an app nobody could see or remove. Install fetches the one commit into a staging directory, checks the manifest, takes the declared slug (else the repository's name, or an override), refuses a taken or reserved one, renames the tree into `apps/<slug>`, records the repository, ref and commit in a new `app_sources` table, and asks the host to build it rather than waiting on the file watcher. A github.com repository the GitHub connection can see is read with a repo-scoped token narrowed to a new read-only `REPO_READ_PERMISSIONS` (never widened on a refusal); another host's private repository is read with a workspace secret named in the install, whose Spendable-at list must name that host and whose spend is audited. The token reaches git only through `GIT_ASKPASS`, answered only for that host, with no credential helper and `GIT_TERMINAL_PROMPT=0` — never in the URL, a command line or `.git/config`. `PUT /api/admin/apps {app, update: true, ref?}` (admin, audited as `app.update` or `app.update-failed`) fetches the new commit into `apps/.<slug>.next`, has the host build and probe it there while the live app keeps serving, swaps the two trees in one `renameat2(RENAME_EXCHANGE)` and keeps the old one as `apps/.<slug>.prev`; a version that fails to build or load, before or after the swap, is rolled back and the app stays enabled on the previous commit. `GET /api/admin/apps?updates=1` (admin) says, per app, whether its ref now points at a newer commit (`git ls-remote`), and Manage → Apps shows each app's repository, ref and short commit, **update available**, an Update button and the outcome. Uninstall now keeps the app's data (database files, `db.env`, the sealed password) unless `wipeData` is set, and a reinstall reattaches it; with `wipeData` the store is emptied while its database still runs, the database is stopped, and the data directory — owned by the database container's user — is removed through a throwaway container. The compose file and any update staging trees go either way, and the host's directory watcher stops an app's database when its directory leaves instead of deleting its data (and no longer writes a failed build pointer back for an uninstalled app). A fresh app database's first start now waits for Postgres over TCP, so an install's first build no longer fails with "database did not start: read ECONNRESET" while initdb's socket-only server is up. `TALARIA_APPS_LOCAL_SOURCES=1` (dev only, lifted from `ui/.env` by `talaria dev`) lets a stack install from `file://` or loopback `http://`. Verified: `bun run gate` passed (check; svelte-check 0 errors over 5588 files; ui vitest 143 files / 2188 tests; cli typecheck and 263 tests; and `cargo fmt --check`, `clippy -D warnings` and tests, each `-p`, for the 15 api packages the stack touches), the migration replays against a scratch `postgres:16-alpine` with `schema.snapshot.sql` regenerated, and `bun run docs:api` renders `PUT /api/admin/apps` as its three variants. Unit tests: talaria-app-manifest, talaria-apps (including a mock smart-HTTP git server that demands a token: the secret reaches git through askpass and in no request line, a missing credential fails at once without a prompt, askpass refuses another host, a github.com repository gets the connection's read token and a refusal falls back to anonymous), talaria-users, talaria-github and talaria-routes-admin tests pass; the TS manifest, update, build and app-host suites pass. Live on a worktree stack, in `talaria dev` and again under `server-entry.ts` in production mode: an app scaffolded with `talaria app new` and committed to a local repository installed through Manage → Apps → Install from Git (built on install), enabled, and stored a record; a new commit showed **update available**, Update moved it from 6f3636f to f0fed9e with its record intact; a commit that broke the build was rolled back with the app still enabled on f0fed9e and its staged build removed; a commit that loaded only where it was staged failed its live probe after the swap and was swapped back; invalid manifests (unknown surface, `sdk: ^2.0`, no name) were refused with their reasons and left nothing in `apps/`; a hand-placed broken app was listed with its reason, refused enable and uninstalled; uninstall keeping data removed the container, code, build and compose file and kept `pg/`, `db.env` and the password, and a reinstall reported and reattached the record; uninstall with `wipeData` ran `truncate docs` in the running database, then stopped it, then removed the root-owned files through a throwaway container, leaving no data directory or password; a private repository on a local git host that demands a token installed only with a workspace secret listing that host (no credential: "terminal prompts disabled"; a secret locked to another host: refused by name), its spend was audited, and its updates, an up-to-date check, a commit-pinned ref and a switch back to `main` worked through the same secret; in production the app database container saw no stop or restart during an update.
